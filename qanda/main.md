# Kubernetes. Что такое оператор в Kubernetes? Как их делать?
- работают как клиенты API и расширяют его возможности
- задача - автоматизация и кодификация операционных знаний о приложении: как его развертывать, обновлять, масштабировать, бекапить и восстанавливать после сбоев
- это программное расширение, которое использует Custom Resources (CR) для управления приложениями и их компонентами, следуя принципу цикла управления (control loop)
- состоит из:
  - Custom Resource Definition (CRD) расширение API Kubernetes, которое определяет новый тип ресурса (например, `SampleDB` или `PostgreSQL`). CRD описывает, какие поля и настройки могут быть у пользовательского ресурса
  - Controller: непрерывно отслеживает изменения пользовательских ресурсов и приводит реальное состояние системы к желаемому (reconciliation)
- При создании экземпляра CR (например, `SampleDB`), контроллер видит это и автоматически создает необходимые ресурсы Kubernetes (StatefulSet, PersistentVolumeClaims, Job и т.д.), а также управляет их жизненным циклом
- как создать оператор:
  - Operator SDK. на базе Kubebuilder. Go, Ansible, Helm. Самый распространенный путь для «классических» операторов на Go
  - Kubebuilder. Go. Часто используется напрямую или как основа Operator SDK; предоставляет каркас проекта и генерацию кода
  - Java Operator SDK. Готовый фреймворк для написания операторов на Java
  - KubeOps. SDK для создания операторов на платформе .NET
  - cdk8s-operator. TypeScript, Python и др. работает на конструкциях CDK8s
- пример создания на Kubebuilder
  - установить: `Go (1.24+), kubectl, Docker, Minikube, Kubebuilder`
  - инит проекта: `kubebuilder init --domain example.com --repo github.com/yourname/namespace-labeler`
  - создать API (CRD): `kubebuilder create api --group apps --version v1 --kind NamespaceLabeler`
  - kubebuilder сгенерирует структуры для CRD и заготовку контроллера
  - в сгенерированном файле `controllers/namespacelabeler_controller.go` нужно реализовать функцию `Reconcile`. Она будет вызываться при создании или изменении ресурса `NamespaceLabeler`. Внутри функции вы описываем, какие действия должен выполнить оператор (например, добавить метки `team` и `env` к целевому namespace)
  - Сборка и развертывание:
```bash
make docker-build docker-push IMG=yourrepo/namespace-labeler:tag
make deploy IMG=yourrepo/namespace-labeler:tag
```
  - после этого оператор запустится в кластере и начнет отслеживать пользовательские ресурсы
  - создать экземпляр CR:
```yaml
apiVersion: apps.example.com/v1
kind: NamespaceLabeler
metadata:
  name: my-labeler
spec:
  labels:
    team: backend
    env: production
```
  - оператор автоматически применит эти метки ко всем новым namespace (или к указанному, в зависимости от логики).
- Для простых задач (например, автоматическое добавление меток) достаточно минимального контроллера; для сложных stateful-приложений (базы данных, очереди) оператор может управлять десятками связанных ресурсов.

# Kubernetes. Что такое pod?
- под это объект описывающий запуск одного или более контейнера на ноде
- минимальная единица планирования
- все контейнеры из одного пода находятся в одной подсети одного сетевого неймспейса и разделяют томы хранилища
- каждый под имеет свой собственный уникальный внутренний IP-адрес
- PID namespace по умолчанию отдельный, но можно включить `shareProcessNamespace: true`.
- В каждом поде есть служебный **pause-контейнер** (sandbox). Он держит network namespace, чтобы контейнеры могли перезапускаться без потери IP.

# PV, PVC, StorageClass
- PersistentVolume (PV)
  - Cluster-scoped объект, реальное хранилище (EBS, NFS, Ceph, local, CSI).
  - Не привязан к namespace.
  - Создаётся статически (админом) или динамически (провижионером StorageClass).
  - Поля: capacity, accessModes, reclaimPolicy, storageClassName, тип бэкенда.
  - Access modes: RWO (один узел), ROX (много узлов, ro), RWX (много узлов, rw), RWOP (один под).
  - Reclaim: Retain (данные остаются), Delete (удаляются), Recycle (deprecated).
  - Статусы: Available, Bound, Released, Failed.
- PersistentVolumeClaim (PVC)
  - Namespaced объект, запрос на хранилище от пода.
  - Поля: accessModes, resources.requests.storage, storageClassName, selector.
  - Под монтирует PVC, не PV.
  - Статусы: Pending, Bound, Lost.
- Binding (связывание)
  - Static: админ создаёт PV, K8s биндит подходящий PVC по capacity, accessModes, storageClassName, selector.
  - Dynamic: админ создаёт StorageClass, провижионер создаёт PV при появлении PVC.
- StorageClass
  - Cluster-scoped, описывает класс хранилища и провижионер.
  - provisioner: CSI-драйвер (ebs.csi.aws.com, efs.csi.aws.com, cephfs.csi.ceph.com).
  - parameters: тип диска, IOPS, encrypted, fsType.
  - reclaimPolicy: Delete или Retain.
  - volumeBindingMode: Immediate или WaitForFirstConsumer.
  - allowVolumeExpansion: true/false.
  - Default StorageClass через аннотацию is-default-class.
- volumeBindingMode
  - Immediate: PV создаётся сразу, в случайной AZ → в multi-AZ под может не найти ноду.
  - WaitForFirstConsumer: PV создаётся после планирования пода, в его AZ.
  - Для EBS/GCE PD/local PV — ВСЕГДА WaitForFirstConsumer.
  - Для NFS/EFS/CephFS (нет привязки к AZ) — можно Immediate.
- StatefulSet
  - volumeClaimTemplates — PVC на каждый под (data-web-0, data-web-1).
  - PVC не удаляются при удалении пода.
  - persistentVolumeClaimRetentionPolicy (1.27+) — управлять удалением.

# Kubernetes. Что такое namespace?
- изоляция для именования и RBAC, но не для сети. 
- Сетевая изоляция требует NetworkPolicy
- по умолчанию есть default (пустой) ns и kube-system c объекттами контрол плейн, kube-public для общедоступных ресурсов, kube-node-lease с информацией о нодах
- некоторые плагины например istio, создают для себя неймспейсы

# Kubernetes. В чем разница между подом и контейнером?
- под это минимальная единица планирования kubernetes
- контейнер создаётся кубелетом через CRI когда он видит соответствующее для себя задание
- в etcd нет объекта контейнер. есть информация о контейнерах внутри pod
- Container — сущность runtime (containerd/CRI-O)
- контейнеры в поде разделяют общие ресурсы. сетевой неймспейс, межпроцессная комуникация, тома, пид, сигруп

# Kubernetes. Что дает helm в кубе?
- helm это утилита-пакетный менеджер для развёртывания приложений в кластере
- также как и apt есть множество репозиториев их можно добавлять и обновлять, скачивать
- скачанный хелм чарт состоит из из шаблонов (Go templates) манифестов объектов и файла values
- одни и те же поля values могут подставляться во множество мест в шаблонах. благодаря этому конфигурировать будующие приложения проще и удобнее
- можно перопределять в комнадной строке и в файле. приоритет соответствующий.
- помимо подстановки значений helm запускает и может удалить описанные ресурсы 
- версионирует каждый запуск в "релиз" (Secret в namespace), благодаря  чему можно откатиться
- можно использовать зависимости. вложенные чарты (ссылки  на них), которые усттанавливаются перед основным

# Что такое iptables?
- классический механизм фильтрации и обработки сетевых пакетов на уровне ядра Linux (L3/L4)
- ещё широко используется, но в современных дистрибутивах заменяютт на nftables
- помимо фильтрации умеет NAT, mangle, conntrack, маркировку, redirect, forwarding
- состоит из 5 таблиц: raw, nat, filter, mangle,  security
- и 5 цепочек: PREROUTING, POSTROUTING, INPUT, OUTPUT, FORWARD
- можно создавать пользовательские цепочки
- действия в правилах: ACCEPT, DROP, REJECT, LOG, RETURN, JUMP, SNAT, DNAT, MASQUERADE, REDIRECT, MARK, NOTRACK 

---

# Чем отличается NAT/MASQUERADE/REDIRECT?
- SNAT меняет source IP на явно указанный адрес
- MASQUERADE меняет source IP на IP исходящего интерфейса (автоматически опеределяет). дороже SNAT
- DNAT меняет destination IP:port на указанный адрес
- REDIRECT меняет destination IP:port на localhost

# Kubernetes. Что такое Deployment?
- контроллер над ReplicaSet'ами умеющий rolling update, rollback, историю ревизий
- предназначен для stateless приложений (например nginx)
- новый replica set создаётся при каждом изменении spec.template deployment. по умолчанию их хранится последние 10 штук, и таким образом можно легко сделать rollback к предыдущему состоянию
- при изменении replicas - просто масштабируется
- не имеет стабильных имён подов

# Kubernetes. Как создается под? Какие компоненты задействуются при его создании?
- допустим мы сделали kubectl apply нового пода
- api получил наш запрос, проверил манифест права и разместил его в etcd
- sheduler контроллер при очередной проверке через api увидел что появился неназначенный на ноду, scheduler определил согласно правил (affinity, taints, resources) на какую ноду назначить под и оставил в манифесте соответствующую запись в spec
- kubelet при очередной проверке увидел что на его ноду есть назначенный но незапущенный под
- kubelet посредством CRI скачивает образ (ImageManager), создаёт песочницу (pause container) и настраивает сеть (CNI), затем создаёт и запускает контейнеры приложения, монтирует тома (VolumeManager) и запускает проверки (probe)
- kubelet и отправляет в api информациюю о статусе пода, которая в сао очередь записывается в etcd

# Kubernetes. Что произойдет при изменении имейджа? Как будут докатываться изменения?
- когда мы меняем image в манифесте - соответствующийй контроллер обнаруживает это изменение в etcd посредством api и запускает определённый в манифесте механизм обновлениия
- kubelet обнаруживает что на его ноду назначен новый под с новым шаблоном и что в etcd старый под помечен на удаление (и удаляет)
- container runtime (containerd/CRI-O) проверяет, каких слоёв не хватает локально, и докачивает их из registry

# Infrastructure as Code. Что это такое?
- это подход, при котором инфраструктура (сети, серверы, балансировщики, базы данных) описывается в конфигурационных файлах, а не настраивается вручную через веб-интерфейсы или скрипты. Этот код хранится в системе контроля версий (например, Git), проходит проверки и применяется автоматически.
- Ключевые преимущества:
  - Воспроизводимость: Одна и та же конфигурация каждый раз создаёт идентичную среду, что исключает ошибки, связанные с «человеческим фактором».
  - Скорость и масштабируемость: Можно быстро развернуть целую инфраструктуру или создать её копию для тестирования.
  - Управление версиями: Все изменения инфраструктуры фиксируются в Git. Это даёт возможность проводить ревью, откатываться к предыдущим версиям и видеть полную историю изменений.
  - Безопасность и соответствие: Подход «инфраструктура как код» позволяет сканировать конфигурации на наличие уязвимостей и проверять соответствие политикам безопасности до развёртывания.

# Terraform. Зачем нужен. Аналоги. Чем выделяется.
- фактически стандарт для декларативного управления инфраструктурой, особенно в мультиоблачных средах
- Основной рабочий процесс состоит из трёх этапов: Write (написание конфигурации), Plan (создание плана изменений) и Apply (применение плана).
- Файл состояния (State): Terraform хранит состояние управляемой инфраструктуры в специальном файле (terraform.tfstate). Этот файл сопоставляет ресурсы из вашей конфигурации с реальными объектами в облаке. Он критически важен для понимания того, что уже существует, и что нужно изменить.
- Провайдеры (Providers): Это плагины, которые позволяют Terraform взаимодействовать с API различных платформ: облаков (AWS, Azure, GCP), локальных систем (VMware), SaaS-сервисов (Cloudflare, GitHub) и других. Именно благодаря провайдерам Terraform обеспечивает свою мультиоблачность.
- Модули (Modules): Это переиспользуемые блоки конфигурации, которые позволяют инкапсулировать сложные архитектуры и использовать их многократно, как функции в программировании.
- аналоги:
  - OpenTofu	Декларативный (HCL)	Open-source форк Terraform. Появился после смены лицензии Terraform на BSL. Полностью совместим с HCL и провайдерами Terraform (начиная с версии 1.5.x).
  - Pulumi	Императивный (Code-first)	Позволяет описывать инфраструктуру на языках программирования общего назначения (TypeScript, Python, Go, C#). Даёт больше гибкости для сложной логики, но требует навыков программирования.
  - AWS CloudFormation	Декларативный (YAML/JSON)	Нативный инструмент AWS. Обеспечивает глубокую интеграцию с сервисами AWS, но сильно привязывает к этому облаку (vendor lock-in).
  - Ansible	Процедурный (YAML)	Инструмент управления конфигурацией, а не провижининга. Он не создаёт инфраструктуру с нуля, а настраивает уже существующие серверы (устанавливает ПО, управляет файлами). Работает без агентов.
  - Crossplane	Декларативный (Kubernetes-native)	Управляет облачными ресурсами через Kubernetes API (CRD). Позволяет использовать GitOps-подход для инфраструктуры, делая Kubernetes единой контрольной точкой.

# Kubernetes. Crossplane. Что это такое, и зачем нужно?
- инструмент превращающий Kubernetes в универсальную панель управления для любых облачных ресурсов, не только для контейнеров.
- позволяет управлять внешними ресурсами (например, базой данных AWS RDS, бакетом S3 или балансировщиком GCP) точно так же, как вы управляете подами или деплойментами внутри кластера Kubernetes — через YAML-манифесты и kubectl
- достигается за счёт расширения API Kubernetes с помощью Custom Resource Definitions (CRDs). Crossplane устанавливает свои контроллеры, которые следят за этими новыми типами ресурсов и приводят реальную инфраструктуру в соответствие с описанным в них желаемым состоянием
- так же как и terraform реализует подход infrastructure-as-a-code но не является заменой. скорее дополнением. больше подходит как инструмент для создания платформы для разработчиков
- ключевые компоненты:
  - Providers (Провайдеры): Это плагины, которые «учат» Crossplane общаться с API различных облачных платформ (AWS, GCP, Azure и др.). Провайдер устанавливает набор Managed Resources (Управляемых ресурсов) — это CRD, которые представляют собой один-к-одному реальный облачный ресурс (например, RDSInstance или S3Bucket).
  - Managed Resources (Управляемые ресурсы): Это низкоуровневое представление реального облачного ресурса в Kubernetes. Вы можете создавать их напрямую, но на практике это используется редко, так как они слишком детализированы.
  - Composite Resources (XR) и CompositeResourceDefinitions (XRD): Это сердце платформенного подхода Crossplane.
  - XRD (CompositeResourceDefinition) — это, по сути, схема вашего «золотого пути». Платформенная команда создаёт XRD, который определяет высокоуровневый API для разработчиков. Например, Database с полями size, engine, region.
  - XR (Composite Resource) — это экземпляр, созданный по этой схеме. Разработчик пишет простой манифест kind: Database, и не заботится о том, что под капотом будут созданы RDS, Security Group, Subnet Group и Secret с паролем.
  - Compositions (Композиции): Это «рецепт» или «шаблон», который объясняет Crossplane, как именно из одного высокоуровневого XR (например, Database) развернуть набор низкоуровневых Managed Resources (RDS + Security Group + Secret и т.д.). Композиции позволяют инкапсулировать всю сложность и лучшие практики безопасности.

# Какие сетевые модели существуют? Чем они отличаются?
- Мне известны модели OSI и DoD (TCP/IP)
- OSI разработана исторически раньше (скорее акадимечиская чем практическая модель) и состит из уровней:
  - 1. физический (сигнал в среде передачи)
  - 2. канальный (мак адреса, VLAN, одна сеть)
  - 3. сетевой (ip адреса, маршрутизация между сетями)
  - 4. транспортный (tcp/udp порты)
  - 5. сеансовый (RPC, sockets (частично), NetBIOS, PPTP, SIP (частично), TLS handshake (частично))
  - 6. представления (шифрование, сжатие, TLS (между 5 и 6))
  - 7. прикладной (http, ssh и другие)
- Модель TCP/IP (реальная модель, сформирована на практике, короче и лаконичнее)
  - 1. уровень доступа к сети (объединяет OSI L1 + L2)
  - 2. сетевой (ip адреса, VLAN, маршрутизация между сетями)
  - 3. транспортный (tcp/udp порты)
  - 4. прикладной (http, ssh, tls и другие)

# Что такое декларативный подход? 
- Описание желаемого состояния, а не последовательности шагов. Terraform, Kubernetes-манифесты, Ansible в declarative-режиме, Helm values
- Единый источник правды — Git. Всё, что не в Git, не существует
- Immutable infrastructure — не патчим серверы руками, а пересоздаём из кода.
- Версионирование — каждое изменение = коммит + PR + ревью.
- Идемпотентность — повторное применение даёт тот же результат

# Что такое GitOps?
- Git — единственный источник правды для состояния кластера/инфраструктуры.
- Оператор в кластере (ArgoCD, Flux) непрерывно сверяет реальное состояние с Git и приводит к нему.
- Pull-модель: оператор сам тянет изменения из Git, а не CI пушит в кластер. Это безопаснее — кластер не даёт внешний доступ.
- Drift detection: если кто-то руками поменял ресурс — оператор откатит.
- Аудит: кто, что, когда изменил — всё в истории Git.
- Rollback = git revert + оператор применит
- PR-based workflow: изменение → PR → ревью → CI-проверки (lint, plan, policy) → merge → деплой.
- Политики (Policy as Code): OPA/Gatekeeper, Kyverno, Conftest — проверяют манифесты на соответствие правилам до применения.
- Secrets management: не хранить секреты в Git. Sealed Secrets, External Secrets Operator, Vault, SOPS.
- Разделение окружений: отдельные директории/ветки/кластеры для dev/stage/prod, но один и тот же код с разными values.
- Дрифт-менеджмент: terraform plan в CI на регулярной основе, argocd app diff, алерты на drift

# Как тестировать изменения? Пирамида тестирования
- Локально / pre-commit — линтеры (tflint, hadolint, yamllint), форматтеры (terraform fmt, prettier), pre-commit hooks.
- Unit / статические проверки в CI — terraform validate, terraform plan (показать diff), helm template, kustomize build, kubeconform (валидация схем), conftest/OPA (политики).
- Секьюрити-сканы — trivy, grype (образы), checkov, tfsec, kics (IaC), gitleaks (секреты), semgrep (код).
- Интеграционные тесты — развернуть в ephemeral-окружении (namespace, kind, отдельный аккаунт), прогнать smoke-тесты, API-тесты.
- Test / Dev environment — первое реальное окружение, максимально похожее на прод.
- Stage / Pre-prod — копия прода (или максимально близко), с прод-данными (анонимизированными) или синтетикой.
- Prod — canary, blue/green, feature flags.

# Как выкатывать изменения?
- Стратегии:
  - Rolling.	постепенная замена подов/инстансов. нет простоя, дефолт в K8s	смешанные версии. откат не мгновенный
  - Blue/Green. две среды, переключение трафика. мгновенный откат, чистота. двойные ресурсы, сложнее с БД
  - Canary	небольшой % трафика на новую версию. раннее обнаружение проблем.	нужна метрика и автоматика
  - Feature flags. код задеплоен, но выключен.	деплой ≠ релиз, мгновенное выключение. сложность, технический долг
  - Shadow / dark launch.	трафик дублируется на новую версию	проверка на реальном трафике	сложно, двойная нагрузка
  - A/B. разным пользователям разные версии. продуктовые эксперименты. не для инфраструктуры

# Зачем в веб-приложении nginx в качестве фронтенда?
- nginx это зарекомендовавший себя годами, де-факто стандарт в качестве веб сервера
- написан на С, за счёт чего имеет высокую производительность и стабильность. один воркер поддерживает десятки тысяч соединенийй
- хорош в качетсве L7 reverse proxy: принимает соединение, разбирает HTTP, проксирует запрос на upstream, возвращает ответ. Клиент не знает, что за nginx стоит другой сервер
- также в качестве провайдера HTTPS
- можно с помощью него например удобно вывести в интернет поддомен (либо path). а внутри этот обратный прокси будет перенаправлять на любую внутреннюю машину, любой порт. своего рода "L7 маршрутизация/DNAT"
- имеет множество параметров, защищающих от атак. например медленных (буферизация), умеет ограничивать rate, connections, размер запроса, фильтровать по User-Agent/IP, интегрируется с fail2ban. Это снижает нагрузку от ботов и сканеров,
- ведёт подробное access логирование
- также хорош для отдачи статики
- можно использовать в качетс=стиве балансировшика
- им модно реализовать A/B-тесты, canary
- может проксировать grpc
- потребление памяти на порядок меньше Apache
- может перечитать конфигурацию без разрыва соединений
- альтернативы: envoy, HAProxy, Traefik, Caddy, Pingora

# Чем отличается GitOps от IaC?
- IaC — это широкий подход: инфраструктура описывается кодом, обычно в Git, и применяется через terraform apply, ansible-playbook или kubectl apply. 
- Это push-модель — CI или инженер запускает применение. 
- IaC не гарантирует, что реальное состояние совпадает с кодом прямо сейчас: дрейф обнаружится только при следующем plan. 
- GitOps — это частный случай IaC с конкретной операционной моделью: Git — единственный источник правды, а агент внутри кластера (ArgoCD, Flux) сам тянет изменения из Git и непрерывно сверяет реальное состояние с описанным, автоматически исправляя дрейф. 
- Это pull-модель, безопаснее для кластера, и даёт непрерывный drift detection. 
- Всякий GitOps — это IaC, но не всякий IaC — GitOps: Terraform из CI — IaC, но не GitOps. 
- Terraform можно сделать GitOps через Atlantis или Flux/Crossplane. 
- GitOps в первую очередь Kubernetes-центричен, не решает миграции БД, секреты и динамическую конфигурацию — для них нужны отдельные инструменты.

# Чем отличается CI от CD ?
- CI — Continuous Integration — это практика частых мержей в основную ветку с автоматической сборкой и тестами на каждое изменение. Цель — быстрая обратная связь и борьба с merge hell. 
- CD имеет два значения. 
- Continuous Delivery — это CI плюс автоматическая доставка артефакта в stage, но деплой в прод по кнопке, с ручным подтверждением. 
- Continuous Deployment — это когда каждое зелёное изменение автоматически едет в прод без человека. 
- Delivery — про готовность к проду с контролем, Deployment — про максимальную скорость с автоматикой. 
- Для Continuous Deployment нужны зрелые тесты, feature flags, canary, мониторинг и быстрый rollback. 
- CI/CD — это практики, а не инструменты; Jenkins или GitLab CI — лишь реализация.

# Зачем в HTTP коды ответов? Какие они бывают?
- Код ответа кратко сообщает клиенту результат выполнения его запроса
- клиент понимает, что произошло, без разбора тела ответа
- из часто встречаемых:
  - 404 страница не найдена
  - 401 клиент не аутентифицирован. не представил учётные данные (или они неверны). 
  - 403 Доступ отклонён. клиент аутентифицирован, но у него нет прав
  - 500 внутренняя ошибка сервера
  - 301-308 редиректы
- классы:
  - 1xx	Informational промежуточный ответ
  - 2xx	Success успех
  - 3xx	Redirection перенаправление
  - 4xx	Client Error ошибка клиента
  - 5xx	Server Error — ошибка сервера

# Из каких компонентов состоит Kubernetes?
- Control plane (мозг. не запускает контейнеры)
  - kube-apiserver — REST API, единая точка входа. Все компоненты общаются только через него. Authn, authz (RBAC), admission, валидация.
  - etcd — KV-хранилище, источник правды. Кластерный (Raft), 3 или 5 узлов. Только apiserver общается с etcd напрямую.
  - kube-scheduler — выбирает ноду для пода (affinity, taints, resources, topology) и делает Bind (spec.nodeName) через API.
  - kube-controller-manager — один бинарь, много контроллеров: Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, CronJob, Node, Endpoint, PV, PVC, ServiceAccount и др. Реконсилируют desired vs actual.
  - cloud-controller-manager — опционально. Интеграция с облаком: LB, маршруты, ноды.

- Node components (на каждой ноде)
  - kubelet — агент ноды. Watch'ит API на поды с его nodeName. Через CRI создаёт контейнеры, через CNI настраивает сеть, монтирует volumes, probes, репортит статус.
  - kube-proxy — реализует Service на ноде: iptables/IPVS-правила (DNAT на поды). Режимы: iptables, IPVS, userspace (legacy). Обычно DaemonSet.
  - container runtime — containerd, CRI-O. Реализует CRI. Через runc запускает контейнеры. Docker не используется с K8s 1.24.

- Addons (не часть ядра, но почти всегда есть)
  - CoreDNS — DNS для сервисов и подов (svc.ns.svc.cluster.local).
  - CNI-плагин — сеть подов. Calico, Cilium, Flannel, Weave. Модели: overlay (VXLAN), routing (BGP), eBPF (Cilium).
  - CSI-драйвер — хранилище. EBS, GCE PD, Ceph, NFS.
  - Ingress Controller — ingress-nginx, Traefik, HAProxy. L7.
  - metrics-server — для HPA и kubectl top.
  - kube-state-metrics — метрики состояния объектов.
  - cert-manager — TLS-сертификаты (оператор, не ядро).
  - Prometheus, Grafana, Loki, Dashboard.

- Service — это API-объект, не компонент
  - Service — декларация «виртуальный IP + балансировка на поды».
  - Реализуют: kube-proxy (iptables/IPVS), CNI (Cilium eBPF), Ingress/LB (для LoadBalancer).
  - Service сам трафик не распределяет.

# Как работает Taint и Toleration?
- это «не пускай сюда поды без разрешения».
- Формат: key=value:Effect
- `kubectl taint nodes node1 gpu=true:NoSchedule`
- Удалить: `kubectl taint nodes node1 gpu=true:NoSchedule-` (минус в конце!)
- Эффекты:
  - NoSchedule — не пускает новые, старые живут.
  - PreferNoSchedule — старается не пускать, но если нет альтернативы — пустит.
  - NoExecute — выселяет старые и не пускает новые.
- Toleration (на поде)
  - «Мне можно на ноде с таким taint».
  - operator: Equal (default, с value) или Exists (любой value).
  - effect: NoSchedule / PreferNoSchedule / NoExecute.
  - tolerationSeconds — для NoExecute, сколько жить до выселения.
- Toleration снимает запрет, но НЕ гарантирует размещение.
- Обычно комбинируют: taint на ноде + toleration + nodeAffinity/nodeSelector.
- Системные taint'ы
  - node.kubernetes.io/not-ready:NoExecute
  - node.kubernetes.io/unreachable:NoExecute
  - node.kubernetes.io/memory-pressure:NoSchedule
  - node.kubernetes.io/disk-pressure:NoSchedule
  - node.kubernetes.io/pid-pressure:NoSchedule
  - node.kubernetes.io/unschedulable:NoSchedule
  - У подов по умолчанию toleration на not-ready/unreachable с tolerationSeconds: 300.
- Taint vs Affinity
  - Taint — нода → под (repel). Affinity — под → нода (attract).
  - Taint + toleration — разрешить. Affinity/nodeSelector — притянуть.
  - Часто комбинируют: taint выделяет ноду, toleration разрешает, affinity притягивает.

# Job
- нужен для одноразового запуска
- restartPolicy: (Never, OnFailure)
- backoffLimit - количество попыток. по умолчанию 6
- каждая следующая попытка с большим интервалом
- ttlSecondsAfterFinished - после этого таймаута джоб (и соответственно под) будет удалён
- completions: Сколько подов должны успешно завершиться, чтобы Job считался выполненным (по умолчанию 1).
- parallelism: Максимальное количество подов, которые могут работать одновременно (по умолчанию 1).
- activeDeadlineSeconds: Жёсткий лимит времени на выполнение всего Job. Если время истекло, Job останавливается и помечается как failed. Имеет приоритет над backoffLimit

---

# CronJob
- для периодический джобов
- successfulJobsHistoryLimit
- failedJobsHistoryLimit
- concurrencyPolicy: Определяет, что делать, если предыдущий запуск ещё не завершился, а наступило время нового:
  - Allow (по умолчанию): Разрешает параллельные запуски.
  - Forbid: Запрещает параллельные запуски, новый Job пропускается, если предыдущий ещё работает.
  - Replace: Отменяет текущий Job и запускает новый.
- startingDeadlineSeconds: Крайний срок (в секундах), в течение которого CronJob должен запуститься, если по какой-то причине пропустил своё время. Если опоздание больше этого значения, запуск считается пропущенным (failed) и не выполняется.
- suspend: Флаг (boolean), который позволяет временно приостановить выполнение CronJob, не удаляя его. Уже запущенные Job продолжат работу. По умолчанию false.
- timeZone: Часовой пояс для расписания (например, Europe/Moscow). Если не указан, используется часовой пояс, в котором работает kube-controller-manager

# Affinity
- Виды:
  - nodeAffinity — притянуть под к нодам по labels/полям.
  - podAffinity — притянуть под к подам (на той же ноде/зоне/...).
  - podAntiAffinity — отталкивать под от подов (не на той же ноде/зоне/...).
- Уровни жёсткости:
  - requiredDuringSchedulingIgnoredDuringExecution — жёстко, иначе Pending.
  - preferredDuringSchedulingIgnoredDuringExecution — мягко, с weight 1-100, scheduler суммирует.
  - IgnoredDuringExecution: если labels изменились после запуска — под не выселяется.
- nodeAffinity
  - nodeSelectorTerms: matchExpressions (In, NotIn, Exists, DoesNotExist, Gt, Lt) и matchFields (metadata.name).
  - Проще: nodeSelector (map[string]string, точное совпадение) — частный случай.
- podAffinity / podAntiAffinity
  - labelSelector — какие поды искать.
  - namespaceSelector — в каких namespace (по умолчанию только свой!).
  - topologyKey — что значит «рядом»: kubernetes.io/hostname (нода), topology.kubernetes.io/zone (AZ), region, или любой label ноды.
  - Без topologyKey не работает.

# topologySpreadConstraints
-  способ управления распределением подов по доменам топологии (зонам, узлам, регионам). 
- В отличие от podAntiAffinity, который работает как жёсткий запрет ("не более одного пода в домене"), topologySpreadConstraints позволяют гибко настраивать допустимую степень неравномерности через параметр maxSkew
- maxSkew: Максимально допустимая разница в количестве подов между доменами. Обязательное поле. Например, при maxSkew: 1 и трёх зонах с 10 подами распределение может быть 4-3-3, но не 5-3-2.
- whenUnsatisfiable: Определяет поведение, если распределение не может быть соблюдено:
  - DoNotSchedule (жёсткое правило): Под останется в статусе Pending, пока не появится подходящий домен.
  - ScheduleAnyway (мягкое правило): Планировщик разместит под, даже если это нарушит maxSkew, отдав предпочтение домену с наименьшим перекосом.
- topologyKey: Ключ метки узла, который определяет домен топологии. Например, kubernetes.io/hostname (узел), topology.kubernetes.io/zone (зона доступности) или topology.kubernetes.io/region (регион).
- labelSelector: Селектор, который определяет, какие поды учитываются при подсчёте для расчёта skew.
- minDomains (опционально): Минимальное количество доменов, которое должно быть доступно для планирования. Если доступных доменов меньше, maxSkew будет считаться нарушенным.
- nodeAffinityPolicy и nodeTaintsPolicy (опционально, Beta с v1.26): Определяют, следует ли учитывать при расчёте skew узлы, которые не проходят по nodeAffinity/nodeSelector пода или имеют taints, которые под не терпит. Значение Honor (по умолчанию) означает, что такие узлы не учитываются при подсчёте, что даёт более точную картину распределения.

# Kubernetes. Что такое зона доступности?
- Изолированный ЦОД (или группа) внутри региона облака.
- Обычно 3 AZ в регионе (минимум 2, бывает 4-6).
- Между AZ — низкая задержка (<2 мс), но физическая изоляция.
- Высокая доступность: реплики распределены, потеря AZ не роняет приложение.
- SLA: 99.99% multi-AZ vs 99.9% single-AZ.
- Защита от сбоя дата-центра (пожар, питание, сеть).
- В Kubernetes
  - K8s не управляет AZ, а знает через labels на нодах.
  - Ставит cloud-controller-manager (облако) или вручную (bare-metal).
  - Labels: topology.kubernetes.io/zone, topology.kubernetes.io/region, kubernetes.io/hostname.
- Использование при планировании
  - topologySpreadConstraints + topologyKey: topology.kubernetes.io/zone — равномерное распределение с maxSkew.
  - podAntiAffinity + topologyKey: zone — «не более одного в AZ» (жёстко, блокирует scaling).
  - nodeAffinity — «только в определённых AZ».
  - volumeBindingMode: WaitForFirstConsumer для StatefulSet + PVC (EBS/GCE PD привязаны к AZ).
- При падении AZ
  - Ноды NotReady → taint unreachable:NoExecute (tolerationSeconds: 300).
  - Поды выселяются через 5 мин, контроллер создаёт новые в доступных AZ.
  - Stateful с PVC может застрять — volume привязан к зоне.
  - LB перестаёт слать трафик на упавшие ноды.

# ConfigMap
- Namespaced-объект. Хранит неконфиденциальные данные: строки, конфиги, переменные окружения, целые файлы.
- Не предназначен для секретов — они не шифруются, видны всем, у кого есть доступ к namespace.
- Ограничение размера одного ConfigMap — **1 MiB** (лимит etcd на объект).
- Может хранить несколько ключей: каждый ключ — либо строка, либо файл.
- Как использовать в поде:
  - Как переменные окружения
  - Как файл в volume (mount)
  - Как аргументы командной строки
- Обновление ConfigMap
  - Volume mount: kubelet периодически (по умолчанию ~1 мин, `--sync-frequency`) обновляет файлы в смонтированном volume. Приложение должно перечитывать файл (например, по SIGHUP или само).
  - Env vars: не обновляются в запущенном поде. Нужен рестарт пода (`kubectl rollout restart`).
  - `subPath`: если ConfigMap смонтирован через `subPath`, обновления **не приходят** вообще — известное ограничение. Лучше монтировать директорию, а не отдельный файл.
  - Immutable ConfigMap (`immutable: true`) — нельзя менять, только удалить и создать. Плюс: меньше нагрузки на apiserver, безопаснее.

# Kubernetes. Secret (API объект)
- Namespaced-объект, хранит конфиденциальные данные в виде key-value.
- Данные в `data` — **base64-encoded** (не зашифрованы!).
- Данные в `stringData` — plain text, K8s сам закодирует при сохранении (удобно для ручного создания, но не для Git).
- Лимит размера одного Secret — **1 MiB** (как у ConfigMap, лимит etcd).
- Может быть `immutable: true` — нельзя менять, только пересоздать.
- Зачем нужен (отличие от ConfigMap)
  - Семантическое разделение: Secret помечен как sensitive, ConfigMap — нет.
  - Отдельный RBAC: можно дать доступ к ConfigMap, но не к Secret.
  - **Encryption at rest** — Secret можно шифровать в etcd (ConfigMap — тоже, но обычно шифруют именно Secret).
  - Поддержка TLS-сертификатов, docker registry credentials, service account tokens — через специализированные типы.
  - Меньше риск случайно залогировать (хотя `kubectl describe` всё равно показывает ключи, а `kubectl get -o yaml` — base64).
- Типы Secret
  - **`Opaque`** — по умолчанию, произвольные key-value. Пароли, токены, ключи.
  - **`kubernetes.io/service-account-token`** — токен для ServiceAccount (устаревает с 1.24, заменяется projected tokens).
  - **`kubernetes.io/dockerconfigjson`** — credentials для Docker registry (`.dockerconfigjson`).
  - **`kubernetes.io/dockercfg`** — legacy-формат для registry.
  - **`kubernetes.io/basic-auth`** — пара `username`/`password`.
  - **`kubernetes.io/ssh-auth`** — SSH-ключ (`ssh-privatekey`).
  - **`kubernetes.io/tls`** — TLS-сертификат (`tls.crt`, `tls.key`).
  - **`bootstrap.kubernetes.io/token`** — для bootstrap-токенов нод.
  - Тип задаёт **валидацию полей** и поведение (например, `tls` требует `tls.crt` и `tls.key`).
- Secret vs Vault / External Secrets Operator
  - **External Secrets Operator** — синхронизирует секреты из Vault/AWS Secrets Manager/GCP Secret Manager в K8s Secret. Приложение работает с обычным Secret, но источник правды — внешний.
  - **Sealed Secrets** — шифрует Secret так, чтобы можно было коммитить в Git; расшифровывается только в кластере.
  - **SOPS + age/KMS** — шифрование файлов в Git, расшифровка на CI/в кластере.
  - **Правило:** для прода с аудитом и ротацией — Vault/External Secrets. Для простых случаев — K8s Secret + encryption at rest + RBAC.

# Kubernetes. Downward API
- Механизм передачи полей Pod'а и контейнера в работающий контейнер.
- Два способа: переменные окружения (`env`) и файлы в томе (`downwardAPI`).
- Не требует доступа к API-серверу или клиентской библиотеке.
- Работает только с **ограниченным набором** полей (не любое поле Pod'а доступно).
- Данные доступны только **своему** поду — нельзя через Downward API получить информацию о другом поде.
- Зачем нужен
  - Приложению нужно знать своё имя, namespace, IP, имя ноды — без обращения к API.
  - Передать лимиты и requests CPU/памяти в приложение (например, для настройки JVM heap или GOMEMLIMIT).
  - Снизить связность: код не зависит от Kubernetes API.
  - Идентификатор пода для логирования/метрик (имя пода уникально в namespace).
  - Передать аннотации/лейблы в приложение (например, версию, окружение).
- Доступные поля (Pod-level, через `fieldRef`)
  - `metadata.name` — имя пода.
  - `metadata.namespace` — namespace пода.
  - `metadata.uid` — уникальный ID пода.
  - `metadata.annotations['<KEY>']` — значение конкретной аннотации.
  - `metadata.labels['<KEY>']` — значение конкретного лейбла.
  - `spec.serviceAccountName` — имя ServiceAccount (только как env).
  - `spec.nodeName` — имя ноды, где запущен под (только как env).
  - `status.hostIP` — основной IP ноды (только как env).
  - `status.hostIPs` — dual-stack версия (только как env).
  - `status.podIP` — основной IP пода (только как env).
  - `status.podIPs` — dual-stack версия (только как env).
  - `metadata.labels` (все лейблы) и `metadata.annotations` (все аннотации) — **только как файлы** в томе, не как env.
- Доступные поля (Container-level, через resourceFieldRef)
  - limits.cpu, requests.cpu
  - limits.memory, requests.memory
  - limits.hugepages-*, requests.hugepages-*
  - limits.ephemeral-storage, requests.ephemeral-storage
  - Если лимит не задан, kubelet подставляет максимально доступное значение (node allocatable).

# Kubernetes. Projected volume
- Том, который «проецирует» несколько источников в одну директорию.
- Задаётся через `volumes[].projected.sources[]`.
- Каждый source — один из типов: `secret`, `configMap`, `downwardAPI`, `serviceAccountToken`, `clusterTrustBundle`.
- Все файлы из всех источников оказываются в **одном** `mountPath`.
- Namespaced-объект (как и обычный под), но сам том — часть Pod'а.

# Kubernetes. EmptyDir
- Тип тома, создаётся пустым при старте пода на ноде.
- Живёт ровно столько же, сколько Pod (от планирования до удаления).
- Удаляется вместе с подом — данные не переживают удаление пода.
- Не является persistent storage
- Namespaced-объект в том смысле, что под живёт в namespace, но сам EmptyDir — это часть Pod spec, не отдельный API-объект.
- Права по умолчанию — `0777` (в некоторых версиях `0770`), можно задать через `fsGroup`/`securityContext`.
- Где физически хранится
  - По умолчанию — на **диске ноды**, в `/var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/<volume-name>/`.
  - `medium: ""` (default) — диск ноды (SSD/HDD).
  - `medium: Memory` — **tmpfs** (RAM-backed), быстрее, но занимает память.
  - `sizeLimit` — ограничение размера (опционально), в байтах или с суффиксом (`1Gi`).
  - Для `medium: Memory` `sizeLimit` учитывается в **memory limit** контейнера и пода — если превысить, под может быть evicted (OOM).
- Как использовать
  - **Как scratch/cache** — временные файлы, кэш, буферы, загрузки.
  - **Обмен между контейнерами пода** — два контейнера монтируют один том, один пишет, другой читает.
  - **Логи для sidecar** — приложение пишет логи в EmptyDir, sidecar (Fluent Bit, Filebeat) читает и отправляет в Loki/Elastic.
  - **Промежуточные данные** для init-контейнеров — init скачивает артефакт в EmptyDir, основной контейнер использует.
  - **tmpfs для чувствительных данных** — `medium: Memory` для данных, которые не должны попасть на диск (ключи, токены, временные пароли).

# Kubernetes. Annotations
- Что это
  - Key-value метаданные на объекте Kubernetes (Pod, Deployment, Service, Ingress, Node, и т.д.).
  - **Не участвуют в селекторах** — нельзя выбрать объекты по аннотации через `kubectl get -l` или `selector` в Service/Deployment.
  - Хранятся в `metadata.annotations` — map[string]string.
  - Значения — **строки**, любые (JSON, YAML, base64, URL, числа как строки).
  - Лимит: **256 KiB** суммарно на объект (включая labels и annotations), ключ — до 63 символов в name + опциональный префикс DNS.
  - Кластер-scoped и namespaced объекты — у всех есть annotations.
- Зачем нужны
  - Передать инструкции **контроллерам и инструментам** (ingress, Prometheus, cert-manager, external-dns, Vault, CSI).
  - Хранить метаданные, не участвующие в выборке: контакт владельца, тикет, ссылка на runbook, дата деплоя.
  - Служебные метаданные от Kubernetes и инструментов (kubectl, ArgoCD, Helm, cloud-provider).
  - Управлять поведением плагинов без изменения их кода (декларативно, через манифест).
  - Хранить произвольные структуры (JSON) — в отличие от labels, где значения ограничены.
- Annotations vs Labels
  - **Labels** — для **идентификации и выборки**: `app=web`, `env=prod`, `version=1.2.3`. Участвуют в selectors, используются в Service, Deployment, NetworkPolicy, affinity.
  - **Annotations** — для **метаданных и инструкций**: `nginx.ingress.kubernetes.io/rewrite-target`, `prometheus.io/scrape`. **Не участвуют в selectors**.
  - Оба — key-value, но у labels **строгие ограничения** на значения (≤63 символа, `[a-z0-9A-Z-_.]`), у annotations — **свободный текст** (до 256 KiB суммарно).
  - Правило: если по полю нужно **выбирать** — label. Если **передать информацию инструменту** — annotation.
  - Частая ошибка: пытаться выбрать поды по annotation через `kubectl get -l` — не работает.

# hostPath

- Что это
  - Тип тома в `spec.volumes[]` пода, а **не** отдельный API-объект.
  - Монтирует **путь с файловой системы ноды** внутрь контейнера.
  - Pod привязан к ноде, на которой физически существует этот путь.
  - Не является persistent storage в смысле «следует за подом при переносе на другую ноду» — данные остаются на **конкретной** ноде.
  - Namespaced-объекта нет — это часть Pod spec.
  - Может использоваться как backend для PV (`spec.hostPath`)

- Привязка пода к ноде
  - Мржно с помощью **`nodeSelector`** (простой случай) или **`nodeAffinity`** (гибкий) — «хочу на ноду X, где есть этот путь».
  - Без привязки под может уехать на ноду, где пути нет → ошибка или создание пустой директории (`DirectoryOrCreate`).
  - В managed-кластерах (EKS, GKE, AKS) hostPath часто **запрещён** или ограничен admission-политиками.

- Зачем нужен (легитимные сценарии)
  - **Системные компоненты**:
    - **CNI-плагины** (Calico, Cilium, Flannel) — монтируют `/etc/cni/net.d`, `/opt/cni/bin`, `/var/run/netns` с ноды.
    - **CSI-драйверы** (node-driver) — монтируют `/dev`, `/var/lib/kubelet`, `/var/lib/iscsi` и т.д.
    - **kube-proxy** — доступ к `/run/xtables.lock`, iptables.
    - **node-exporter** — `/proc`, `/sys`, `/` (readOnly).
    - **Fluent Bit, Filebeat, Loki promtail** — `/var/log/pods`, `/var/lib/docker/containers`.
    - **NVIDIA device plugin** — `/dev/nvidia*`.
  - **Dev-среда** — быстро смонтировать локальную папку с кодом, конфиги, логи.
  - **Однонодовые кластеры** (kind, minikube, k3s) — для тестов, чтения `/var/log`, `/etc/kubernetes`.
  - **Специфичное железо** — доступ к `/dev/kvm` для virt-драйверов, `/dev/fuse` для fuse-монтирований.

- Почему небезопасно
  - **Побег из контейнера** — если смонтировать `/`, `/etc`, `/var/run/docker.sock`, `/proc`, злоумышленник получает доступ к хосту.
  - **`/var/run/docker.sock`** — полный контроль над Docker на хосте = root на ноде.
  - **`/etc`** — можно изменить `/etc/passwd`, `/etc/shadow`, kubelet-конфиг, — всё, что угодно.
  - **`/dev`** — прямой доступ к дискам, можно смонтировать/записать в `/dev/sda`.
  - **`/proc`** — утечка информации о процессах, возможность инъекции.
  - **`/var/lib/kubelet`** — доступ к credentials kubelet, можно попытаться получить API-доступ.
  - **`/root`** — SSH-ключи, токены, конфиги.
  - **`/var/lib/docker`** — прямой доступ к образам, слоям, секретам.
  - **`/sys`** — ядерные параметры, cgroups.
  - **`/run/containerd/containerd.sock`** — аналог docker.sock для containerd.
  - **CVE** — некоторые CVE (например, CVE-2021-25741 в subPath) связаны с манипуляцией путями.
  - Итог: hostPath в руках злоумышленника = **compromise ноды и всех подов на ней**.

- Как ограничивать (не запрещать)
  - **Pod Security Standards (PSS)**:
    - `baseline` — не запрещает hostPath, но ограничивает.
    - `restricted` — **запрещает** hostPath.
  - **OPA/Gatekeeper** — политика, разрешать hostPath только для определённых namespaces/путей/SA.
  - **Kyverno** — политики в YAML, разрешать по whitelist
  - **`allowedHostPaths`** в PodSecurityPolicy (legacy, удалён в K8s 1.25) — был whitelist путей.
  - **`readOnly: true`** в `volumeMounts` — обязательно, если только чтение.
  - **`allowedHostPaths`** — whitelist конкретных путей, не «всё».
  - **Привязка к ноде** через `nodeSelector`/`nodeAffinity` — сужает область.
  - **Отдельные namespaces** для системных компонентов (`kube-system`), а в прикладных — запрет.
  - **RBAC** — не давать `create pods` тем, кто не должен использовать hostPath.
  - **Admission webhooks** — свой webhook для сложных проверок.

- hostPath в dev vs prod
  - **Dev** — ок: kind, minikube, k3d, локальная разработка, монтирование кода, логов.
  - **Prod** — **только для системных компонентов** (`kube-system`, CNI, CSI, node-exporter), с `readOnly`, whitelist путей, RBAC, admission-политикой.
  - **Не для приложений** — для данных использовать PVC, для конфигов ConfigMap/Secret, для логов — stdout + сборщик.
  - **Managed-кластеры** (EKS, GKE, AKS) — часто запрещают hostPath для прикладных подов или требуют PSS restricted.

# Kyverno

- Что это
  - Kubernetes-native policy engine: политики — это CRD (ClusterPolicy или Policy), описанные на YAML.
  - Работает как динамический admission controller: получает AdmissionReview от API-сервера и применяет к запросу matching-политики.
  - Не требует изучения Rego — политики выглядят как обычные Kubernetes-манифесты.
  - Поддерживает CEL (Common Expression Language) для сложных выражений, но базовые политики пишутся паттернами.

- Зачем нужен (задачи)
  - **Guardrails для разработчиков**: запретить privileged-контейнеры, `:latest`, hostPath, отсутствие resource limits, запуск от root.
  - **Автоматическая мутация**: добавить дефолтные labels, sidecar, tolerations, `imagePullPolicy: Always`, resource limits.
  - **Генерация ресурсов**: автоматически создавать NetworkPolicy, PodDisruptionBudget, ResourceQuota, LimitRange для новых namespace.
  - **Supply chain security**: проверять подписи образов (cosign, notation) и attestations перед допуском в кластер.
  - **Очистка**: удалять старые ресурсы по TTL или расписанию (Cleanup Policy).
  - **Аудит и отчётность**: PolicyReport с нарушениями для observability и compliance.

- Режимы работы (Audit vs Enforce)
  - **Audit** (по умолчанию): нарушения **не блокируются**, записываются в `PolicyReport` / `ClusterPolicyReport`. Используется для «мягкого» включения политики, чтобы увидеть, кого она затронет.
  - **Enforce**: нарушения **блокируются** на admission. API-сервер возвращает ошибку, ресурс не создаётся.
  - Рекомендуется: сначала выкатить политику в **Audit**, посмотреть отчёты, добавить исключения (PolicyException), потом переключить в **Enforce**.
  - `validationFailureAction` задаётся на уровне правила или политики.

- Типы правил (что умеет политика)
  - **Validate**: проверить ресурс на соответствие паттерну или CEL-выражению. Пример: запретить `privileged: true`, `:latest`, отсутствие `resources.limits`.
  - **Mutate**: изменить ресурс при admission или ретроактивно (mutate-existing). Пример: добавить labels, sidecar, дефолтные limits.
  - **Generate**: создать новый ресурс на основе политики. Пример: NetworkPolicy, PDB, ResourceQuota для каждого нового namespace.
  - **VerifyImages**: проверить подпись образа и attestations (cosign, notation, Notary).
  - **Cleanup**: удалить ресурсы по TTL-лейблу (`cleanup.kyverno.io/ttl`) или по расписанию (DeletingPolicy).
  - Каждое правило содержит `match` (какие ресурсы), опционально `exclude` (кого исключить) и одно из действий: `validate`, `mutate`, `generate`, `verifyImages`, `cleanup`.

- Архитектура (контроллеры)
  - **Admission Controller**: сердце Kyverno, обрабатывает AdmissionReview, вызывает движок политик.
  - **Background Controller**: выполняет generate и mutate-existing для уже существующих ресурсов, реконсилит `UpdateRequests`.
  - **Cleanup Controller**: удаляет ресурсы по TTL или расписанию.
  - **Report Controller**: создаёт и обновляет `PolicyReport` / `ClusterPolicyReport` на основе admission и background scan.
  - **Webhook Controller**: динамически настраивает admission- и mutating-webhook'и под установленные политики, чтобы не дёргать Kyverno для ресурсов, которые ни одна политика не матчит.
  - **Cert Renewer**: обновляет TLS-сертификаты webhook'ов, хранящиеся в Secret.
  - Поддерживает HA: несколько реплик контроллеров.

- Политики: ClusterPolicy vs Policy
  - **ClusterPolicy** — cluster-scoped, действует на весь кластер.
  - **Policy** — namespaced, действует только в своём namespace.
  - В новых версиях (1.14+) появились отдельные типы политик: `ValidatingPolicy`, `MutatingPolicy`, `GeneratingPolicy`, `ImageValidatingPolicy`, `DeletingPolicy`, построенные на CEL. `ClusterPolicy` с `validate`/`mutate`/`generate`/`verifyImages` постепенно уходит в deprecated (v1.19), но пока поддерживается для обратной совместимости.

# RBAC

- Что это
  - Механизм **авторизации** (не аутентификации) в Kubernetes.
  - Определяет, какие **verbs** (get, list, create, delete...) субъект может применять к каким **resources** (pods, deployments...) в каких **apiGroups** и **namespaces**.
  - Работает **после** аутентификации: сначала K8s узнаёт, кто ты (cert, token, OIDC), потом RBAC решает, что тебе можно.
  - Default deny: **после аутентификации прав нет**, пока их явно не выдадут.
  - Встроен в API-сервер, включается флагом `--authorization-mode=RBAC` (обычно вместе с Node, Webhook).
  - Пользователи (users) **не являются объектами API** — они внешние (cert CN, OIDC subject, токен). А вот ServiceAccount — объект API.

- Authentication vs Authorization — критично
  - **Authentication** (кто ты): TLS-сертификат (CN = user), OIDC (Google, Keycloak, Dex), ServiceAccount JWT token, static token file, webhook.
  - **Authorization** (что можно): RBAC, ABAC (legacy), Node (для kubelet), Webhook (внешний сервис, например OPA), AlwaysAllow/AlwaysDeny.
  - **RBAC не аутентифицирует.** Сертификат — это аутентификация. RBAC лишь проверяет права уже аутентифицированного субъекта.
  - Ошибки: **401 Unauthorized** — не аутентифицирован; **403 Forbidden** — аутентифицирован, но прав нет (RBAC запретил).

- Основные объекты
  - **Role** — namespaced, набор правил в **одном** namespace.
  - **ClusterRole** — cluster-scoped, набор правил на **весь кластер** (или на cluster-scoped ресурсы: nodes, PV, namespaces, CRD).
  - **RoleBinding** — namespaced, связывает Role (или ClusterRole) с субъектами **в своём namespace**.
  - **ClusterRoleBinding** — cluster-scoped, связывает ClusterRole с субъектами **на весь кластер**.
  - **Ключевой паттерн:** ClusterRole + RoleBinding = «права из ClusterRole, но только в одном namespace». Это часто используется, чтобы не дублировать Role в каждом namespace.

- Subjects (кому выдаём)
  - **User** — внешний пользователь, `name: "alice"` (из cert CN, OIDC `sub`).
  - **Group** — группа, `name: "developers"` (из cert O, OIDC `groups`).
  - **ServiceAccount** — `name: "ci-bot"`, `namespace: "ci"`.
  - В `subjects` указывается `kind`, `name`, `apiGroup` (для User/Group — `rbac.authorization.k8s.io`, для SA — пусто), `namespace` (только для SA).
  - Пользователи и группы **не создаются в K8s** — они приходят извне (cert, OIDC). K8s не хранит их как объекты.
  - Группы **системные**:
    - `system:authenticated` — все аутентифицированные.
    - `system:unauthenticated` — неаутентифицированные (обычно без прав).
    - `system:masters` — встроенная группа с полным доступом (cert с `O=system:masters` = cluster-admin).
    - `system:serviceaccounts` — все SA кластера.
    - `system:serviceaccounts:<ns>` — все SA в namespace.

- Rules — из чего состоит правило
  - **`apiGroups`** — группа API: `""` (core, **не** `v1`!), `apps`, `batch`, `networking.k8s.io`, `rbac.authorization.k8s.io` и т.д.
  - **`resources`** — `pods`, `deployments`, `services`, `secrets`, `configmaps`, `nodes`, `persistentvolumes`, `customresourcedefinitions`...
  - **`verbs`** — `get`, `list`, `watch`, `create`, `update`, `patch`, `delete`, `deletecollection`.
  - **`resourceNames`** — опционально, ограничить конкретными именами (например, только `configmap/global-config`). Не работает с `list`/`watch`/`create`.
  - **`nonResourceURLs`** — для не-ресурсных эндпоинтов (`/healthz`, `/metrics`, `/logs`). Только в ClusterRole.

# ServiceAccounts
- Что это:
  - **Каждый под** получает токен SA (по умолчанию — `default` в своём namespace), если не отключено.
  - **`default` SA** по умолчанию **не имеет прав** (кроме discovery). «Хватит default» — потому что он **ничего не может**, а не потому что «достаточно прав».
  - **`automountServiceAccountToken: false`** — на Pod или SA, если под не обращается к API. Меньше поверхности атаки.
  - Для пода, который **ходит в API** — создать отдельный SA, выдать Role/ClusterRole через Binding.
  - **Projected token** (K8s 1.24+) — TTL, audience, bound to pod, ротация. Legacy Secret с токеном — устарел.
  - ServiceAccount **не аутентифицируется сертификатом** — только JWT-токеном (projected или legacy Secret).
  - Связывание с правами — **RoleBinding** (в namespace) или **ClusterRoleBinding** (на кластер). Не «только ClusterRoleBinding» — RoleBinding тоже работает, и это чаще правильнее.

- Пользователи vs ServiceAccounts
  - **Пользователь** — внешний субъект, не объект API. Аутентификация: cert (CN=user, O=group), OIDC, static token, webhook. Создать пользователя через `kubectl` **нельзя** — только выдать сертификат/настроить OIDC.
  - **ServiceAccount** — объект API в namespace. Аутентификация: JWT token. Создаётся через `kubectl create sa`.
  - **kubeconfig** для пользователя: cluster + user (cert/token) + context (namespace). Пользователь получает kubeconfig, а права — через Binding.
  - **kubeconfig для SA** — можно сгенерировать (cluster + token + context), но лучше использовать projected token или `kubectl create token`.
