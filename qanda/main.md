# Kubernetes. Что такое оператор в Kubernetes? Как их делать?
- работают как клиенты API и расширяют его возможности
- задача - автоматизация и кодификация операционных знаний о приложении: как его развертывать, обновлять, масштабировать, бекапить и восстанавливать после сбоев
- это программное расширение, которое использует Custom Resources (CR) для управления приложениями и их компонентами, следуя принципу цикла управления (control loop)
- состоит из:
  - Custom Resource Definition (CRD) расширение API Kubernetes, которое определяет новый тип ресурса (например, `SampleDB` или `PostgreSQL`). CRD описывает, какие поля и настройки могут быть у пользовательского ресурса
  - Controller: непрерывно отслеживает изменения пользовательских ресурсов и приводит реальное состояние системы к желаемому (reconciliation)
- При создании экземпляра CR (например, `SampleDB`), контроллер видит это и автоматически создает необходимые ресурсы Kubernetes (StatefulSet, PersistentVolumeClaims, Job и т.д.), а также управляет их жизненным циклом
- как создать оператор:
  - Operator SDK. на базе Kubebuilder. Go, Ansible, Helm. Самый распространенный путь для «классических» операторов на Go
  - Kubebuilder. Go. Часто используется напрямую или как основа Operator SDK; предоставляет каркас проекта и генерацию кода
  - Java Operator SDK. Готовый фреймворк для написания операторов на Java
  - KubeOps. SDK для создания операторов на платформе .NET
  - cdk8s-operator. TypeScript, Python и др. работает на конструкциях CDK8s
- пример создания на Kubebuilder
  - установить: `Go (1.24+), kubectl, Docker, Minikube, Kubebuilder`
  - инит проекта: `kubebuilder init --domain example.com --repo github.com/yourname/namespace-labeler`
  - создать API (CRD): `kubebuilder create api --group apps --version v1 --kind NamespaceLabeler`
  - kubebuilder сгенерирует структуры для CRD и заготовку контроллера
  - в сгенерированном файле `controllers/namespacelabeler_controller.go` нужно реализовать функцию `Reconcile`. Она будет вызываться при создании или изменении ресурса `NamespaceLabeler`. Внутри функции вы описываем, какие действия должен выполнить оператор (например, добавить метки `team` и `env` к целевому namespace)
  - Сборка и развертывание:
```bash
make docker-build docker-push IMG=yourrepo/namespace-labeler:tag
make deploy IMG=yourrepo/namespace-labeler:tag
```
  - после этого оператор запустится в кластере и начнет отслеживать пользовательские ресурсы
  - создать экземпляр CR:
  - оператор автоматически применит эти метки ко всем новым namespace (или к указанному, в зависимости от логики).
- Для простых задач (например, автоматическое добавление меток) достаточно минимального контроллера; для сложных stateful-приложений (базы данных, очереди) оператор может управлять десятками связанных ресурсов.

# Kubernetes. Что такое pod?
- под это объект описывающий запуск одного или более контейнера на ноде
- минимальная единица планирования
- все контейнеры из одного пода находятся в одной подсети одного сетевого неймспейса и разделяют томы хранилища
- каждый под имеет свой собственный уникальный внутренний IP-адрес
- PID namespace по умолчанию отдельный, но можно включить `shareProcessNamespace: true`.
- В каждом поде есть служебный **pause-контейнер** (sandbox). Он держит network namespace, чтобы контейнеры могли перезапускаться без потери IP.

# PV, PVC, StorageClass
- PersistentVolume (PV)
  - Cluster-scoped объект, реальное хранилище (EBS, NFS, Ceph, local, CSI).
  - Не привязан к namespace.
  - Создаётся статически (админом) или динамически (провижионером StorageClass).
  - Поля: capacity, accessModes, reclaimPolicy, storageClassName, тип бэкенда.
  - Access modes: RWO (один узел), ROX (много узлов, ro), RWX (много узлов, rw), RWOP (один под).
  - Reclaim: Retain (данные остаются), Delete (удаляются), Recycle (deprecated).
  - Статусы: Available, Bound, Released, Failed.
- PersistentVolumeClaim (PVC)
  - Namespaced объект, запрос на хранилище от пода.
  - Поля: accessModes, resources.requests.storage, storageClassName, selector.
  - Под монтирует PVC, не PV.
  - Статусы: Pending, Bound, Lost.
- Binding (связывание)
  - Static: админ создаёт PV, K8s биндит подходящий PVC по capacity, accessModes, storageClassName, selector.
  - Dynamic: админ создаёт StorageClass, провижионер создаёт PV при появлении PVC.
- StorageClass
  - Cluster-scoped, описывает класс хранилища и провижионер.
  - provisioner: CSI-драйвер (ebs.csi.aws.com, efs.csi.aws.com, cephfs.csi.ceph.com).
  - parameters: тип диска, IOPS, encrypted, fsType.
  - reclaimPolicy: Delete или Retain.
  - volumeBindingMode: Immediate или WaitForFirstConsumer.
  - allowVolumeExpansion: true/false.
  - Default StorageClass через аннотацию is-default-class.
- volumeBindingMode
  - Immediate: PV создаётся сразу, в случайной AZ → в multi-AZ под может не найти ноду.
  - WaitForFirstConsumer: PV создаётся после планирования пода, в его AZ.
  - Для EBS/GCE PD/local PV — ВСЕГДА WaitForFirstConsumer.
  - Для NFS/EFS/CephFS (нет привязки к AZ) — можно Immediate.
- StatefulSet
  - volumeClaimTemplates — PVC на каждый под (data-web-0, data-web-1).
  - PVC не удаляются при удалении пода.
  - persistentVolumeClaimRetentionPolicy (1.27+) — управлять удалением.

# iptables

- Что это:
  - классическая userspace-утилита для управления правилами **netfilter** (фреймворк в ядре Linux), которые фильтруют, транслируют и модифицируют сетевые пакеты на уровнях L3/L4. 
  - В современных дистрибутивах iptables заменяется на **nftables**, но `iptables-nft` — совместимый слой, и знание iptables всё ещё обязательно.

- Три уровня иерархии (снизу вверх)
  - **Правило (rule)** — одно условие + target (действие). Пример: «если tcp dport 22 → ACCEPT».
  - **Цепочка (chain)** — упорядоченный список правил. Пакет идёт сверху вниз, срабатывает **первое совпавшее** правило, дальше target решает судьбу.
  - **Таблица (table)** — набор цепочек, сгруппированных по функции: filter, nat, mangle, raw, security.
  - **Хук (hook)** — точка в ядре (netfilter), где пакет встречается с iptables: PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING.
  - Таблица — это «столбец» (функция), цепочка — «строка» (точка пути). На пересечении — правила.

- Пять таблиц (функции)
  - **raw** — обход conntrack (target `NOTRACK`). Работает **до** отслеживания соединений.
  - **mangle** — модификация заголовков: TTL, TOS, MARK, TCP MSS.
  - **nat** — трансляция адресов/портов: SNAT, DNAT, MASQUERADE, REDIRECT.
  - **filter** — фильтрация: ACCEPT, DROP, REJECT. **Дефолтная таблица**, если `-t` не указан.
  - **security** — маркировка для SELinux (SECMARK).

- Пять встроенных цепочек (точки пути)
  - **PREROUTING** — пакет только пришёл на интерфейс, routing decision ещё не было.
  - **INPUT** — пакет адресован локальной машине.
  - **FORWARD** — пакет транзитный (не нам, но через нас).
  - **OUTPUT** — пакет сгенерирован локально.
  - **POSTROUTING** — пакет готов уйти с интерфейса, routing decision уже было.

- Матрица: какие таблицы есть в каких цепочках
  - **PREROUTING**: raw → mangle → nat
  - **INPUT**: mangle → filter → security
  - **FORWARD**: mangle → filter → security
  - **OUTPUT**: raw → mangle → nat → filter → security
  - **POSTROUTING**: mangle → nat
  - Запомнить: `raw` — только там, где **до** conntrack (PREROUTING, OUTPUT). `nat` — только там, где меняются адреса (PREROUTING, OUTPUT, POSTROUTING). `filter` — только там, где решается судьба пакета (INPUT, FORWARD, OUTPUT). `mangle` — везде. `security` — INPUT, FORWARD, OUTPUT.

- Путь пакета — как это работает вместе
  - **Входящий пакет к локальной машине**: NIC → PREROUTING (raw→mangle→nat) → routing → INPUT (mangle→filter→security) → локальный процесс.
  - **Транзитный пакет (forwarding)**: NIC → PREROUTING (raw→mangle→nat) → routing → FORWARD (mangle→filter→security) → POSTROUTING (mangle→nat) → NIC.
  - **Локально сгенерированный пакет**: процесс → OUTPUT (raw→mangle→nat→filter→security) → POSTROUTING (mangle→nat) → NIC.
  - На каждом хуке пакет проходит таблицы в фиксированном порядке, в каждой таблице — цепочку с этим именем, в цепочке — правила сверху вниз до первого совпадения.

- Чем `raw` отличается от `INPUT` (частый вопрос)
  - **`raw` — это таблица**, **`INPUT` — это цепочка**. Это **разные измерения**, их нельзя сравнивать напрямую.
  - `raw` отвечает на вопрос «отслеживать ли соединение» (NOTRACK), работает **до** conntrack, есть только в PREROUTING и OUTPUT.
  - `INPUT` — хук для пакетов, адресованных локальной машине. В нём обрабатываются таблицы mangle, filter, security, но **не raw** (её там нет).
  - Аналогия: `raw` — «отдел ранней обработки», `INPUT` — «входная дверь». Отдел работает **до** двери, а не внутри неё.

- Targets (действия в правилах)
  - **Терминальные**: `ACCEPT` (пропустить), `DROP` (молча отбросить), `REJECT` (отбросить с ICMP/RST).
  - **Не терминальные**: `LOG` (залогировать и продолжить), `MARK` (пометить), `NOTRACK` (в raw, отключить conntrack).
  - **Переходы**: `JUMP` (`-j` в пользовательскую цепочку), `RETURN` (вернуться в предыдущую), `GOTO` (`-g` в другую встроенную).
  - **NAT**: `SNAT`, `DNAT`, `MASQUERADE`, `REDIRECT`.
  - **Политика цепочки** (`-P INPUT DROP`) — дефолтное действие, если ни одно правило не совпало. Не путать с правилом.

# Чем отличается NAT/MASQUERADE/REDIRECT?
- SNAT меняет source IP на явно указанный адрес
- MASQUERADE меняет source IP на IP исходящего интерфейса (автоматически опеределяет). дороже SNAT
- DNAT меняет destination IP:port на указанный адрес
- REDIRECT меняет destination IP:port на localhost

# Kubernetes. Что такое Deployment?
- контроллер над ReplicaSet'ами умеющий rolling update, rollback, историю ревизий
- предназначен для stateless приложений (например nginx)
- новый replica set создаётся при каждом изменении spec.template deployment. по умолчанию их хранится последние 10 штук, и таким образом можно легко сделать rollback к предыдущему состоянию
- при изменении replicas - просто масштабируется
- не имеет стабильных имён подов

# Kubernetes. Как создается под? Какие компоненты задействуются при его создании?
- допустим мы сделали kubectl apply нового пода
- api получил наш запрос, проверил манифест права и разместил его в etcd
- sheduler контроллер при очередной проверке через api увидел что появился неназначенный на ноду, scheduler определил согласно правил (affinity, taints, resources) на какую ноду назначить под и оставил в манифесте соответствующую запись в spec
- kubelet при очередной проверке увидел что на его ноду есть назначенный но незапущенный под
- kubelet посредством CRI скачивает образ (ImageManager), создаёт песочницу (pause container) и настраивает сеть (CNI), затем создаёт и запускает контейнеры приложения, монтирует тома (VolumeManager) и запускает проверки (probe)
- kubelet и отправляет в api информациюю о статусе пода, которая в сао очередь записывается в etcd

# Kubernetes. Что произойдет при изменении имейджа? Как будут докатываться изменения?
- когда мы меняем image в манифесте - соответствующийй контроллер обнаруживает это изменение в etcd посредством api и запускает определённый в манифесте механизм обновлениия
- kubelet обнаруживает что на его ноду назначен новый под с новым шаблоном и что в etcd старый под помечен на удаление (и удаляет)
- container runtime (containerd/CRI-O) проверяет, каких слоёв не хватает локально, и докачивает их из registry

# Infrastructure as Code. Что это такое?
- это подход, при котором инфраструктура (сети, серверы, балансировщики, базы данных) описывается в конфигурационных файлах, а не настраивается вручную через веб-интерфейсы или скрипты. Этот код хранится в системе контроля версий (например, Git), проходит проверки и применяется автоматически.
- Ключевые преимущества:
  - Воспроизводимость: Одна и та же конфигурация каждый раз создаёт идентичную среду, что исключает ошибки, связанные с «человеческим фактором».
  - Скорость и масштабируемость: Можно быстро развернуть целую инфраструктуру или создать её копию для тестирования.
  - Управление версиями: Все изменения инфраструктуры фиксируются в Git. Это даёт возможность проводить ревью, откатываться к предыдущим версиям и видеть полную историю изменений.
  - Безопасность и соответствие: Подход «инфраструктура как код» позволяет сканировать конфигурации на наличие уязвимостей и проверять соответствие политикам безопасности до развёртывания.

# Terraform. Зачем нужен. Аналоги. Чем выделяется.
- фактически стандарт для декларативного управления инфраструктурой, особенно в мультиоблачных средах
- Основной рабочий процесс состоит из трёх этапов: Write (написание конфигурации), Plan (создание плана изменений) и Apply (применение плана).
- Файл состояния (State): Terraform хранит состояние управляемой инфраструктуры в специальном файле (terraform.tfstate). Этот файл сопоставляет ресурсы из вашей конфигурации с реальными объектами в облаке. Он критически важен для понимания того, что уже существует, и что нужно изменить.
- Провайдеры (Providers): Это плагины, которые позволяют Terraform взаимодействовать с API различных платформ: облаков (AWS, Azure, GCP), локальных систем (VMware), SaaS-сервисов (Cloudflare, GitHub) и других. Именно благодаря провайдерам Terraform обеспечивает свою мультиоблачность.
- Модули (Modules): Это переиспользуемые блоки конфигурации, которые позволяют инкапсулировать сложные архитектуры и использовать их многократно, как функции в программировании.
- аналоги:
  - OpenTofu	Декларативный (HCL)	Open-source форк Terraform. Появился после смены лицензии Terraform на BSL. Полностью совместим с HCL и провайдерами Terraform (начиная с версии 1.5.x).
  - Pulumi	Императивный (Code-first)	Позволяет описывать инфраструктуру на языках программирования общего назначения (TypeScript, Python, Go, C#). Даёт больше гибкости для сложной логики, но требует навыков программирования.
  - AWS CloudFormation	Декларативный (YAML/JSON)	Нативный инструмент AWS. Обеспечивает глубокую интеграцию с сервисами AWS, но сильно привязывает к этому облаку (vendor lock-in).
  - Ansible	Процедурный (YAML)	Инструмент управления конфигурацией, а не провижининга. Он не создаёт инфраструктуру с нуля, а настраивает уже существующие серверы (устанавливает ПО, управляет файлами). Работает без агентов.
  - Crossplane	Декларативный (Kubernetes-native)	Управляет облачными ресурсами через Kubernetes API (CRD). Позволяет использовать GitOps-подход для инфраструктуры, делая Kubernetes единой контрольной точкой.

# Kubernetes. Crossplane: что это такое и зачем нужно

- Что это по своей природе
  - **Фреймворк для построения control plane**, а не монолитный инструмент.
  - **Не «контроллер» и не «плагин» в единственном числе**, а набор контроллеров и CRD, работающих внутри кластера Kubernetes.
  - **Не заменяет Kubernetes**, а расширяет его, превращая в универсальную панель управления для любых ресурсов (облачных, SaaS, внешних API).
  - **Не является заменой Terraform**, а дополняет его, закрывая другие задачи (непрерывное управление, self-service для разработчиков).
  - Позволяет управлять внешними ресурсами (например, AWS RDS, S3, балансировщиком GCP) точно так же, как подами или деплойментами — через YAML-манифесты и `kubectl`.
  - Достигается за счёт расширения API Kubernetes через Custom Resource Definitions (CRD): Crossplane устанавливает контроллеры, которые следят за новыми типами ресурсов и приводят реальную инфраструктуру к описанному желаемому состоянию.

- Архитектура (из чего состоит)
  - **Ядро (Core Crossplane)**: главный контроллер, устанавливается в namespace `crossplane-system`. Управляет жизненным циклом остальных компонентов и обеспечивает работу механизма **Composition** (сборки высокоуровневых абстракций из низкоуровневых ресурсов).
  - **Провайдеры (Providers)**: отдельные контроллеры-операторы, устанавливаемые как пакеты. Они «учат» Crossplane работать с API конкретного облака или сервиса (AWS, GCP, Azure, GitHub и т.д.). Именно провайдеры создают **Managed Resources** — CRD, которые один-к-одному отражают реальные облачные ресурсы (например, `RDSInstance`, `S3Bucket`).
  - **Composition Engine**: движок, который по заранее описанному «рецепту» (Composition) собирает из нескольких Managed Resources один высокоуровневый объект (XR — Composite Resource), который запрашивает разработчик.
  - **Package Manager**: менеджер пакетов, через который устанавливаются сами Провайдеры и дополнительные функции (Composition Functions).
  - **Итог по архитектуре**: можно сказать, что Crossplane — это оператор, но очень крупный и модульный. Он состоит из ядра и набора устанавливаемых провайдеров, каждый из которых является отдельным контроллером.

- Ключевые компоненты и понятия
  - **Providers (Провайдеры)**: плагины, которые «учат» Crossplane общаться с API различных облачных платформ. Устанавливают набор **Managed Resources**.
  - **Managed Resources (Управляемые ресурсы)**: низкоуровневое представление реального облачного ресурса в Kubernetes (`RDSInstance`, `S3Bucket`). Можно создавать напрямую, но на практике используется редко — слишком детализированы.
  - **Composite Resources (XR) и CompositeResourceDefinitions (XRD)**: сердце платформенного подхода Crossplane.
    - **XRD (CompositeResourceDefinition)** — схема «золотого пути». Платформенная команда создаёт XRD, который определяет высокоуровневый API для разработчиков (например, `Database` с полями `size`, `engine`, `region`).
    - **XR (Composite Resource)** — экземпляр, созданный по этой схеме. Разработчик пишет простой манифест `kind: Database` и не заботится о том, что под капотом будут созданы RDS, Security Group, Subnet Group и Secret с паролем.
  - **Compositions (Композиции)**: «рецепт» или «шаблон», который объясняет Crossplane, как именно из одного высокоуровневого XR (например, `Database`) развернуть набор низкоуровневых Managed Resources (RDS + Security Group + Secret и т.д.). Композиции инкапсулируют всю сложность и лучшие практики безопасности.

- Зачем нужен в конечном счёте (главная ценность)
  - **Создание «золотых путей» (Golden Paths) для разработчиков**. Платформенная команда один раз описывает сложную инфраструктуру (например, «база данных с нужными настройками, бэкапами и секретами») в виде высокоуровневого API (`kind: Database`). Разработчик просто пишет `kind: Database` в своём YAML, и Crossplane автоматически разворачивает под капотом все необходимые облачные ресурсы.
  - **Непрерывное согласование (Continuous Reconciliation)**. В отличие от Terraform, который работает как пакетный процесс (`plan` → `apply`), Crossplane **постоянно следит** за реальным состоянием инфраструктуры. Если кто-то вручную изменил настройки RDS в консоли AWS (возник «дрейф»), Crossplane обнаружит это и **автоматически вернёт** конфигурацию к состоянию, описанному в Git.
  - **Self-Service для команд**. Разработчики самостоятельно запрашивают инфраструктуру через привычные Kubernetes-манифесты и `kubectl`, не дожидаясь платформенной команды и не разбираясь в деталях каждого облачного провайдера.
  - **Построение Internal Developer Platform (IDP)** — Crossplane больше подходит как инструмент для создания платформы для разработчиков, чем как замена Terraform.

- Crossplane vs Terraform (ключевое различие)
  - **Terraform** — инструмент **провижининга** (batch-задача). Запускается, создаёт/изменяет ресурсы по плану и завершается. Хорош для фундаментальной инфраструктуры (VPC, кластеры), где важен этап предварительного просмотра `plan`.
  - **Crossplane** — **непрерывный control loop**. Работает как «вечный двигатель», постоянно поддерживает состояние. Лучше подходит для **управления жизненным циклом** ресурсов, которые нужны приложениям (БД, бакеты, очереди), и для построения **IDP**.
  - **На практике**: их часто **комбинируют**. Terraform создаёт базовую инфраструктуру (кластеры, сети), а Crossplane управляет прикладными ресурсами внутри неё.
  - **Ключевое отличие**: Crossplane обеспечивает непрерывное согласование (reconciliation) и автоматическое исправление дрейфа; Terraform — только при следующем `plan`/`apply`.

- Короткий ответ на собеседовании
  - «Crossplane — это не просто контроллер или плагин, а **фреймворк для построения control plane**, который устанавливается в Kubernetes. Он состоит из ядра-оператора и набора провайдеров (тоже контроллеров), которые расширяют API Kubernetes для управления внешними ресурсами. Его главная ценность в том, что он позволяет платформенной команде создать **высокоуровневый self-service API** (например, `kind: Database`) для разработчиков. Разработчик пишет простой YAML, а Crossplane через механизм Composition автоматически разворачивает и **непрерывно поддерживает** все необходимые облачные ресурсы (RDS, Security Group и т.д.), автоматически исправляя любые отклонения. В отличие от Terraform, который работает как пакетный процесс, Crossplane обеспечивает непрерывное согласование и самоисправление. Это делает его идеальным инструментом для построения внутренней платформы разработчика».

- Что запомнить железно
  - **Crossplane — это фреймворк для построения control plane**, а не один контроллер.
  - Состоит из **ядра** и **провайдеров** (каждый — контроллер).
  - **Ключевые компоненты**: Providers, Managed Resources, **XRD** (схема API), **XR** (экземпляр), **Compositions** (рецепт сборки).
  - **Главная цель** — self-service и «золотые пути» для разработчиков.
  - **Ключевое отличие от Terraform** — непрерывное согласование (reconciliation) и автоматическое исправление дрейфа.
  - **Terraform** лучше для провижининга базовой инфраструктуры, **Crossplane** — для управления прикладными ресурсами и построения платформы.
  - **Не заменяет, а дополняет** Terraform.
  - **Требует** работающего и отказоустойчивого кластера Kubernetes.

# Какие сетевые модели существуют? Чем они отличаются?
- Мне известны модели OSI и DoD (TCP/IP)
- OSI разработана исторически раньше (скорее акадимечиская чем практическая модель) и состит из уровней:
  - 1. физический (сигнал в среде передачи)
  - 2. канальный (мак адреса, VLAN, одна сеть)
  - 3. сетевой (ip адреса, маршрутизация между сетями)
  - 4. транспортный (tcp/udp порты)
  - 5. сеансовый (RPC, sockets (частично), NetBIOS, PPTP, SIP (частично), TLS handshake (частично))
  - 6. представления (шифрование, сжатие, TLS (между 5 и 6))
  - 7. прикладной (http, ssh и другие)
- Модель TCP/IP (реальная модель, сформирована на практике, короче и лаконичнее)
  - 1. уровень доступа к сети (объединяет OSI L1 + L2)
  - 2. сетевой (ip адреса, VLAN, маршрутизация между сетями)
  - 3. транспортный (tcp/udp порты)
  - 4. прикладной (http, ssh, tls и другие)

# Что такое декларативный подход? 
- Описание желаемого состояния, а не последовательности шагов. Terraform, Kubernetes-манифесты, Ansible в declarative-режиме, Helm values
- Единый источник правды — Git. Всё, что не в Git, не существует
- Immutable infrastructure — не патчим серверы руками, а пересоздаём из кода.
- Версионирование — каждое изменение = коммит + PR + ревью.
- Идемпотентность — повторное применение даёт тот же результат

# Что такое GitOps?
- Git — единственный источник правды для состояния кластера/инфраструктуры.
- Оператор в кластере (ArgoCD, Flux) непрерывно сверяет реальное состояние с Git и приводит к нему.
- Pull-модель: оператор сам тянет изменения из Git, а не CI пушит в кластер. Это безопаснее — кластер не даёт внешний доступ.
- Drift detection: если кто-то руками поменял ресурс — оператор откатит.
- Аудит: кто, что, когда изменил — всё в истории Git.
- Rollback = git revert + оператор применит
- PR-based workflow: изменение → PR → ревью → CI-проверки (lint, plan, policy) → merge → деплой.
- Политики (Policy as Code): OPA/Gatekeeper, Kyverno, Conftest — проверяют манифесты на соответствие правилам до применения.
- Secrets management: не хранить секреты в Git. Sealed Secrets, External Secrets Operator, Vault, SOPS.
- Разделение окружений: отдельные директории/ветки/кластеры для dev/stage/prod, но один и тот же код с разными values.
- Дрифт-менеджмент: terraform plan в CI на регулярной основе, argocd app diff, алерты на drift

# Как тестировать изменения? Пирамида тестирования
- Локально / pre-commit — линтеры (tflint, hadolint, yamllint), форматтеры (terraform fmt, prettier), pre-commit hooks.
- Unit / статические проверки в CI — terraform validate, terraform plan (показать diff), helm template, kustomize build, kubeconform (валидация схем), conftest/OPA (политики).
- Секьюрити-сканы — trivy, grype (образы), checkov, tfsec, kics (IaC), gitleaks (секреты), semgrep (код).
- Интеграционные тесты — развернуть в ephemeral-окружении (namespace, kind, отдельный аккаунт), прогнать smoke-тесты, API-тесты.
- Test / Dev environment — первое реальное окружение, максимально похожее на прод.
- Stage / Pre-prod — копия прода (или максимально близко), с прод-данными (анонимизированными) или синтетикой.
- Prod — canary, blue/green, feature flags.

# Как выкатывать изменения?

- Общая картина
  - Все стратегии — про **progressive delivery**: не «выкатить всё сразу», а **постепенно** снижать риск.
  - Выбор зависит от: критичности сервиса, требований к downtime, зрелости мониторинга, стоимости ресурсов, совместимости БД.
  - Любая стратегия **требует rollback plan** — как откатить, за сколько, кто решает.
  - **Feature flags** — не стратегия деплоя, а способ **отделить деплой от релиза**. Часто комбинируется с остальными.

- Rolling (Rolling Update)
  - Что: постепенная замена подов/инстансов — старые гасятся, новые поднимаются, порциями.
  - Плюсы:
    - Нет простоя (при правильных `maxSurge`/`maxUnavailable`).
    - Дефолт в Kubernetes — не надо ничего настраивать.
    - Не требует двойных ресурсов (как blue/green).
  - Минусы:
    - **Смешанные версии** в моменте — старые и новые поды работают одновременно.
    - Откат не мгновенный — это ещё один rolling update в обратную сторону.
    - Нужна обратная совместимость API/схемы БД.
  - Когда: дефолт для stateless-сервисов, когда нет жёстких требований к мгновенному откату.

- Blue/Green
  - Что: две среды (blue — текущая, green — новая), после проверки трафик переключается целиком.
  - Плюсы:
    - Мгновенный откат — переключить трафик обратно.
    - Чистота: в моменте работает только одна версия.
    - Легко тестировать green перед переключением.
  - Минусы:
    - **Двойные ресурсы** на время деплоя.
    - **Сложнее с БД** — схема должна быть совместима с обеими версиями (expand/contract).
    - Переключение трафика — отдельная инфраструктура (LB, DNS, service mesh).
  - Когда: критичные сервисы, где нужен мгновенный откат и есть ресурсы на двойную среду.

- Canary
  - Что: небольшой % трафика (1–5%) направляется на новую версию, метрики решают — увеличивать или откатывать.
  - Плюсы:
    - **Раннее обнаружение проблем** на реальном трафике, но без риска для всех.
    - Постепенное увеличение — 1% → 5% → 25% → 100%.
  - Минусы:
    - Нужна **метрика** (error rate, latency p99) и **автоматика** (Argo Rollouts, Flagger) — иначе это ручной canary, который забывают откатить.
    - Нужен трафик-менеджмент (service mesh, ingress, LB с весами).
    - Сложнее с сессиями/состоянием.
  - Когда: есть мониторинг и автоматика, сервис критичный, но не требует мгновенного отката.

- Feature flags
  - Что: код задеплоен, но функциональность **выключена** флагом; включение — отдельный шаг.
  - Плюсы:
    - **Деплой ≠ релиз** — можно деплоить хоть каждый день, включать по готовности.
    - Мгновенное выключение без отката деплоя.
    - Таргетинг по пользователям, регионам, проценту.
    - A/B-тесты на той же базе.
  - Минусы:
    - **Технический долг** — флаги надо чистить, иначе код обрастает `if (flag)`.
    - **Сложность** — нужна система флагов (LaunchDarkly, Unleash, Flagsmith) и дисциплина.
    - Не заменяет стратегию деплоя — комбинируется с rolling/canary.
  - Когда: всегда, когда есть возможность — это лучший способ отделить риск релиза от риска деплоя.

- Shadow / Dark launch
  - Что: трафик **дублируется** на новую версию, но её ответы **не возвращаются** клиенту — только сравниваются.
  - Плюсы:
    - Проверка на **реальном трафике** без риска для пользователей.
    - Сравнение ответов old vs new — ловит регрессии.
    - Хорошо для миграций, смены БД, переписывания сервиса.
  - Минусы:
    - **Сложно** — нужен прокси/дублирование (Envoy, Istio mirror, nginx mirror).
    - **Двойная нагрузка** на бэкенд и БД — может быть дорого.
    - Побочные эффекты (запись в БД, отправка писем) надо подавлять.
  - Когда: крупные миграции, переписывание критичных сервисов, когда canary недостаточно.

- A/B-тестирование
  - Что: разным пользователям — разные версии, сравнение **продуктовых** метрик (конверсия, retention).
  - Плюсы:
    - Продуктовые эксперименты, а не только технические.
    - Статистически значимые решения.
  - Минусы:
    - **Не для инфраструктуры** — это про продукт, не про деплой.
    - Нужна аналитика и статистика.
    - Требует сегментации пользователей.
  - Когда: продуктовые гипотезы, не технические изменения.

- Как это комбинируется
  - **Rolling + feature flags** — дефолт: деплоим постепенно, включаем флагом.
  - **Canary + feature flags** — для критичных сервисов с автоматическим откатом.
  - **Blue/green + feature flags** — для мгновенного отката и тестирования.
  - **Shadow → canary → rolling** — для крупных миграций: сначала проверить на дубле, потом 1%, потом всех.
  - **A/B** — поверх любой стратегии, если нужен продуктовый эксперимент.

# Зачем в веб-приложении nginx в качестве фронтенда?
- nginx это зарекомендовавший себя годами, де-факто стандарт в качестве веб сервера
- написан на С, за счёт чего имеет высокую производительность и стабильность. один воркер поддерживает десятки тысяч соединенийй
- хорош в качетсве L7 reverse proxy: принимает соединение, разбирает HTTP, проксирует запрос на upstream, возвращает ответ. Клиент не знает, что за nginx стоит другой сервер
- также в качестве провайдера HTTPS
- можно с помощью него например удобно вывести в интернет поддомен (либо path). а внутри этот обратный прокси будет перенаправлять на любую внутреннюю машину, любой порт. своего рода "L7 маршрутизация/DNAT"
- имеет множество параметров, защищающих от атак. например медленных (буферизация), умеет ограничивать rate, connections, размер запроса, фильтровать по User-Agent/IP, интегрируется с fail2ban. Это снижает нагрузку от ботов и сканеров,
- ведёт подробное access логирование
- также хорош для отдачи статики
- можно использовать в качетс=стиве балансировшика
- им модно реализовать A/B-тесты, canary
- может проксировать grpc
- потребление памяти на порядок меньше Apache
- может перечитать конфигурацию без разрыва соединений
- альтернативы: envoy, HAProxy, Traefik, Caddy, Pingora

# Чем отличается GitOps от IaC?
- IaC — это широкий подход: инфраструктура описывается кодом, обычно в Git, и применяется через terraform apply, ansible-playbook или kubectl apply. 
- Это push-модель — CI или инженер запускает применение. 
- IaC не гарантирует, что реальное состояние совпадает с кодом прямо сейчас: дрейф обнаружится только при следующем plan. 
- GitOps — это частный случай IaC с конкретной операционной моделью: Git — единственный источник правды, а агент внутри кластера (ArgoCD, Flux) сам тянет изменения из Git и непрерывно сверяет реальное состояние с описанным, автоматически исправляя дрейф. 
- Это pull-модель, безопаснее для кластера, и даёт непрерывный drift detection. 
- Всякий GitOps — это IaC, но не всякий IaC — GitOps: Terraform из CI — IaC, но не GitOps. 
- Terraform можно сделать GitOps через Atlantis или Flux/Crossplane. 
- GitOps в первую очередь Kubernetes-центричен, не решает миграции БД, секреты и динамическую конфигурацию — для них нужны отдельные инструменты.

# Чем отличается CI от CD ?
- CI — Continuous Integration — это практика частых мержей в основную ветку с автоматической сборкой и тестами на каждое изменение. Цель — быстрая обратная связь и борьба с merge hell. 
- CD имеет два значения. 
- Continuous Delivery — это CI плюс автоматическая доставка артефакта в stage, но деплой в прод по кнопке, с ручным подтверждением. 
- Continuous Deployment — это когда каждое зелёное изменение автоматически едет в прод без человека. 
- Delivery — про готовность к проду с контролем, Deployment — про максимальную скорость с автоматикой. 
- Для Continuous Deployment нужны зрелые тесты, feature flags, canary, мониторинг и быстрый rollback. 
- CI/CD — это практики, а не инструменты; Jenkins или GitLab CI — лишь реализация.

# Зачем в HTTP коды ответов? Какие они бывают?
- Код ответа кратко сообщает клиенту результат выполнения его запроса
- клиент понимает, что произошло, без разбора тела ответа
- из часто встречаемых:
  - 404 страница не найдена
  - 401 клиент не аутентифицирован. не представил учётные данные (или они неверны). 
  - 403 Доступ отклонён. клиент аутентифицирован, но у него нет прав
  - 500 внутренняя ошибка сервера
  - 301-308 редиректы
- классы:
  - 1xx	Informational промежуточный ответ
  - 2xx	Success успех
  - 3xx	Redirection перенаправление
  - 4xx	Client Error ошибка клиента
  - 5xx	Server Error — ошибка сервера

# Из каких компонентов состоит Kubernetes?
- Control plane (мозг. не запускает контейнеры)
  - kube-apiserver — REST API, единая точка входа. Все компоненты общаются только через него. Authn, authz (RBAC), admission, валидация.
  - etcd — KV-хранилище, источник правды. Кластерный (Raft), 3 или 5 узлов. Только apiserver общается с etcd напрямую.
  - kube-scheduler — выбирает ноду для пода (affinity, taints, resources, topology) и делает Bind (spec.nodeName) через API.
  - kube-controller-manager — один бинарь, много контроллеров: Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, CronJob, Node, Endpoint, PV, PVC, ServiceAccount и др. Реконсилируют desired vs actual.
  - cloud-controller-manager — опционально. Интеграция с облаком: LB, маршруты, ноды.

- Node components (на каждой ноде)
  - kubelet — агент ноды. Watch'ит API на поды с его nodeName. Через CRI создаёт контейнеры, через CNI настраивает сеть, монтирует volumes, probes, репортит статус.
  - kube-proxy — реализует Service на ноде: iptables/IPVS-правила (DNAT на поды). Режимы: iptables, IPVS, userspace (legacy). Обычно DaemonSet.
  - container runtime — containerd, CRI-O. Реализует CRI. Через runc запускает контейнеры. Docker не используется с K8s 1.24.

- Addons (не часть ядра, но почти всегда есть)
  - CoreDNS — DNS для сервисов и подов (svc.ns.svc.cluster.local).
  - CNI-плагин — сеть подов. Calico, Cilium, Flannel, Weave. Модели: overlay (VXLAN), routing (BGP), eBPF (Cilium).
  - CSI-драйвер — хранилище. EBS, GCE PD, Ceph, NFS.
  - Ingress Controller — ingress-nginx, Traefik, HAProxy. L7.
  - metrics-server — для HPA и kubectl top.
  - kube-state-metrics — метрики состояния объектов.
  - cert-manager — TLS-сертификаты (оператор, не ядро).
  - Prometheus, Grafana, Loki, Dashboard.

- Service — это API-объект, не компонент
  - Service — декларация «виртуальный IP + балансировка на поды».
  - Реализуют: kube-proxy (iptables/IPVS), CNI (Cilium eBPF), Ingress/LB (для LoadBalancer).
  - Service сам трафик не распределяет.

# Как работает Taint и Toleration?
- это «не пускай сюда поды без разрешения».
- Формат: key=value:Effect
- `kubectl taint nodes node1 gpu=true:NoSchedule`
- Удалить: `kubectl taint nodes node1 gpu=true:NoSchedule-` (минус в конце!)
- Эффекты:
  - NoSchedule — не пускает новые, старые живут.
  - PreferNoSchedule — старается не пускать, но если нет альтернативы — пустит.
  - NoExecute — выселяет старые и не пускает новые.
- Toleration (на поде)
  - «Мне можно на ноде с таким taint».
  - operator: Equal (default, с value) или Exists (любой value).
  - effect: NoSchedule / PreferNoSchedule / NoExecute.
  - tolerationSeconds — для NoExecute, сколько жить до выселения.
- Toleration снимает запрет, но НЕ гарантирует размещение.
- Обычно комбинируют: taint на ноде + toleration + nodeAffinity/nodeSelector.
- Системные taint'ы
  - node.kubernetes.io/not-ready:NoExecute
  - node.kubernetes.io/unreachable:NoExecute
  - node.kubernetes.io/memory-pressure:NoSchedule
  - node.kubernetes.io/disk-pressure:NoSchedule
  - node.kubernetes.io/pid-pressure:NoSchedule
  - node.kubernetes.io/unschedulable:NoSchedule
  - У подов по умолчанию toleration на not-ready/unreachable с tolerationSeconds: 300.
- Taint vs Affinity
  - Taint — нода → под (repel). Affinity — под → нода (attract).
  - Taint + toleration — разрешить. Affinity/nodeSelector — притянуть.
  - Часто комбинируют: taint выделяет ноду, toleration разрешает, affinity притягивает.

# Job
- нужен для одноразового запуска
- restartPolicy: (Never, OnFailure)
- backoffLimit - количество попыток. по умолчанию 6
- каждая следующая попытка с большим интервалом
- ttlSecondsAfterFinished - после этого таймаута джоб (и соответственно под) будет удалён
- completions: Сколько подов должны успешно завершиться, чтобы Job считался выполненным (по умолчанию 1).
- parallelism: Максимальное количество подов, которые могут работать одновременно (по умолчанию 1).
- activeDeadlineSeconds: Жёсткий лимит времени на выполнение всего Job. Если время истекло, Job останавливается и помечается как failed. Имеет приоритет над backoffLimit

---

# CronJob
- для периодический джобов
- successfulJobsHistoryLimit
- failedJobsHistoryLimit
- concurrencyPolicy: Определяет, что делать, если предыдущий запуск ещё не завершился, а наступило время нового:
  - Allow (по умолчанию): Разрешает параллельные запуски.
  - Forbid: Запрещает параллельные запуски, новый Job пропускается, если предыдущий ещё работает.
  - Replace: Отменяет текущий Job и запускает новый.
- startingDeadlineSeconds: Крайний срок (в секундах), в течение которого CronJob должен запуститься, если по какой-то причине пропустил своё время. Если опоздание больше этого значения, запуск считается пропущенным (failed) и не выполняется.
- suspend: Флаг (boolean), который позволяет временно приостановить выполнение CronJob, не удаляя его. Уже запущенные Job продолжат работу. По умолчанию false.
- timeZone: Часовой пояс для расписания (например, Europe/Moscow). Если не указан, используется часовой пояс, в котором работает kube-controller-manager

# Affinity

- Виды
  - nodeAffinity — притянуть под к нодам по labels/полям.
  - podAffinity — притянуть под к подам (на той же ноде/зоне/...).
  - podAntiAffinity — отталкивать под от подов (не на той же ноде/зоне/...).
  - Все три — часть `spec.affinity` пода, не отдельные API-объекты.

- Уровни жёсткости
  - requiredDuringSchedulingIgnoredDuringExecution — жёстко, иначе Pending.
  - preferredDuringSchedulingIgnoredDuringExecution — мягко, с weight 1-100, scheduler суммирует.
  - IgnoredDuringExecution: если labels изменились после запуска — под не выселяется.
  - **`weight`** — только у `preferred`, целое 1–100. Scheduler суммирует веса всех подходящих preferred-правил для каждой ноды и выбирает ноду с максимальной суммой. У `required` weight нет — либо правило выполнено, либо нет.
  - **`IgnoredDuringExecution`** — важная часть названия: affinity проверяется **только в момент планирования**. Для выселения при изменении labels нужен taint `NoExecute`, а не affinity.
  - **`requiredDuringSchedulingRequiredDuringExecution`** — обещан, но **не реализован** в K8s. Только `Ignored`.

- nodeAffinity
  - nodeSelectorTerms: matchExpressions (In, NotIn, Exists, DoesNotExist, Gt, Lt) и matchFields (metadata.name).
  - Проще: nodeSelector (map[string]string, точное совпадение) — частный случай.
  - **`matchExpressions`** — по labels ноды (`disktype`, `zone`, `gpu`).
  - **`matchFields`** — по полям объекта ноды, чаще всего `metadata.name` (имя ноды). Полезно, когда нужно «только на конкретную ноду по имени».
  - **`nodeSelectorTerms`** — OR между terms, **`matchExpressions` внутри term** — AND. То есть `(A AND B) OR (C AND D)`.
  - **Операторы**:
    - `In` — label входит в список значений.
    - `NotIn` — label не входит.
    - `Exists` — label существует (значение любое).
    - `DoesNotExist` — label отсутствует.
    - `Gt` / `Lt` — значение больше/меньше (для числовых строк).
  - **`nodeSelector` vs `nodeAffinity`**: `nodeSelector` — простой map, точное совпадение, по факту `required` с одним `In`. `nodeAffinity` — операторы, `preferred`, `matchFields`. Если нужно только «хочу на ноду с `gpu=true`» — хватит `nodeSelector`.

- podAffinity / podAntiAffinity
  - labelSelector — какие поды искать.
  - namespaceSelector — в каких namespace (по умолчанию только свой!).
  - topologyKey — что значит «рядом»: kubernetes.io/hostname (нода), topology.kubernetes.io/zone (AZ), region, или любой label ноды.
  - Без topologyKey не работает.
  - **`labelSelector`** — `matchLabels` (map) или `matchExpressions` (операторы). Ищет поды по их labels.
  - **`namespaceSelector`** — по умолчанию `podAffinity`/`antiAffinity` ищет **только в своём namespace**. Чтобы искать в других — указать `namespaceSelector: {}` (все namespace) или `namespaceSelector: {matchLabels: {env: prod}}`.
  - **`topologyKey`** — обязателен. Определяет, что считать «рядом»:
    - `kubernetes.io/hostname` — нода. «Не размещать два пода `app=web` на одной ноде».
    - `topology.kubernetes.io/zone` — зона доступности. «Разные реплики в разных AZ».
    - `topology.kubernetes.io/region` — регион.
    - Любой label ноды — `rack`, `datacenter`, `gpu-type`.
  - **`requiredDuringSchedulingIgnoredDuringExecution`** для anti-affinity — жёстко. **Проблема**: если реплик больше, чем доменов (нод/AZ), часть подов навсегда в `Pending`. Например, 4 реплики и 3 AZ с `required` anti-affinity → 4-я не запустится.
  - **`preferredDuringSchedulingIgnoredDuringExecution`** для anti-affinity — мягко: «стараться не размещать рядом, но если нет альтернативы — разместить».
  - **Производительность**: inter-pod affinity/anti-affinity — **дорогая операция** для scheduler'а. Для каждого пода-кандидата нужно проверить все поды в кластере (или в namespace). В больших кластерах (тысячи подов) замедляет планирование. Отсюда — `topologySpreadConstraints`.


- Практическое правило — что использовать

| Задача | Инструмент |
|---|---|
| «Хочу на ноду с label `gpu=true`» | `nodeSelector` |
| «Хочу на SSD, но если нет — на HDD» | `nodeAffinity.preferred` |
| «Только на ноды в зоне `eu-west-1a`» | `nodeAffinity.required` + `topologyKey` |
| «Не размещать два пода `app=web` на одной ноде» | `podAntiAffinity.required` + `topologyKey: hostname` |
| «Стараться не размещать рядом, но можно» | `podAntiAffinity.preferred` |
| «Разные реплики в разных AZ» | `topologySpreadConstraints` (лучше) или `podAntiAffinity.required` + `topologyKey: zone` |
| «Под `app=cache` должен быть на той же ноде, что `app=web`» | `podAffinity.required` + `topologyKey: hostname` |

# topologySpreadConstraints
-  способ управления распределением подов по доменам топологии (зонам, узлам, регионам). 
- В отличие от podAntiAffinity, который работает как жёсткий запрет ("не более одного пода в домене"), topologySpreadConstraints позволяют гибко настраивать допустимую степень неравномерности через параметр maxSkew
- maxSkew: Максимально допустимая разница в количестве подов между доменами. Обязательное поле. Например, при maxSkew: 1 и трёх зонах с 10 подами распределение может быть 4-3-3, но не 5-3-2.
- whenUnsatisfiable: Определяет поведение, если распределение не может быть соблюдено:
  - DoNotSchedule (жёсткое правило): Под останется в статусе Pending, пока не появится подходящий домен.
  - ScheduleAnyway (мягкое правило): Планировщик разместит под, даже если это нарушит maxSkew, отдав предпочтение домену с наименьшим перекосом.
- topologyKey: Ключ метки узла, который определяет домен топологии. Например, kubernetes.io/hostname (узел), topology.kubernetes.io/zone (зона доступности) или topology.kubernetes.io/region (регион).
- labelSelector: Селектор, который определяет, какие поды учитываются при подсчёте для расчёта skew.
- minDomains (опционально): Минимальное количество доменов, которое должно быть доступно для планирования. Если доступных доменов меньше, maxSkew будет считаться нарушенным.
- nodeAffinityPolicy и nodeTaintsPolicy (опционально, Beta с v1.26): Определяют, следует ли учитывать при расчёте skew узлы, которые не проходят по nodeAffinity/nodeSelector пода или имеют taints, которые под не терпит. Значение Honor (по умолчанию) означает, что такие узлы не учитываются при подсчёте, что даёт более точную картину распределения.

# Kubernetes. Что такое зона доступности?
- Изолированный ЦОД (или группа) внутри региона облака.
- Обычно 3 AZ в регионе (минимум 2, бывает 4-6).
- Между AZ — низкая задержка (<2 мс), но физическая изоляция.
- Высокая доступность: реплики распределены, потеря AZ не роняет приложение.
- SLA: 99.99% multi-AZ vs 99.9% single-AZ.
- Защита от сбоя дата-центра (пожар, питание, сеть).
- В Kubernetes
  - K8s не управляет AZ, а знает через labels на нодах.
  - Ставит cloud-controller-manager (облако) или вручную (bare-metal).
  - Labels: topology.kubernetes.io/zone, topology.kubernetes.io/region, kubernetes.io/hostname.
- Использование при планировании
  - topologySpreadConstraints + topologyKey: topology.kubernetes.io/zone — равномерное распределение с maxSkew.
  - podAntiAffinity + topologyKey: zone — «не более одного в AZ» (жёстко, блокирует scaling).
  - nodeAffinity — «только в определённых AZ».
  - volumeBindingMode: WaitForFirstConsumer для StatefulSet + PVC (EBS/GCE PD привязаны к AZ).
- При падении AZ
  - Ноды NotReady → taint unreachable:NoExecute (tolerationSeconds: 300).
  - Поды выселяются через 5 мин, контроллер создаёт новые в доступных AZ.
  - Stateful с PVC может застрять — volume привязан к зоне.
  - LB перестаёт слать трафик на упавшие ноды.

# ConfigMap
- Namespaced-объект. Хранит неконфиденциальные данные: строки, конфиги, переменные окружения, целые файлы.
- Не предназначен для секретов — они не шифруются, видны всем, у кого есть доступ к namespace.
- Ограничение размера одного ConfigMap — **1 MiB** (лимит etcd на объект).
- Может хранить несколько ключей: каждый ключ — либо строка, либо файл.
- Как использовать в поде:
  - Как переменные окружения
  - Как файл в volume (mount)
  - Как аргументы командной строки
- Обновление ConfigMap
  - Volume mount: kubelet периодически (по умолчанию ~1 мин, `--sync-frequency`) обновляет файлы в смонтированном volume. Приложение должно перечитывать файл (например, по SIGHUP или само).
  - Env vars: не обновляются в запущенном поде. Нужен рестарт пода (`kubectl rollout restart`).
  - `subPath`: если ConfigMap смонтирован через `subPath`, обновления **не приходят** вообще — известное ограничение. Лучше монтировать директорию, а не отдельный файл.
  - Immutable ConfigMap (`immutable: true`) — нельзя менять, только удалить и создать. Плюс: меньше нагрузки на apiserver, безопаснее.

# Kubernetes. Secret (API объект)
- Namespaced-объект, хранит конфиденциальные данные в виде key-value.
- Данные в `data` — **base64-encoded** (не зашифрованы!).
- Данные в `stringData` — plain text, K8s сам закодирует при сохранении (удобно для ручного создания, но не для Git).
- Лимит размера одного Secret — **1 MiB** (как у ConfigMap, лимит etcd).
- Может быть `immutable: true` — нельзя менять, только пересоздать.
- Зачем нужен (отличие от ConfigMap)
  - Семантическое разделение: Secret помечен как sensitive, ConfigMap — нет.
  - Отдельный RBAC: можно дать доступ к ConfigMap, но не к Secret.
  - **Encryption at rest** — Secret можно шифровать в etcd (ConfigMap — тоже, но обычно шифруют именно Secret).
  - Поддержка TLS-сертификатов, docker registry credentials, service account tokens — через специализированные типы.
  - Меньше риск случайно залогировать (хотя `kubectl describe` всё равно показывает ключи, а `kubectl get -o yaml` — base64).
- Типы Secret
  - **`Opaque`** — по умолчанию, произвольные key-value. Пароли, токены, ключи.
  - **`kubernetes.io/service-account-token`** — токен для ServiceAccount (устаревает с 1.24, заменяется projected tokens).
  - **`kubernetes.io/dockerconfigjson`** — credentials для Docker registry (`.dockerconfigjson`).
  - **`kubernetes.io/dockercfg`** — legacy-формат для registry.
  - **`kubernetes.io/basic-auth`** — пара `username`/`password`.
  - **`kubernetes.io/ssh-auth`** — SSH-ключ (`ssh-privatekey`).
  - **`kubernetes.io/tls`** — TLS-сертификат (`tls.crt`, `tls.key`).
  - **`bootstrap.kubernetes.io/token`** — для bootstrap-токенов нод.
  - Тип задаёт **валидацию полей** и поведение (например, `tls` требует `tls.crt` и `tls.key`).
- Secret vs Vault / External Secrets Operator
  - **External Secrets Operator** — синхронизирует секреты из Vault/AWS Secrets Manager/GCP Secret Manager в K8s Secret. Приложение работает с обычным Secret, но источник правды — внешний.
  - **Sealed Secrets** — шифрует Secret так, чтобы можно было коммитить в Git; расшифровывается только в кластере.
  - **SOPS + age/KMS** — шифрование файлов в Git, расшифровка на CI/в кластере.
  - **Правило:** для прода с аудитом и ротацией — Vault/External Secrets. Для простых случаев — K8s Secret + encryption at rest + RBAC.

# Kubernetes. Downward API
- Механизм передачи полей Pod'а и контейнера в работающий контейнер.
- Два способа: переменные окружения (`env`) и файлы в томе (`downwardAPI`).
- Не требует доступа к API-серверу или клиентской библиотеке.
- Работает только с **ограниченным набором** полей (не любое поле Pod'а доступно).
- Данные доступны только **своему** поду — нельзя через Downward API получить информацию о другом поде.
- Зачем нужен
  - Приложению нужно знать своё имя, namespace, IP, имя ноды — без обращения к API.
  - Передать лимиты и requests CPU/памяти в приложение (например, для настройки JVM heap или GOMEMLIMIT).
  - Снизить связность: код не зависит от Kubernetes API.
  - Идентификатор пода для логирования/метрик (имя пода уникально в namespace).
  - Передать аннотации/лейблы в приложение (например, версию, окружение).
- Доступные поля (Pod-level, через `fieldRef`)
  - `metadata.name` — имя пода.
  - `metadata.namespace` — namespace пода.
  - `metadata.uid` — уникальный ID пода.
  - `metadata.annotations['<KEY>']` — значение конкретной аннотации.
  - `metadata.labels['<KEY>']` — значение конкретного лейбла.
  - `spec.serviceAccountName` — имя ServiceAccount (только как env).
  - `spec.nodeName` — имя ноды, где запущен под (только как env).
  - `status.hostIP` — основной IP ноды (только как env).
  - `status.hostIPs` — dual-stack версия (только как env).
  - `status.podIP` — основной IP пода (только как env).
  - `status.podIPs` — dual-stack версия (только как env).
  - `metadata.labels` (все лейблы) и `metadata.annotations` (все аннотации) — **только как файлы** в томе, не как env.
- Доступные поля (Container-level, через resourceFieldRef)
  - limits.cpu, requests.cpu
  - limits.memory, requests.memory
  - limits.hugepages-*, requests.hugepages-*
  - limits.ephemeral-storage, requests.ephemeral-storage
  - Если лимит не задан, kubelet подставляет максимально доступное значение (node allocatable).

# Kubernetes. Projected volume
- Том, который «проецирует» несколько источников в одну директорию.
- Задаётся через `volumes[].projected.sources[]`.
- Каждый source — один из типов: `secret`, `configMap`, `downwardAPI`, `serviceAccountToken`, `clusterTrustBundle`.
- Все файлы из всех источников оказываются в **одном** `mountPath`.
- Namespaced-объект (как и обычный под), но сам том — часть Pod'а.

# Kubernetes. EmptyDir
- Тип тома, создаётся пустым при старте пода на ноде.
- Живёт ровно столько же, сколько Pod (от планирования до удаления).
- Удаляется вместе с подом — данные не переживают удаление пода.
- Не является persistent storage
- Namespaced-объект в том смысле, что под живёт в namespace, но сам EmptyDir — это часть Pod spec, не отдельный API-объект.
- Права по умолчанию — `0777` (в некоторых версиях `0770`), можно задать через `fsGroup`/`securityContext`.
- Где физически хранится
  - По умолчанию — на **диске ноды**, в `/var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/<volume-name>/`.
  - `medium: ""` (default) — диск ноды (SSD/HDD).
  - `medium: Memory` — **tmpfs** (RAM-backed), быстрее, но занимает память.
  - `sizeLimit` — ограничение размера (опционально), в байтах или с суффиксом (`1Gi`).
  - Для `medium: Memory` `sizeLimit` учитывается в **memory limit** контейнера и пода — если превысить, под может быть evicted (OOM).
- Как использовать
  - **Как scratch/cache** — временные файлы, кэш, буферы, загрузки.
  - **Обмен между контейнерами пода** — два контейнера монтируют один том, один пишет, другой читает.
  - **Логи для sidecar** — приложение пишет логи в EmptyDir, sidecar (Fluent Bit, Filebeat) читает и отправляет в Loki/Elastic.
  - **Промежуточные данные** для init-контейнеров — init скачивает артефакт в EmptyDir, основной контейнер использует.
  - **tmpfs для чувствительных данных** — `medium: Memory` для данных, которые не должны попасть на диск (ключи, токены, временные пароли).

# Kubernetes. Annotations
- Что это
  - Key-value метаданные на объекте Kubernetes (Pod, Deployment, Service, Ingress, Node, и т.д.).
  - **Не участвуют в селекторах** — нельзя выбрать объекты по аннотации через `kubectl get -l` или `selector` в Service/Deployment.
  - Хранятся в `metadata.annotations` — map[string]string.
  - Значения — **строки**, любые (JSON, YAML, base64, URL, числа как строки).
  - Лимит: **256 KiB** суммарно на объект (включая labels и annotations), ключ — до 63 символов в name + опциональный префикс DNS.
  - Кластер-scoped и namespaced объекты — у всех есть annotations.
- Зачем нужны
  - Передать инструкции **контроллерам и инструментам** (ingress, Prometheus, cert-manager, external-dns, Vault, CSI).
  - Хранить метаданные, не участвующие в выборке: контакт владельца, тикет, ссылка на runbook, дата деплоя.
  - Служебные метаданные от Kubernetes и инструментов (kubectl, ArgoCD, Helm, cloud-provider).
  - Управлять поведением плагинов без изменения их кода (декларативно, через манифест).
  - Хранить произвольные структуры (JSON) — в отличие от labels, где значения ограничены.
- Annotations vs Labels
  - **Labels** — для **идентификации и выборки**: `app=web`, `env=prod`, `version=1.2.3`. Участвуют в selectors, используются в Service, Deployment, NetworkPolicy, affinity.
  - **Annotations** — для **метаданных и инструкций**: `nginx.ingress.kubernetes.io/rewrite-target`, `prometheus.io/scrape`. **Не участвуют в selectors**.
  - Оба — key-value, но у labels **строгие ограничения** на значения (≤63 символа, `[a-z0-9A-Z-_.]`), у annotations — **свободный текст** (до 256 KiB суммарно).
  - Правило: если по полю нужно **выбирать** — label. Если **передать информацию инструменту** — annotation.
  - Частая ошибка: пытаться выбрать поды по annotation через `kubectl get -l` — не работает.

# hostPath

- Что это
  - Тип тома в `spec.volumes[]` пода, а **не** отдельный API-объект.
  - Монтирует **путь с файловой системы ноды** внутрь контейнера.
  - Pod привязан к ноде, на которой физически существует этот путь.
  - Не является persistent storage в смысле «следует за подом при переносе на другую ноду» — данные остаются на **конкретной** ноде.
  - Namespaced-объекта нет — это часть Pod spec.
  - Может использоваться как backend для PV (`spec.hostPath`)

- Привязка пода к ноде
  - Мржно с помощью **`nodeSelector`** (простой случай) или **`nodeAffinity`** (гибкий) — «хочу на ноду X, где есть этот путь».
  - Без привязки под может уехать на ноду, где пути нет → ошибка или создание пустой директории (`DirectoryOrCreate`).
  - В managed-кластерах (EKS, GKE, AKS) hostPath часто **запрещён** или ограничен admission-политиками.

- Зачем нужен (легитимные сценарии)
  - **Системные компоненты**:
    - **CNI-плагины** (Calico, Cilium, Flannel) — монтируют `/etc/cni/net.d`, `/opt/cni/bin`, `/var/run/netns` с ноды.
    - **CSI-драйверы** (node-driver) — монтируют `/dev`, `/var/lib/kubelet`, `/var/lib/iscsi` и т.д.
    - **kube-proxy** — доступ к `/run/xtables.lock`, iptables.
    - **node-exporter** — `/proc`, `/sys`, `/` (readOnly).
    - **Fluent Bit, Filebeat, Loki promtail** — `/var/log/pods`, `/var/lib/docker/containers`.
    - **NVIDIA device plugin** — `/dev/nvidia*`.
  - **Dev-среда** — быстро смонтировать локальную папку с кодом, конфиги, логи.
  - **Однонодовые кластеры** (kind, minikube, k3s) — для тестов, чтения `/var/log`, `/etc/kubernetes`.
  - **Специфичное железо** — доступ к `/dev/kvm` для virt-драйверов, `/dev/fuse` для fuse-монтирований.

- Почему небезопасно
  - **Побег из контейнера** — если смонтировать `/`, `/etc`, `/var/run/docker.sock`, `/proc`, злоумышленник получает доступ к хосту.
  - **`/var/run/docker.sock`** — полный контроль над Docker на хосте = root на ноде.
  - **`/etc`** — можно изменить `/etc/passwd`, `/etc/shadow`, kubelet-конфиг, — всё, что угодно.
  - **`/dev`** — прямой доступ к дискам, можно смонтировать/записать в `/dev/sda`.
  - **`/proc`** — утечка информации о процессах, возможность инъекции.
  - **`/var/lib/kubelet`** — доступ к credentials kubelet, можно попытаться получить API-доступ.
  - **`/root`** — SSH-ключи, токены, конфиги.
  - **`/var/lib/docker`** — прямой доступ к образам, слоям, секретам.
  - **`/sys`** — ядерные параметры, cgroups.
  - **`/run/containerd/containerd.sock`** — аналог docker.sock для containerd.
  - **CVE** — некоторые CVE (например, CVE-2021-25741 в subPath) связаны с манипуляцией путями.
  - Итог: hostPath в руках злоумышленника = **compromise ноды и всех подов на ней**.

- Как ограничивать (не запрещать)
  - **Pod Security Standards (PSS)**:
    - `baseline` — не запрещает hostPath, но ограничивает.
    - `restricted` — **запрещает** hostPath.
  - **OPA/Gatekeeper** — политика, разрешать hostPath только для определённых namespaces/путей/SA.
  - **Kyverno** — политики в YAML, разрешать по whitelist
  - **`allowedHostPaths`** в PodSecurityPolicy (legacy, удалён в K8s 1.25) — был whitelist путей.
  - **`readOnly: true`** в `volumeMounts` — обязательно, если только чтение.
  - **`allowedHostPaths`** — whitelist конкретных путей, не «всё».
  - **Привязка к ноде** через `nodeSelector`/`nodeAffinity` — сужает область.
  - **Отдельные namespaces** для системных компонентов (`kube-system`), а в прикладных — запрет.
  - **RBAC** — не давать `create pods` тем, кто не должен использовать hostPath.
  - **Admission webhooks** — свой webhook для сложных проверок.

- hostPath в dev vs prod
  - **Dev** — ок: kind, minikube, k3d, локальная разработка, монтирование кода, логов.
  - **Prod** — **только для системных компонентов** (`kube-system`, CNI, CSI, node-exporter), с `readOnly`, whitelist путей, RBAC, admission-политикой.
  - **Не для приложений** — для данных использовать PVC, для конфигов ConfigMap/Secret, для логов — stdout + сборщик.
  - **Managed-кластеры** (EKS, GKE, AKS) — часто запрещают hostPath для прикладных подов или требуют PSS restricted.

# Kyverno

- Что это
  - Kubernetes-native policy engine: политики — это CRD (ClusterPolicy или Policy), описанные на YAML.
  - Работает как динамический admission controller: получает AdmissionReview от API-сервера и применяет к запросу matching-политики.
  - Не требует изучения Rego — политики выглядят как обычные Kubernetes-манифесты.
  - Поддерживает CEL (Common Expression Language) для сложных выражений, но базовые политики пишутся паттернами.

- Зачем нужен (задачи)
  - **Guardrails для разработчиков**: запретить privileged-контейнеры, `:latest`, hostPath, отсутствие resource limits, запуск от root.
  - **Автоматическая мутация**: добавить дефолтные labels, sidecar, tolerations, `imagePullPolicy: Always`, resource limits.
  - **Генерация ресурсов**: автоматически создавать NetworkPolicy, PodDisruptionBudget, ResourceQuota, LimitRange для новых namespace.
  - **Supply chain security**: проверять подписи образов (cosign, notation) и attestations перед допуском в кластер.
  - **Очистка**: удалять старые ресурсы по TTL или расписанию (Cleanup Policy).
  - **Аудит и отчётность**: PolicyReport с нарушениями для observability и compliance.

- Режимы работы (Audit vs Enforce)
  - **Audit** (по умолчанию): нарушения **не блокируются**, записываются в `PolicyReport` / `ClusterPolicyReport`. Используется для «мягкого» включения политики, чтобы увидеть, кого она затронет.
  - **Enforce**: нарушения **блокируются** на admission. API-сервер возвращает ошибку, ресурс не создаётся.
  - Рекомендуется: сначала выкатить политику в **Audit**, посмотреть отчёты, добавить исключения (PolicyException), потом переключить в **Enforce**.
  - `validationFailureAction` задаётся на уровне правила или политики.

- Типы правил (что умеет политика)
  - **Validate**: проверить ресурс на соответствие паттерну или CEL-выражению. Пример: запретить `privileged: true`, `:latest`, отсутствие `resources.limits`.
  - **Mutate**: изменить ресурс при admission или ретроактивно (mutate-existing). Пример: добавить labels, sidecar, дефолтные limits.
  - **Generate**: создать новый ресурс на основе политики. Пример: NetworkPolicy, PDB, ResourceQuota для каждого нового namespace.
  - **VerifyImages**: проверить подпись образа и attestations (cosign, notation, Notary).
  - **Cleanup**: удалить ресурсы по TTL-лейблу (`cleanup.kyverno.io/ttl`) или по расписанию (DeletingPolicy).
  - Каждое правило содержит `match` (какие ресурсы), опционально `exclude` (кого исключить) и одно из действий: `validate`, `mutate`, `generate`, `verifyImages`, `cleanup`.

- Архитектура (контроллеры)
  - **Admission Controller**: сердце Kyverno, обрабатывает AdmissionReview, вызывает движок политик.
  - **Background Controller**: выполняет generate и mutate-existing для уже существующих ресурсов, реконсилит `UpdateRequests`.
  - **Cleanup Controller**: удаляет ресурсы по TTL или расписанию.
  - **Report Controller**: создаёт и обновляет `PolicyReport` / `ClusterPolicyReport` на основе admission и background scan.
  - **Webhook Controller**: динамически настраивает admission- и mutating-webhook'и под установленные политики, чтобы не дёргать Kyverno для ресурсов, которые ни одна политика не матчит.
  - **Cert Renewer**: обновляет TLS-сертификаты webhook'ов, хранящиеся в Secret.
  - Поддерживает HA: несколько реплик контроллеров.

- Политики: ClusterPolicy vs Policy
  - **ClusterPolicy** — cluster-scoped, действует на весь кластер.
  - **Policy** — namespaced, действует только в своём namespace.
  - В новых версиях (1.14+) появились отдельные типы политик: `ValidatingPolicy`, `MutatingPolicy`, `GeneratingPolicy`, `ImageValidatingPolicy`, `DeletingPolicy`, построенные на CEL. `ClusterPolicy` с `validate`/`mutate`/`generate`/`verifyImages` постепенно уходит в deprecated (v1.19), но пока поддерживается для обратной совместимости.

# RBAC

- Что это
  - Механизм **авторизации** (не аутентификации) в Kubernetes.
  - Определяет, какие **verbs** (get, list, create, delete...) субъект может применять к каким **resources** (pods, deployments...) в каких **apiGroups** и **namespaces**.
  - Работает **после** аутентификации: сначала K8s узнаёт, кто ты (cert, token, OIDC), потом RBAC решает, что тебе можно.
  - Default deny: **после аутентификации прав нет**, пока их явно не выдадут.
  - Встроен в API-сервер, включается флагом `--authorization-mode=RBAC` (обычно вместе с Node, Webhook).
  - Пользователи (users) **не являются объектами API** — они внешние (cert CN, OIDC subject, токен). А вот ServiceAccount — объект API.

- Authentication vs Authorization — критично
  - **Authentication** (кто ты): TLS-сертификат (CN = user), OIDC (Google, Keycloak, Dex), ServiceAccount JWT token, static token file, webhook.
  - **Authorization** (что можно): RBAC, ABAC (legacy), Node (для kubelet), Webhook (внешний сервис, например OPA), AlwaysAllow/AlwaysDeny.
  - **RBAC не аутентифицирует.** Сертификат — это аутентификация. RBAC лишь проверяет права уже аутентифицированного субъекта.
  - Ошибки: **401 Unauthorized** — не аутентифицирован; **403 Forbidden** — аутентифицирован, но прав нет (RBAC запретил).

- Основные объекты
  - **Role** — namespaced, набор правил в **одном** namespace.
  - **ClusterRole** — cluster-scoped, набор правил на **весь кластер** (или на cluster-scoped ресурсы: nodes, PV, namespaces, CRD).
  - **RoleBinding** — namespaced, связывает Role (или ClusterRole) с субъектами **в своём namespace**.
  - **ClusterRoleBinding** — cluster-scoped, связывает ClusterRole с субъектами **на весь кластер**.
  - **Ключевой паттерн:** ClusterRole + RoleBinding = «права из ClusterRole, но только в одном namespace». Это часто используется, чтобы не дублировать Role в каждом namespace.

- Subjects (кому выдаём)
  - **User** — внешний пользователь, `name: "alice"` (из cert CN, OIDC `sub`).
  - **Group** — группа, `name: "developers"` (из cert O, OIDC `groups`).
  - **ServiceAccount** — `name: "ci-bot"`, `namespace: "ci"`.
  - В `subjects` указывается `kind`, `name`, `apiGroup` (для User/Group — `rbac.authorization.k8s.io`, для SA — пусто), `namespace` (только для SA).
  - Пользователи и группы **не создаются в K8s** — они приходят извне (cert, OIDC). K8s не хранит их как объекты.
  - Группы **системные**:
    - `system:authenticated` — все аутентифицированные.
    - `system:unauthenticated` — неаутентифицированные (обычно без прав).
    - `system:masters` — встроенная группа с полным доступом (cert с `O=system:masters` = cluster-admin).
    - `system:serviceaccounts` — все SA кластера.
    - `system:serviceaccounts:<ns>` — все SA в namespace.

- Rules — из чего состоит правило
  - **`apiGroups`** — группа API: `""` (core, **не** `v1`!), `apps`, `batch`, `networking.k8s.io`, `rbac.authorization.k8s.io` и т.д.
  - **`resources`** — `pods`, `deployments`, `services`, `secrets`, `configmaps`, `nodes`, `persistentvolumes`, `customresourcedefinitions`...
  - **`verbs`** — `get`, `list`, `watch`, `create`, `update`, `patch`, `delete`, `deletecollection`.
  - **`resourceNames`** — опционально, ограничить конкретными именами (например, только `configmap/global-config`). Не работает с `list`/`watch`/`create`.
  - **`nonResourceURLs`** — для не-ресурсных эндпоинтов (`/healthz`, `/metrics`, `/logs`). Только в ClusterRole.

# ServiceAccounts
- Что это:
  - **Каждый под** получает токен SA (по умолчанию — `default` в своём namespace), если не отключено.
  - **`default` SA** по умолчанию **не имеет прав** (кроме discovery). «Хватит default» — потому что он **ничего не может**, а не потому что «достаточно прав».
  - **`automountServiceAccountToken: false`** — на Pod или SA, если под не обращается к API. Меньше поверхности атаки.
  - Для пода, который **ходит в API** — создать отдельный SA, выдать Role/ClusterRole через Binding.
  - **Projected token** (K8s 1.24+) — TTL, audience, bound to pod, ротация. Legacy Secret с токеном — устарел.
  - ServiceAccount **не аутентифицируется сертификатом** — только JWT-токеном (projected или legacy Secret).
  - Связывание с правами — **RoleBinding** (в namespace) или **ClusterRoleBinding** (на кластер). Не «только ClusterRoleBinding» — RoleBinding тоже работает, и это чаще правильнее.

- Пользователи vs ServiceAccounts
  - **Пользователь** — внешний субъект, не объект API. Аутентификация: cert (CN=user, O=group), OIDC, static token, webhook. Создать пользователя через `kubectl` **нельзя** — только выдать сертификат/настроить OIDC.
  - **ServiceAccount** — объект API в namespace. Аутентификация: JWT token. Создаётся через `kubectl create sa`.
  - **kubeconfig** для пользователя: cluster + user (cert/token) + context (namespace). Пользователь получает kubeconfig, а права — через Binding.
  - **kubeconfig для SA** — можно сгенерировать (cluster + token + context), но лучше использовать projected token или `kubectl create token`.

# Ingress

- Что такое Ingress (важное различие)
  - **Ingress — это API-объект** (YAML-правила): «host/path → Service». Сам по себе **ничего не делает**.
  - **Ingress Controller** — это **реальный прокси** (nginx, Traefik, HAProxy, Envoy), который читает Ingress-объекты и настраивает себя под них.
  - Без контроллера Ingress-объект — просто «мёртвый» YAML, никто его не исполняет.
  - Есть стандартный **API `networking.k8s.io/v1`** и разные контроллеры: `ingress-nginx` (community, SIG Network), NGINX Ingress Controller (F5/NGINX Inc), Traefik, HAProxy, Kong, ALB Ingress Controller, Istio Gateway, Contour, Skipper.

- Что умеет Ingress (L7)
  - **Маршрутизация по host** — `example.com` → один Service, `api.example.com` → другой.
  - **Маршрутизация по path** — `/api/*` → backend-api, `/static/*` → backend-static.
  - **Path types**: `Exact` (точное совпадение), `Prefix` (по префиксу), `ImplementationSpecific` (зависит от контроллера — например, regex в nginx через аннотации).
  - **TLS termination** — `spec.tls` + Secret с `tls.crt`/`tls.key`, HTTPS на Ingress, HTTP до пода (или re-encrypt).
  - **Rewrite URL** — через аннотации контроллера (`nginx.ingress.kubernetes.io/rewrite-target`), скрыть префикс от пода.
  - **Redirect** (HTTP → HTTPS, www → non-www), **CORS**, **rate limiting**, **auth** (basic, OAuth, JWT) — через аннотации или CRD контроллера.
  - **Default backend** — catch-all для несовпавших запросов (404 или fallback).
  - **Name-based virtual hosting** — много доменов на одном IP, через `Host`-заголовок и SNI.

- Что Ingress **не** умеет
  - **TCP/UDP** — Ingress только HTTP/HTTPS (L7). Для TCP/UDP — `Service type: LoadBalancer` или `NodePort`, или CRD контроллера (например, `TCPIngress` в Traefik, `configmap tcp-services` в ingress-nginx).
  - **L4-балансировка** — это Service.
  - **gRPC** — только через специальные аннотации контроллера (`grpc_pass` в nginx), не нативно.
  - **WebSocket** — работает через Upgrade-заголовки, но требует настройки таймаутов.
  - **mTLS** — через аннотации контроллера, не стандарт.
  - **Сложная маршрутизация** (header, method, query, weight) — частично через аннотации, но это уже не стандарт Ingress.

- Аннотации
  - Стандарт Ingress — **минимальный**. Всё остальное — через **аннотации**, специфичные для контроллера.
  - Примеры для `ingress-nginx`:
    - `nginx.ingress.kubernetes.io/rewrite-target` — переписать путь.
    - `nginx.ingress.kubernetes.io/ssl-redirect` — HTTP → HTTPS.
    - `nginx.ingress.kubernetes.io/proxy-body-size` — размер тела.
    - `nginx.ingress.kubernetes.io/limit-rps` — rate limit.
    - `nginx.ingress.kubernetes.io/auth-type`, `auth-secret` — basic auth.
    - `nginx.ingress.kubernetes.io/configuration-snippet` — вставить произвольный nginx-конфиг (мощно и опасно).
    - `cert-manager.io/cluster-issuer` — авто-выпуск TLS через cert-manager.
  - **Минус:** аннотации не переносимы между контроллерами — переезд с nginx на Traefik = переписать все аннотации.
  - **Это одна из причин, почему появился Gateway API**.

- Популярные Ingress Controllers
  - **ingress-nginx** (community, Kubernetes SIG Network) — самый распространённый, на nginx. **Важно:** проект **объявлен deprecated**, поддержка до марта 2026 — планируется миграция на Gateway API или Ingress NGINX от F5. Это стоит знать на собеседовании в 2025–2026.
  - **NGINX Ingress Controller** (F5/NGINX Inc) — коммерческая поддержка, NGINX Plus, HA, расширенные фичи. Платный.
  - **Traefik** — Go, нативный для K8s/Docker, автообнаружение, ACME «из коробки», canary через `TraefikService` (weighted), middleware CRD. Хорош для динамических окружений.
  - **HAProxy Ingress** — на HAProxy, быстрый, надёжный, меньше «фишечек», чем у nginx.
  - **Kong** — на OpenResty (nginx + Lua), богатая экосистема плагинов (auth, rate limit, logging, transformations), API Gateway-функции. Тяжелее, но мощнее.
  - **AWS Load Balancer Controller** — создаёт ALB/NLB по Ingress-объектам, нативный для AWS.
  - **Contour** — на Envoy, поддержка HTTPProxy CRD (богаче стандартного Ingress).
  - **Istio Gateway / VirtualService** — если уже есть service mesh, Ingress может быть заменён на Istio Gateway.
  - **Skipper** (Zalando) — для сложной маршрутизации.
  - **Cilium Ingress** — если Cilium как CNI, может быть Ingress-контроллером на eBPF.

- Ingress vs Gateway API (современный тренд)
  - **Ingress** — старый API, минимальный, всё через аннотации, не переносимо между контроллерами, нет TCP/UDP, нет сложной маршрутизации.
  - **Gateway API** — новый стандарт (K8s SIG Network), **роли** ( infra provider / cluster operator / app developer), **типизированные** ресурсы (`GatewayClass`, `Gateway`, `HTTPRoute`, `TCPRoute`, `GRPCRoute`, `TLSRoute`), **переносимые** между контроллерами, поддержка L4/L7, header/method/query matching, weights, traffic splitting.
  - **Gateway API — преемник Ingress**, в 2025–2026 активно мигрируют. `ingress-nginx` deprecated → миграция на Gateway API или Ingress NGINX (F5).
  - На собеседовании 2025+ стоит упомянуть, что Ingress — legacy, а Gateway API — современный стандарт.

# cert-manager

- Что это
  - Kubernetes-оператор, который превращает кластер в систему управления X.509-сертификатами. 
  - позволяет декларативно запрашивать, выпускать и автоматически продлевать TLS-сертификаты
  - Сертификат становится таким же объектом api, как Pod или Deployment: вы описываете желаемое состояние в YAML, а контроллер приводит реальность к нему в непрерывном цикле согласования (reconciliation loop).

- Три ключевых компонента (поды в namespace `cert-manager`)
  - **Controller (cert-manager-controller)** — основной мозг: следит за `Certificate`, `CertificateRequest`, `Order`, `Challenge` и управляет всем жизненным циклом выпуска и продления.
  - **Webhook (cert-manager-webhook)** — динамический admission-контроллер. Валидирует, мутирует (проставляет дефолты) и конвертирует версии API для CRD cert-manager при создании/обновлении ресурсов. Без него нельзя применить ни один `Issuer` или `Certificate`.
  - **CA Injector (cert-manager-cainjector)** — автоматически вставляет CA-бандлы в конфигурации webhook’ов и APIService’ей. Именно он создаёт самоподписанный корневой CA (`cert-manager-webhook-ca`) и подписывает TLS-сертификат для пода webhook’а, чтобы API-сервер мог с ним безопасно общаться.

- Ключевые CRD (пользовательские ресурсы)
  - **Issuer / ClusterIssuer** — конфигурация «кто и как подписывает». `Issuer` работает в пределах одного namespace; `ClusterIssuer` — на весь кластер. Они не выпускают сертификаты сами, а описывают бэкенд: ACME (Let’s Encrypt), HashiCorp Vault, приватный CA, Venafi и т.д.
  - **Certificate** — главный объект для прикладной команды. Описывает: домены (DNS names), срок жизни, окно продления (`renewBefore`), имя Secret для сохранения и ссылку на `Issuer`/`ClusterIssuer`.
  - **CertificateRequest** — автоматически создаётся контроллером на каждый выпуск или продление. Содержит CSR (запрос на подпись) и ссылку на issuer. Это «артефакт» конкретного выпуска, а не долгоживущий объект; история хранится для аудита.
  - **Order и Challenge** — специфичны для ACME. `Order` представляет запрос к ACME-серверу; `Challenge` — конкретный метод доказательства владения доменом (`HTTP-01`, `DNS-01`, `TLS-ALPN-01`).

- Пошаговый процесс выпуска (на примере ACME / Let’s Encrypt)
  - **Шаг 1. Декларация Issuer**: платформенная команда один раз создаёт `ClusterIssuer` (например, для Let’s Encrypt production или staging) с настройками solvers для HTTP-01 или DNS-01.
  - **Шаг 2. Создание Certificate**: приложение (или Helm-чарт, или платформенная абстракция) создаёт `Certificate` с нужными доменами и `secretName`.
  - **Шаг 3. CertificateRequest**: controller замечает `Certificate`, генерирует приватный ключ, формирует CSR и создаёт `CertificateRequest`.
  - **Шаг 4. Order и Challenge (только ACME)**: для ACME-issuer’а `CertificateRequest` порождает `Order`, который затем создаёт `Challenge`’и (например, DNS TXT-запись или HTTP-эндпоинт) для подтверждения владения доменом.
  - **Шаг 5. Подпись и запись в Secret**: после успешного прохождения challenge ACME-сервер возвращает подписанный сертификат. Controller сериализует цепочку, ключ и сертификат в Secret типа `kubernetes.io/tls` (ключи `tls.crt`, `tls.key`, `ca.crt`).
  - **Шаг 6. Потребление подом**: приложение монтирует этот Secret как volume или читает через env. **Никаких ручных действий** — Secret уже содержит актуальный сертификат.

- Автоматическое продление
  - Controller **непрерывно** сверяет фактическое состояние с желаемым. Если Secret удалён — перевыпуск. Если изменился `spec` (добавили SAN, сменили алгоритм) — перевыпуск. Если сертификат приближается к `renewBefore` (по умолчанию — за треть срока до истечения) — перевыпуск.
  - Это принципиальное отличие от cron-запуска `certbot`: нет расписания, есть только цикл согласования, который закрывает разрыв между объявленным и реальным состоянием.
  - Для критичных сценариев можно использовать `rotationPolicy: Always`, чтобы при каждом продлении генерировался новый приватный ключ (консервативный подход для всего, что пересекает сетевую границу).

- Основные бэкенды (Issuer)
  - **ACME** (Let’s Encrypt, ZeroSSL, Google Public CA, приватный ACME) — самый распространённый. Поддерживает HTTP-01, DNS-01 и TLS-ALPN-01.
  - **HashiCorp Vault PKI** — через AppRole или Kubernetes ServiceAccount. Удобно, когда сертификаты должны следовать той же модели управления и аудита, что и остальные секреты в Vault.
  - **Приватный CA / Self-signed** — для внутренних нужд, тестовых сред, короткоживущих промежуточных CA. Не подходит как долгоживущий корень (нет HSM, нет разделения обязанностей).
  - **Venafi, AWS Private CA, Google CAS, External Issuers** — для корпоративных PKI и облачных CA через плагинную модель.

- Где используется в экосистеме
  - **Ingress**: аннотация `cert-manager.io/cluster-issuer` запускает автоматический выпуск для хостов Ingress. Это самый частый сценарий в веб-приложениях.
  - **Service Mesh (Istio, Linkerd, Cilium)**: для mTLS и короткоживущих сертификатов рабочих нагрузок (workload identity).
  - **API Gateway** и кастомные операторы — все интегрируются через стандартный Secret с TLS.

# Service Mesh и Istio

- Что такое service mesh
  - Инфраструктурный слой для управления service-to-service коммуникацией.
  - Выносит из приложения: балансировку, mTLS, ретраи, таймауты, circuit breaking, rate limiting, метрики, трейсинг, health checks.
  - Реализуется через **sidecar-прокси** рядом с каждым подом (обычно Envoy) + **control plane**, который раздаёт конфигурацию прокси.
  - Приложение общается с localhost, прокси перехватывает трафик прозрачно (iptables, eBPF или userspace).
  - Зачем: единообразная безопасность (mTLS по умолчанию), observability без изменений кода, управление трафиком (canary, blue/green, A/B) на уровне инфраструктуры.

- Data plane vs Control plane
  - **Data plane** — сами прокси (Envoy) в подах. Они обрабатывают трафик: маршрутизация, TLS, метрики, ретраи.
  - **Control plane** — центральный компонент (istiod), который **раздаёт конфигурацию** прокси через **xDS API** (LDS, RDS, CDS, EDS, SDS). Прокси динамически подхватывают изменения, без рестарта.
  - **Почему Envoy, а не nginx**: Envoy изначально проектировался под динамическую конфигурацию через xDS, поддерживает hot reload без разрыва соединений, L7-фильтры, богатую observability. nginx исторически более статичен (reload конфига — отдельный процесс, есть нюансы с long-lived соединениями).

- Ключевые возможности
  - **mTLS** — автоматическое шифрование между подами, ротация сертификатов (через Citadel/SDS).
  - **Traffic management** — canary, blue/green, A/B, traffic mirroring (shadow), fault injection, retries, timeouts.
  - **Circuit breaking** — «предохранитель»: если сервис отвечает ошибками или таймаутами, mesh перестаёт слать ему трафик на время, чтобы не копить очередь и не ронять соседей. Быстрый fail вместо долгого ожидания.
  - **Observability** — метрики (Prometheus), трейсинг (Jaeger, Tempo), access-логи, Kiali (UI для topology).
  - **Security** — mTLS, авторизация (AuthorizationPolicy), аутентификация (RequestAuthentication), JWT.
  - **Load balancing** — round-robin, least-request, consistent hash, locality-aware (zone-aware), outlier detection.

- Популярные service mesh
  - **Istio** — самый богатый функционал, Envoy, свой control plane (istiod), CNCF. Не подходит для маленьких кластеров. Накладные расходы
  - **Linkerd** — легче Istio, свой Rust-прокси (linkerd2-proxy), проще в эксплуатации, меньше функций, CNCF.
  - **Consul Connect** (HashiCorp) — service mesh + service discovery, Envoy, интеграция с Vault.
  - **Kuma** (Kong) — на Envoy, мульти-zone, CNCF.
  - **Traefik Mesh** — проще, на Traefik.
  - **Cilium Service Mesh** — на eBPF, без sidecar (или с sidecar опционально), часть CNI Cilium.
  - **AWS App Mesh** — managed, Envoy, только AWS.
  - **Open Service Mesh (OSM)** — Microsoft, Envoy, но проект фактически передан сообществу и менее активен.
  - **Тренд**: sidecar-less (Cilium eBPF, Istio ambient mode) — меньше overhead.

- Архитектура Istio — актуальная (1.5+)
  - **istiod** — единый control plane. Внутри:
    - **Pilot** — раздаёт конфигурацию маршрутизации и балансировки через xDS.
    - **Citadel** — управление сертификатами для mTLS (выдача, ротация).
    - **Galley** — валидация и обработка конфигурации (в основном исторически, часть функций ушла в istiod).
    - **Mixer** — **удалён** с Istio 1.8, telemetry теперь в Envoy (WASM-фильтры).
  - **Istio CNI** — опциональный плагин, настраивает iptables без привилегий в поде (вместо `istio-init`).
  - **Ingress Gateway** — Envoy на входе в mesh (аналог Ingress Controller).
  - **Egress Gateway** — Envoy на выходе из mesh (контроль исходящего трафика).
  - **Sidecar (istio-proxy)** — Envoy-контейнер рядом с приложением.
  - **istio-init** — init-контейнер, который настраивает iptables для перехвата трафика (или заменяется на Istio CNI).
  - **Важно**: старые «Pilot, Citadel, Galley как отдельные поды» — **устаревшая архитектура** (до 1.5). Сейчас всё в одном `istiod`.

- Как Istio внедряется в поды (sidecar injection)
  - **Автоматическая инъекция** через mutating admission webhook: Istio смотрит на label namespace (`istio-injection=enabled`) или пода (`sidecar.istio.io/inject: "true"`).
  - В под добавляется **два контейнера**:
    - **`istio-init`** (init) — настраивает iptables, чтобы весь трафик шёл через sidecar. После этого завершается.
    - **`istio-proxy`** (sidecar) — сам Envoy, работает всё время жизни пода.
  - **Важно**: Envoy — **sidecar**, а не init. Init только подготавливает сеть.
  - Альтернатива: **Istio CNI** — настраивает iptables на уровне ноды, без `istio-init` (полезно, если запрещены privileged init-контейнеры).
  - **Ambient mode** (Istio 1.22+) — sidecar-less: ztunnel (L4) и waypoint proxy (L7) вместо sidecar в каждом поде. Меньше overhead, проще.

- Установка Istio — варианты
  - **`istioctl install`** — рекомендуемый способ. Делает **pre-check** (валидация кластера, версии K8s, конфликты), генерирует и применяет манифесты. Профили: `default`, `demo`, `minimal`, `ambient`, `empty`.
  - **`istioctl manifest generate` + `kubectl apply`** — генерирует манифесты, применяет вручную. **Pre-check нет**.
  - **Helm** — установка через чарты `istiod`, `istio-base`, `istio-ingressgateway`, `istio-egressgateway`. Гибко, но **pre-check нет**, нужно самому валидировать.
  - **Istio Operator** — CRD `IstioOperator`, контроллер в кластере, работает с повышенными правами. Удобно для GitOps, но добавляет свой контроллер. В новых версиях **deprecated** в пользу `istioctl` + Helm.
  - **Все варианты ставят компоненты в namespace `istio-system`** (по умолчанию).

- Ручная инъекция sidecar (для отладки)
  ```bash
  istioctl kube-inject -f pod.yaml -o pod-injected.yaml
  ```
  - **Важно**: не `> pod.yaml` (затрёт исходник), а `-o` или другой файл.
  - Обычно не нужно — работает автоматическая инъекция по label namespace.

- Включение инъекции на namespace
  ```bash
  kubectl label namespace default istio-injection=enabled
  ```
  - После этого все новые поды в namespace получат sidecar.
  - Существующие поды — только после пересоздания (`kubectl rollout restart`).
  - Точечно на под: аннотация `sidecar.istio.io/inject: "true"` или `"false"` (отключить).
  - В современных версиях также `istio.io/rev=<revision>` для canary-обновлений control plane.

- Управление трафиком (Istio CRD)
  - **VirtualService** — правила маршрутизации: host, path, headers, weights (canary), retries, timeouts, fault injection, mirroring.
  - **DestinationRule** — политики для destination: load balancing, connection pool, outlier detection (circuit breaking), TLS mode (ISTIO_MUTUAL), subsets.
  - **Gateway** — вход/выход трафика (L4/L6), порты, TLS, SNI.
  - **ServiceEntry** — добавить внешний сервис в mesh (например, внешний API), чтобы применять policy.
  - **Sidecar** — ограничить набор сервисов, которые видит прокси (производительность в больших кластерах).
  - **AuthorizationPolicy** — L4/L7 авторизация (кто к кому может).
  - **RequestAuthentication** — JWT-валидация.
  - **PeerAuthentication** — режим mTLS (STRICT, PERMISSIVE, DISABLE).

- Когда Istio, когда нет
  - **Istio**: много сервисов (десятки-сотни), нужен mTLS, canary, observability, есть команда, которая будет поддерживать.
  - **Linkerd**: нужен mTLS и базовые метрики, но проще и легче.
  - **Cilium Service Mesh**: уже используют Cilium как CNI, хотят sidecar-less.
  - **Без mesh**: мало сервисов, нет требований к mTLS, можно обойтись Ingress + Service + NetworkPolicy.

- Короткий ответ на собеседовании
  - Service mesh — это инфраструктурный слой, который выносит из приложений сетевые задачи: балансировку, mTLS, ретраи, circuit breaking, метрики, трейсинг. Реализуется через sidecar-прокси (обычно Envoy) в каждом поде и control plane, который раздаёт конфигурацию через xDS. Istio — самый функциональный mesh: control plane — **istiod** (внутри Pilot, Citadel, Galley — консолидированы с 1.5; Mixer удалён), data plane — Envoy как **sidecar-контейнер** `istio-proxy` (не init; init `istio-init` только настраивает iptables, или Istio CNI вместо него). Инъекция включается label namespace `istio-injection=enabled` или аннотацией пода. Traffic management — через VirtualService (маршрутизация, canary, retries) и DestinationRule (LB, outlier detection = circuit breaking, TLS). mTLS по умолчанию, сертификаты ротируются автоматически. Observability — Prometheus, Jaeger, Kiali. Установка: `istioctl install` (с pre-check, рекомендуется), Helm или `manifest generate` (без pre-check), Istio Operator (deprecated). Диагностика: `istioctl analyze`, `proxy-status`, `proxy-config`, Kiali. Overhead: +50–100 МБ RAM, +1–3 мс latency на sidecar; ambient mode (ztunnel + waypoint) уменьшает. Для маленьких кластеров mesh часто избыточен — Linkerd или Cilium Service Mesh проще.

# Kiali

- Что это
  - UI и валидатор конфигурации для Istio (и других mesh).
  - Не хранит данные сам — читает из **Prometheus** (метрики), **Jaeger/Tempo/Zipkin** (трейсы), **Grafana** (дашборды), **Kubernetes API** (объекты).
  - Показывает **топологию сервисов**: кто с кем общается, какие ошибки, latency, throughput.
  - Health сервисов: error rate, request rate, latency — на основе метрик Istio (Envoy).
  - **Валидация конфигурации**: находит ошибки в VirtualService, DestinationRule, Gateway (аналог `istioctl analyze`, но в UI).
  - Показывает mTLS-статус между сервисами, какие политики применены.
  - Может открывать дашборды **Grafana** и трейсы **Jaeger** прямо из UI (deep links).
  - Установка: `istioctl dashboard kiali` или Helm-чарт `kiali-server`.
  - Аутентификация: через токен ServiceAccount, OIDC, OpenShift, LDAP.
  - **Не заменяет** Prometheus/Grafana/Jaeger — это **агрегатор и UI поверх них**.

- Что показывает
  - **Graph** — топология: nodes (сервисы, workloads, app), edges (трафик), с метриками на рёбрах (rps, error %, latency p50/p95/p99), mTLS-иконки.
  - **Applications / Workloads / Services** — списки с health, error rate, latency, throughput.
  - **Istio Config** — список VirtualService, DestinationRule, Gateway с валидацией: зелёный/жёлтый/красный.
  - **Traffic** — детализация по конкретному сервису: входящий/исходящий трафик, кто вызывает, кого вызывает.
  - **Workloads** — поды, их health, Envoy-конфигурация, логи.
  - **Mesh** — общая картина: control plane, data plane, mTLS.
  - **Validations** — все ошибки конфигурации в одном месте.
  - **Deep links** — в Grafana (дашборды), Jaeger (трейсы), Prometheus (метрики).

- Архитектура
  - **Kiali server** — Go-приложение, читает из Prometheus, Kubernetes API, Jaeger, Grafana.
  - **Kiali UI** — React SPA, общается с Kiali server.
  - **Auth** — token, OIDC, openshift, anonymous (для dev).
  - **Storage** — своего нет, всё из внешних источников.
  - **Требует** Prometheus с метриками Istio (Envoy → Prometheus).
  - **Требует** Jaeger/Tempo для трейсов (опционально — без них нет трейсов, но топология работает).

- Как Kiali и Jaeger работают вместе
  - **Kiali** читает метрики из **Prometheus** → строит топологию, health, error rate, latency.
  - **Kiali** читает трейсы из **Jaeger** → при клике на ребро/сервис открывает трейсы, связанные с этим трафиком.
  - **Jaeger** хранит спаны → UI показывает дерево запроса.
  - **Grafana** — дашборды (метрики), Kiali даёт deep link.
  - Цепочка: **Envoy → Prometheus (метрики) + Jaeger (спаны) → Kiali (UI) + Grafana (дашборды)**.
  - **Без Jaeger** Kiali работает (топология, health, config validation), но нет трейсов.
  - **Без Prometheus** Kiali не работает — метрики основа.

# Jaeger
- Что это:
  - **Распределённый трейсинг** (distributed tracing): показывает путь одного запроса через цепочку сервисов.
  - CNCF graduated (изначально Uber, 2017).
  - Реализация идей **Dapper** (Google) и **OpenTracing**.
  - **С 2023** — Jaeger объединён с OpenTelemetry: Jaeger больше не развивает свои клиенты (jaeger-client), использует **OTel SDK** для инструментации. Jaeger остаётся **backend** и **UI** для трейсов.
  - Собирает спаны от инструментированных приложений и от Envoy (Istio).

- Ключевые понятия:
  - **Span** — единица операции: один вызов, одна функция, один HTTP-запрос. Содержит: `trace_id`, `span_id`, `parent_span_id`, имя, start time, duration, tags (key-value), logs (events), status.
  - **Trace** — коллекция спанов одного запроса, связанных через `parent_span_id`. Образует **дерево** (или DAG) — от корневого спана до листьев.
  - **Context propagation** — передача `trace_id`/`span_id` между сервисами через заголовки: **W3C Trace Context** (`traceparent`, `tracestate`) — современный стандарт; **B3** (Zipkin) — старый, но всё ещё распространён; **Jaeger** (`uber-trace-id`) — legacy.
  - **Sampling** — не все трейсы сохраняются (иначе объём взорвётся). Стратегии: probabilistic (1%), rate-limiting, adaptive (Jaeger adaptive sampling), tail-based (по результату — сохранить только ошибки/медленные).
  - **Tags** — метаданные спана: `http.method`, `http.status_code`, `db.statement`, `peer.service`.
  - **Logs** — события внутри спана (например, exception).

- Архитектура (актуальная)
  - **Jaeger Collector** — принимает спаны (по OTLP, Jaeger thrift, Zipkin), валидирует, пишет в storage.
  - **Jaeger Query** — API и UI для чтения трейсов из storage.
  - **Jaeger UI** — веб-интерфейс: поиск по trace_id, сервису, операции, тегам, длительности; просмотр дерева спанов, таймингов, tags, logs.
  - **Storage** — **Elasticsearch/OpenSearch** (production), **Cassandra** (production), **Badger** (local/dev), **встроенная память** (только для тестов). **Не** хранит данные в самом Jaeger.
  - **Agent** — **deprecated** с Jaeger 1.46+, удалён в 2.x; приложения шлют спаны напрямую в collector по OTLP.
  - **Jaeger v2** (2024+) — построен на OpenTelemetry Collector: единый бинарь collector + query + UI, конфигурация через OTel Collector config.
  - **Ingester** (Kafka-based) — для масштабирования, читает спаны из Kafka, пишет в storage.

- Как работает с Istio
  - Envoy sidecar **инструментирован** для трейсинга: генерирует спаны на каждый HTTP/gRPC-запрос, передаёт контекст через заголовки.
  - Istio настраивается на отправку спанов в Jaeger (`meshConfig.defaultConfig.tracing`).
  - Приложение **не обязано** быть инструментировано — Envoy даёт «чёрный ящик» трейсинг между сервисами. Но для **внутренних** операций приложения (БД, вызовы внутри) нужна инструментация через OTel SDK.
  - **Sampling** задаётся в Istio: `pilot.traceSampling` (например, 1%).
  - **Headers**: Istio поддерживает B3, W3C, Jaeger — настраивается через `meshConfig.defaultConfig.tracing`.

- Zipkin, Jaeger, OpenTelemetry — как соотносятся
  - **Zipkin** — старейший open-source трейсинг (Twitter, 2012, на идеях Dapper). Свой формат, свой UI, **B3** propagation. Сейчас менее активен, но всё ещё используется.
  - **Jaeger** — Uber, 2017, CNCF. Изначально свой формат (thrift), свой UI, свой клиент. С 2023 — **backend для OTel**, свои клиенты deprecated.
  - **OpenTelemetry (OTel)** — CNCF, объединение OpenTracing + OpenCensus (2019). **Стандарт** для инструментации, сбора и экспорта телеметрии (traces, metrics, logs). Не backend — SDK + Collector + протокол **OTLP**. Jaeger, Tempo, Zipkin, Datadog, New Relic — все принимают OTLP.
  - **Тренд**: инструментировать через **OTel SDK**, отправлять по **OTLP** в backend (Jaeger, Tempo, Datadog). Jaeger-клиенты и OpenTracing — legacy.
  - **Grafana Tempo** — альтернатива Jaeger от Grafana Labs: дешёвое хранение трейсов в object storage (S3), интегрируется с Grafana. Часто используется вместо Jaeger.

# Kustomize

- Что это
  - Инструмент для «кастомизации» Kubernetes-манифестов без шаблонизации.
  - Работает через **overlay-подход**: base + overlays.
  - Встроен в `kubectl` (`kubectl apply -k <dir>`), отдельный бинарь `kustomize` тоже есть.
  - Часть SIG CLI, развивается как отдельный проект, но всегда доступен в kubectl.
  - **Не шаблонизатор** — оперирует уже готовыми YAML-объектами.
  - **Нет state** — не хранит состояние, как Terraform/Helm-релизы.
  - **Идемпотентен** — повторный рендер даёт тот же результат.

- Зачем нужен
  - Один base — много окружений (dev/stage/prod) с минимальными отличиями.
  - Не дублировать YAML между окружениями.
  - Избежать сложности Go-шаблонов (как в Helm) — YAML остаётся YAML.
  - GitOps-friendly: ArgoCD/Flux нативно поддерживают Kustomize.
  - Простая генерация ConfigMap/Secret с хешем в имени → триггерит rolling update.
  - Патчи точечно: «в prod добавить ресурсы, в dev убрать, в stage изменить replicas».

- Kustomize vs Helm — на практике
  - **Kustomize** — для **своих** манифестов, где нужны overlay'и (dev/stage/prod).
  - **Helm** — для **распространения** (bitnami/nginx, prometheus-operator) и сложной параметризации.
  - **Гибрид**: Helm для установки чарта, Kustomize для патчинга `values`/ресурсов (через `helm template | kustomize build` или `--post-renderer` в Helm).
  - **ArgoCD** поддерживает оба: `source.type: Helm` и `source.type: Kustomize`, плюс `kustomize` как post-renderer для Helm.
  - **Flux** — `Kustomization` CRD + `HelmRelease` CRD, оба нативно.

- Плюсы
  - **Простота**: чистый YAML, без шаблонов.
  - **Встроен в kubectl** — не нужен отдельный инструмент.
  - **GitOps-friendly**: ArgoCD/Flux нативно.
  - **Нет state** — нечего рассинхронизировать.
  - **Overlay'и** — один base, много окружений.
  - **Хеш в имени ConfigMap** — автоматический rolling update.
  - **Предсказуемость**: `kustomize build` всегда даёт один и тот же результат.
  - **Компоненты** — переиспользование фрагментов.
  - **Патчи** — точечные изменения без копирования YAML.

- Минусы и подводные камни
  - **Нет шаблонов** — сложная логика (`if`, `range`, вычисления) невозможна; для этого Helm или Jsonnet.
  - **Нет пакетирования** — нельзя «опубликовать» Kustomize как артефакт в registry (как Helm-чарт).
  - **Нет зависимостей** — нельзя подключить внешний чарт как зависимость (только через `helmCharts` в kustomization, но это ограниченно).
  - **Нет rollback** — откат через Git + ArgoCD/Flux, не `kustomize rollback`.
  - **Патчи стратегические** — могут не работать с CRD без openapi schema; тогда JSON6902.
  - **`commonLabels` меняет selector'ы** — может сломать существующие Deployment (иммутабельный selector). Использовать `labels` (новый) или `commonLabels` только на новых объектах.
  - **`namePrefix`/`nameSuffix`** — ломают ссылки, если не везде; `replacements` помогают, но усложняют.
  - **Хеш в имени ConfigMap** — ссылки в Deployment нужно правильно резолвить (Kustomize обычно справляется, но не всегда для кастомных CRD).
  - **Нет валидации значений** — опечатка в YAML → apply пройдёт, но приложение сломается (нужен kubeconform, conftest, OPA).
  - **Секреты в Git** — `secretGenerator` не шифрует; использовать SOPS/Sealed Secrets/External Secrets.
  - **`patchesStrategicMerge` deprecated** — использовать `patches` (с `path`/`patch`/`target`).

# Императивный подход

- Что это
  - Вы описываете **шаги** (команды, действия), а не **состояние**.
  - Каждый шаг — конкретная инструкция: «создай», «удали», «измени», «запусти».
  - Результат зависит от того, в каком состоянии была система до выполнения и в каком порядке выполнены шаги.
  - Если шаг упал посередине — система остаётся в **промежуточном** состоянии, и нужно думать, как откатить или продолжить.
  - Повторный запуск того же набора шагов **не идемпотентен** — может сломать (например, `mkdir /dir` второй раз упадёт).

- Императивный подход в разных контекстах

  - **IaC (Infrastructure as Code)**
    - **Императивно**: скрипты на bash, Python, AWS CLI (`aws ec2 run-instances ...`), `docker` CLI, `kubectl run/create`.
    - **Декларативно**: Terraform, CloudFormation, Ansible (в основном), Pulumi (code-first, но декларативный по сути), Kubernetes-манифесты.
    - **Плюс императивного**: полный контроль, любая логика, знакомые скрипты.
    - **Минус**: не идемпотентно, сложно откатывать, нет «желаемого состояния», дрейф не отслеживается, повторный запуск может сломать.

  - **Управление конфигурацией**
    - **Императивно**: bash-скрипты, `cmd.run` в SaltStack, `command`/`shell` в Ansible.
    - **Декларативно**: `state`-модули Ansible, Puppet, Chef (частично), SaltStack `state`.
    - Императивные скрипты сложнее поддерживать и тестировать, они не знают, что уже сделано.

  - **Kubernetes**
    - **Императивно**: `kubectl run nginx --image=nginx`, `kubectl create deployment`, `kubectl scale --replicas=3`, `kubectl delete pod`.
    - **Декларативно**: `kubectl apply -f manifest.yaml` (best practice), GitOps (ArgoCD/Flux).
    - **Императивные команды** хороши для отладки, обучения, одноразовых действий.
    - **Декларативные манифесты** — для прода, GitOps, воспроизводимости.
    - **`kubectl create` vs `kubectl apply`**: `create` — императивно (упадёт, если ресурс есть), `apply` — декларативно (создаст или обновит).

  - **Программирование**
    - **Императивно**: C, Python (по умолчанию), Java, Go — вы пишете «сделай A, потом B, потом C».
    - **Декларативно**: SQL («дай мне строки, где...»), HTML/CSS, Prolog, Haskell (частично), React (UI как функция состояния).
    - SQL — классический пример: вы описываете **что** хотите, а планировщик решает **как** (индексы, порядок join'ов).
    - **Functional programming** — ближе к декларативному: `map`, `filter`, `reduce` вместо циклов.

- Плюсы императивного подхода
  - **Полный контроль** над каждым шагом.
  - **Любая логика**: циклы, условия, вычисления, вызовы API.
  - **Знакомые инструменты**: bash, Python, CLI.
  - **Проще для одноразовых задач**: миграция, отладка, эксперимент.
  - **Прозрачность**: видно, что именно происходит.
  - **Хорош для процедурных задач**: «сначала снять бэкап, потом обновить, потом проверить».

- Минусы императивного подхода
  - **Не идемпотентен**: повторный запуск может сломать (`mkdir`, `useradd`, `kubectl create`).
  - **Нет желаемого состояния**: система не знает, «правильно ли сейчас».
  - **Дрейф не отслеживается**: кто-то поменял руками — скрипт не заметит.
  - **Откат сложен**: нужно писать отдельный скрипт или думать, как отменить.
  - **Ошибка посередине** → система в промежуточном состоянии, нужна ручная починка.
  - **Порядок важен**: шаги зависят друг от друга, перестановка ломает.
  - **Сложно тестировать**: нужно эмулировать состояние.
  - **Не масштабируется**: 100 серверов — 100 прогонов скрипта, каждый со своим состоянием.

- Когда императивный подход уместен
  - **Одноразовые задачи**: миграция, восстановление, разовый фикс.
  - **Отладка**: `kubectl run` временного пода, `docker run` для проверки.
  - **Процедурные сценарии**: «сначала бэкап, потом обновление, потом проверка» — порядок критичен.
  - **Сложная логика**, которую неудобно описывать декларативно (например, обход API с пагинацией).
  - **Обучение**: проще понять, что происходит.
  - **Legacy-скрипты**, которые уже работают.

- Когда декларативный подход лучше
  - **Продакшен-инфраструктура**: Terraform, K8s-манифесты, GitOps.
  - **Много окружений**: dev/stage/prod — один код, разные values.
  - **Командная работа**: Git + PR + ревью.
  - **Воспроизводимость**: одинаковый результат у всех.
  - **Drift detection**: «кто-то поменял руками» — видно.
  - **Аудит**: история изменений в Git.
  - **Идемпотентность**: безопасный повторный запуск.

# Jsonnet

- Что это
  - Функциональный язык, компилируемый в JSON (и далее в YAML через конвертеры).
  - Не шаблонизатор: нет подстановки строк, есть вычисление выражений.
  - Полноценный язык: функции, переменные, условия, массивы, объекты, импорты, наследование.
  - Герметичный (hermetic): нет IO, нет сети, нет времени — только входные данные и стандартная библиотека.
  - Детерминированный: один и тот же вход → один и тот же выход.
  - Ленивый: выражения вычисляются по требованию, что позволяет описывать рекурсивные и потенциально бесконечные структуры.
  - Чисто функциональный (с элементами ОО через объекты и `+`-композицию).
  - Создан в Google (2014), открытый, Apache 2.0.

- Зачем нужен в Kubernetes
  - Убрать дублирование между манифестами: один раз описать паттерн, переиспользовать.
  - Генерировать много объектов из одного описания (например, Deployment + Service + HPA для каждого сервиса).
  - Композиция: наследование объектов через `+` (merge), как миксины.
  - Параметризация без «магии» текстовых шаблонов — через функции и аргументы.
  - Много окружений (dev/stage/prod) — один код, разные параметры.
  - Библиотеки: `kube-libsonnet`, `k8s-libsonnet`, `kube-prometheus`, `grafonnet` — готовые абстракции для K8s, Prometheus, Grafana.
  - Валидация на этапе компиляции: ошибки в выражениях видны сразу, а не при `kubectl apply`.

- Ключевые особенности языка
  - **Всё — выражение**: нет операторов, нет top-level деклараций; `local`, `if`, `function`, `import` — тоже выражения.
  - **Объекты и наследование**: `obj1 + obj2` рекурсивно мержит объекты; `+:` — «super», для переопределения с доступом к родителю.
  - **`local`** — привязка переменной: `local x = 1; x + 2`.
  - **Функции** — первоклассные: `local f(x) = x * 2; f(3)`.
  - **Импорты** — `import 'file.libsonnet'`, `importstr 'file.txt'` (как строка), `importbin` (бинарный).
  - **Стандартная библиотека** (`std.*`) — `std.map`, `std.filter`, `std.length`, `std.mergePatch`, `std.parseYaml`, `std.manifestYamlDoc` и т.д.
  - **Comprehension** — генерация массивов и объектов: `[x * 2 for x in [1,2,3]]`.
  - **Assertions** — `assert condition : message;` для валидации.
  - **`self` и `$`** — ссылки на текущий и корневой объект.
  - **Нет циклов** — вместо них рекурсия и comprehension.
  - **Нет присваивания** — переменные неизменяемы.

- Пример: базовый Jsonnet
  ```jsonnet
  local replicas = 3;
  local app = 'web';

  {
    apiVersion: 'apps/v1',
    kind: 'Deployment',
    metadata: { name: app },
    spec: {
      replicas: replicas,
      selector: { matchLabels: { app: app } },
      template: {
        metadata: { labels: { app: app } },
        spec: {
          containers: [{
            name: app,
            image: 'nginx:1.25',
            ports: [{ containerPort: 80 }],
          }],
        },
      },
    },
  }
  ```

- Пример: композиция через `+` (миксины)
  ```jsonnet
  local base = {
    metadata: { labels: { app: 'web' } },
    spec: { replicas: 1 },
  };

  local prod = base + {
    metadata+: { labels+: { env: 'prod' } },
    spec+: { replicas: 5 },
  };
  ```
  - `+:` — «super», позволяет обращаться к родительскому полю и переопределять его.
  - Рекурсивный merge — глубокое слияние объектов.

- Пример: генерация из списка
  ```jsonnet
  local services = ['api', 'web', 'worker'];

  {
    [svc + '-deployment']: {
      apiVersion: 'apps/v1',
      kind: 'Deployment',
      metadata: { name: svc },
      spec: { /* ... */ },
    }
    for svc in services
  }
  ```
  - Object comprehension — генерация ключей и значений.

- Инструменты экосистемы
  - **`jsonnet`** — компилятор (CLI): `jsonnet file.jsonnet`.
  - **`jsonnetfmt`** — форматтер.
  - **`jsonnet-bundler` (`jb`)** — менеджер зависимостей (аналог `go mod`): `jb init`, `jb install github.com/...`.
  - **Tanka** (Grafana Labs) — «надстройка» для K8s: environments, `main.jsonnet`, интеграция с `kubectl`, импорт Helm-чартов и Kustomize, `tk apply`, `tk diff`.
  - **`kubecfg`** — простой инструмент: компилирует Jsonnet и применяет в K8s.
  - **`kube-libsonnet`** (Bitnami) — библиотека абстракций для K8s.
  - **`k8s-libsonnet`** (jsonnet-libs) — сгенерированные библиотеки для всех K8s API (преемник ksonnet-lib).
  - **`kube-prometheus`** — мониторинг-стек на Jsonnet (Prometheus, Alertmanager, Grafana).
  - **`grafonnet`** — библиотека для генерации дашбордов Grafana.
  - **ArgoCD** поддерживает Jsonnet нативно (и через плагины с `jb`).
  - **Flux** — через `jsonnet-controller` или OCI-образы с библиотеками.
  - **Kapitan** (DeepMind) — инструмент для K8s + Jsonnet + шаблоны.

- Jsonnet vs Helm vs Kustomize

| | Jsonnet | Helm | Kustomize |
|---|---|---|---|
| Подход | полноценный язык | текстовые шаблоны (Go) + values | overlay/патчи (YAML) |
| Мощность | высокая (функции, композиция, импорты) | средняя | низкая (патчи) |
| Кривая обучения | **высокая** | средняя | низкая |
| Пакетирование | нет (библиотеки + `jb`) | чарты (OCI, ChartMuseum) | нет |
| Rollback | вручную / GitOps | `helm rollback` | Git revert |
| Экосистема | академическая, Google-adjacent | 20 000+ чартов | встроен в kubectl |
| GitOps | через Tanka/плагины | нативно (ArgoCD/Flux) | нативно |

  - **Когда Jsonnet**: нужна сложная генерация, много окружений, DRY, команда готова учить язык, Google-adjacent окружение.
  - **Когда Helm**: нужны готовые чарты, пакетирование, rollback, экосистема.
  - **Когда Kustomize**: простые overlay'и, YAML без логики, нативный kubectl.
  - **Гибрид**: Tanka умеет импортировать Helm-чарты и Kustomize-манифесты в Jsonnet.

- Jsonnet vs CUE vs Dhall
  - **CUE** — современный язык конфигурации, объединяет типы и значения, встроенная валидация, лучшая композиция (unification). Считается «следующим шагом» после Jsonnet.
  - **Dhall** — строго типизированный, функциональный, но медленная компиляция и сложные типы; ниша — безопасные конфигурации с сильной типизацией.
  - **Jsonnet** — более простой вход, но **нет типов и валидации** — это главный недостаток по сравнению с CUE/Dhall.
  - **KCL** — ещё одна альтернатива с типами и валидацией.

- Плюсы
  - **DRY**: переиспользование через функции и библиотеки.
  - **Мощная композиция**: `+`, `+:` (super), рекурсивный merge.
  - **Детерминизм**: герметичность → одинаковый результат.
  - **Ленивость**: эффективная генерация больших структур.
  - **Библиотеки**: kube-libsonnet, k8s-libsonnet, kube-prometheus, grafonnet.
  - **Ошибки на этапе компиляции**, а не при apply.
  - **Tanka** даёт удобный workflow для K8s (environments, diff, apply).
  - **Поддержка ArgoCD/Flux** (нативно или через плагины).

- Минусы и подводные камни
  - **Высокий порог входа**: функциональный язык, другой образ мышления (не императивный).
  - **Нет типов и валидации**: опечатки в полях не ловятся до apply (в отличие от CUE).
  - **Нет встроенного пакетирования/rollback**: в отличие от Helm.
  - **Экосистема меньше**, чем у Helm.
  - **Отладка сложнее**: ошибки в выражениях, stack traces, «где именно сломалось».
  - **IDE-поддержка слабее** из-за динамической природы.
  - **Производительность** на очень больших проектах может страдать (ленивость помогает, но не всегда).
  - **Герметичность** — плюс для безопасности, но минус, если нужен доступ к внешним данным (приходится передавать через `--ext-str`/`--ext-code` или `importstr`).
  - **Серверная оценка** — риск DoS, если принимать Jsonnet от недоверенных пользователей.
  - **jq может быть лучше** для одноразовых трансформаций JSON; Jsonnet — для конфигурации.

- Best practices
  - **Библиотеки (`libsonnet`)** — выносить общие абстракции, не дублировать.
  - **`jsonnet-bundler`** — фиксировать версии зависимостей (`jsonnetfile.lock.json`).
  - **`jsonnetfmt`** — форматирование в CI.
  - **`assert`** — валидировать входные параметры.
  - **Tanka** — для K8s-workflow: `environments/`, `main.jsonnet`, `tk diff`, `tk apply`.
  - **Не злоупотреблять `+`** — глубокий merge может быть неочевидным; документировать.
  - **Разделять** `lib/` (абстракции), `environments/` (параметры), `manifests/` (генерация).
  - **CI**: `jsonnet` → `kubeconform`/`kubeval` → `conftest`/OPA → diff.
  - **Не принимать Jsonnet от недоверенных источников** без sandbox (DoS-риск).
  - **Документировать** экспортируемые функции и поля библиотек.

- Частые вопросы на собеседовании
  - **«Что такое Jsonnet?»** — Функциональный язык для генерации конфигурации, компилируется в JSON. Полноценный язык (функции, импорты, композиция), но герметичный и детерминированный.
  - **«Jsonnet vs Helm?»** — Jsonnet — язык, Helm — шаблоны + values. Jsonnet мощнее и DRY, но сложнее и без пакетирования/rollback. Helm — экосистема и простота.
  - **«Jsonnet vs Kustomize?»** — Jsonnet — генерация логики, Kustomize — патчи поверх YAML. Jsonnet для сложного, Kustomize для простых overlay'ей.
  - **«Что такое `+` и `+:` в Jsonnet?»** — `+` — рекурсивный merge объектов; `+:` — «super», переопределение с доступом к родительскому значению.
  - **«Что такое герметичность (hermeticity)?»** — Нет IO, сети, времени; только входные данные и stdlib. Детерминизм и безопасность.
  - **«Что такое Tanka?»** — Надстройка над Jsonnet для K8s (Grafana Labs): environments, `main.jsonnet`, `tk apply`, импорт Helm/Kustomize.
  - **«Как управлять зависимостями?»** — `jsonnet-bundler` (`jb`), `jsonnetfile.json` + `jsonnetfile.lock.json`.
  - **«Минусы Jsonnet?»** — Высокий порог входа, нет типов/валидации (в отличие от CUE), нет пакетирования/rollback, меньше экосистема, сложная отладка.
  - **«CUE vs Jsonnet?»** — CUE — типы + валидация + унификация, «следующий шаг». Jsonnet — проще, но без типов.
  - **«Можно ли использовать Jsonnet с ArgoCD/Flux?»** — Да: ArgoCD нативно (и через плагины с `jb`), Flux через `jsonnet-controller`/OCI.

- Короткий ответ на собеседовании
  - Jsonnet — это функциональный язык для генерации конфигурации, компилируемый в JSON. В отличие от Helm и Kustomize, это полноценный язык с функциями, переменными, импортами и композицией объектов (`+`). Он герметичный (нет IO/сети/времени) и детерминированный, что делает его безопасным и предсказуемым. Для Kubernetes Jsonnet позволяет убрать дублирование, генерировать много манифестов из одного описания и переиспользовать библиотеки (`kube-libsonnet`, `k8s-libsonnet`, `kube-prometheus`, `grafonnet`). Экосистема: `jsonnet` CLI, `jsonnetfmt`, `jsonnet-bundler` (`jb`), Tanka (Grafana) для K8s-workflow, ArgoCD/Flux с плагинами. Главные минусы — высокий порог входа, отсутствие типов и валидации (в отличие от CUE), нет пакетирования и rollback, как у Helm. Jsonnet выбирают, когда нужна сложная генерация и DRY, команда готова учить язык, и окружение Google-adjacent; иначе Helm (экосистема, простота) или Kustomize (простые overlay'и).

- Что запомнить железно
  - **Jsonnet = функциональный язык → JSON**, не шаблонизатор.
  - **Герметичный, детерминированный, ленивый**.
  - **`+` — merge, `+:` — super** (доступ к родителю).
  - **`local`** — переменная, **`import`** — библиотека, **`std.*`** — stdlib.
  - **`jsonnet-bundler` (`jb`)** — зависимости, **Tanka** — K8s-workflow.
  - **Библиотеки**: `kube-libsonnet`, `k8s-libsonnet`, `kube-prometheus`, `grafonnet`.
  - **ArgoCD** нативно, **Flux** через плагины.
  - **Минусы**: высокий порог входа, **нет типов/валидации**, нет пакетирования/rollback.
  - **CUE** — «следующий шаг» с типами и валидацией.
  - **Для сложной генерации — Jsonnet**, для экосистемы — Helm, для простых overlay'ей — Kustomize.

# Kubernetes. Liveness, Readiness и Startup probes

- Что это
  - **Probes** — периодические проверки контейнера, которые выполняет **kubelet** на ноде (не control plane).
  - Настраиваются **на каждый контейнер** в `spec.containers[].livenessProbe`, `readinessProbe`, `startupProbe`.
  - Результат: `Success`, `Failure`, `Unknown`.
  - Три типа проб решают **разные задачи** и по-разному влияют на под.

- Способы проверки (mechanics)
  - **`httpGet`** — GET-запрос на `path:port`. Успех — код **200–399**. Остальное — failure.
  - **`tcpSocket`** — попытка TCP-соединения на `port`. Успех — соединение установлено.
  - **`exec`** — выполнить команду **внутри** контейнера. Успех — exit code **0**.
  - **`grpc`** — gRPC health check (K8s 1.23+ beta, 1.24 stable, `grpc_health_probe` или нативный gRPC health protocol).
  - **Лучший выбор**: `httpGet` для HTTP-сервисов (просто, стандартно), `tcpSocket` для TCP-сервисов, `exec` для legacy/специфики, `grpc` для gRPC.
  - **Не использовать `exec` с `curl`/`wget`**, если в образе их нет (distroless, scratch) — проба всегда будет падать.

- Параметры проб (общие для всех трёх)
  - **`initialDelaySeconds`** — сколько ждать перед **первой** проверкой. Default 0.
  - **`periodSeconds`** — как часто проверять. Default 10.
  - **`timeoutSeconds`** — таймаут одной проверки. Default 1.
  - **`successThreshold`** — сколько успехов подряд нужно, чтобы считать «ок» после failure. Default 1. **Для liveness и startup всегда 1** (нельзя больше).
  - **`failureThreshold`** — сколько неудач подряд, чтобы считать «провал». Default 3.
  - **`terminationGracePeriodSeconds`** — при убийстве по liveness — сколько ждать graceful shutdown. Default 30.

- Liveness probe — «жив ли»
  - **Задача**: проверить, что процесс **не завис** (deadlock, бесконечный цикл, утечка, OOM-adjacent). Если процесс жив, но не отвечает — kubelet **убивает** контейнер (SIGTERM → grace → SIGKILL), и он перезапускается согласно `restartPolicy`.
  - **Эффект failure**: контейнер **рестартится**. Под остаётся, IP не меняется (pause держит netns). Счётчик `RESTARTS` растёт.
  - **`failureThreshold` × `periodSeconds`** — сколько времени процесс должен быть «мёртв», чтобы его убили. Например, 3 × 10s = 30 секунд.
  - **Что проверять**: «отвечает ли event loop», «не завис ли главный поток», «жив ли процессор». **Не** зависимости (БД, внешние API) — иначе падение БД убивает все поды.
  - **Классический пример**: HTTP `/healthz` возвращает 200, если приложение отвечает, и 500, если внутренний deadlock.
  - **Антипаттерн**: liveness проверяет БД → БД упала → все поды в рестарт → каскадный сбой. Для зависимостей — readiness.

- Readiness probe — «готов ли принимать трафик»
  - **Задача**: проверить, что контейнер **готов обрабатывать запросы**. Пока не готов — **убирается из Endpoints** Service'а (kube-proxy перестаёт слать трафик), но **не убивается**.
  - **Эффект failure**: под **не получает трафик** от Service, но продолжает работать. Когда проба снова успешна — возвращается в Endpoints.
  - **Что проверять**: прогреты ли кэши, установлены ли соединения с БД, загружены ли конфиги, готов ли HTTP-сервер.
  - **Классический пример**: приложение стартует 30 секунд, прогревает кэш → readiness `/ready` возвращает 200 только после прогрева.
  - **Readiness + Service**: под без readiness-пробы считается готовым **сразу после запуска контейнера** — трафик может пойти на ещё не готовый под. Поэтому readiness нужна почти всегда.
  - **Readiness и rolling update**: Deployment ждёт `Ready=true` перед удалением старого пода. Без readiness — трафик на неготовый под → 502/503.
  - **Readiness и `minReadySeconds`**: под считается `Available` только через `minReadySeconds` после `Ready=true` — защита от «мигнувших» подов.

- Startup probe — «запустился ли»
  - **Задача**: дать приложению **время на старт**, не убивая его liveness-пробой. Пока startup не успешна — **liveness и readiness не выполняются**.
  - **Эффект failure**: если startup не прошла за `failureThreshold × periodSeconds` — контейнер **убивается** (как liveness).
  - **Эффект success**: startup больше **не выполняется**, начинают работать liveness и readiness.
  - **Зачем**: для медленно стартующих приложений (JVM, .NET, большие миграции, ML-модели) — иначе liveness убьёт контейнер до того, как он успел запуститься.
  - **Альтернатива без startup**: увеличить `initialDelaySeconds` у liveness — но это «костыль»: если приложение стартует быстрее, зря ждём; если медленнее — убьёт.
  - **Параметры**: `failureThreshold` × `periodSeconds` = максимальное время на старт. Например, 30 × 10s = 5 минут.
  - **K8s 1.18+** — stable.

- Как они работают вместе
  ```
  Контейнер запущен
      │
      ▼
  startup probe (если задана) ── failure ──► kill, restart
      │ success
      ▼
  liveness + readiness (параллельно)
      │
      ├── liveness failure ──► kill, restart
      │
      └── readiness failure ──► убрать из Endpoints (не убивать)
  ```
  - **Startup** — «гейт» перед liveness/readiness.
  - **Liveness** — «не завис ли».
  - **Readiness** — «можно ли слать трафик».
  - **Все три могут быть на одном контейнере** — обычно так и делают для критичных сервисов.

- Типичные сценарии
  - **Медленный старт (JVM, .NET)**: `startupProbe` с большим `failureThreshold` (например, 5 минут), `livenessProbe` с `periodSeconds: 10`, `readinessProbe` с проверкой прогрева.
  - **HTTP-сервис**: `readinessProbe` на `/ready` (проверяет зависимости), `livenessProbe` на `/healthz` (только процесс).
  - **База данных**: `tcpSocket` на порт, `livenessProbe` не должен трогать репликацию.
  - **Worker без HTTP**: `exec` на проверку heartbeat-файла или `tcpSocket` на метрики-порт.
  - **gRPC-сервис**: `grpc` probe на health-сервис.
  - **Batch/Job**: probes обычно не нужны (Job не перезапускается по liveness так же).

- Типичные ошибки и подводные камни
  - **Liveness проверяет зависимости** (БД, API) → падение зависимости убивает все поды → каскад. **Readiness** — для зависимостей, **liveness** — только «жив ли процесс».
  - **Нет readiness** → трафик идёт на неготовый под → 502/503 при старте и rolling update.
  - **Readiness и liveness на одном endpoint** → при проблеме с зависимостью под выпадает из Endpoints **и** убивается — двойной удар.
  - **`initialDelaySeconds` вместо `startupProbe`** → либо зря ждём, либо убиваем медленный старт. Для медленных — startup.
  - **`successThreshold > 1` для liveness** → ошибка валидации (для liveness и startup всегда 1).
  - **`exec` probe с `curl` в distroless/scratch** → curl нет, проба всегда падает, контейнер в рестарт-лупе.
  - **Слишком агрессивные параметры** (`periodSeconds: 1`, `failureThreshold: 1`) → ложные срабатывания, рестарты на ровном месте.
  - **Слишком мягкие параметры** (`periodSeconds: 60`, `failureThreshold: 5`) → 5 минут на обнаружение зависания, долгий простой.
  - **Readiness без `minReadySeconds`** → под может «мигнуть» и получить трафик, не успев прогреться.
  - **Probes не учитывают `terminationGracePeriodSeconds`** → при liveness-kill контейнер может не успеть graceful shutdown, если grace маленький.
  - **`startupProbe` без `livenessProbe`** → если приложение зависло после старта, никто не заметит.
  - **HTTP probe на `/`** → может вернуть 200, даже если приложение не готово (лендинг). Лучше отдельный `/healthz`/`/ready`.
  - **Probe на порт, который слушает только localhost** → `httpGet` идёт с ноды, не с localhost, может не достучаться.
  - **`timeoutSeconds: 1` по умолчанию** → для медленных проверок (БД-пинг) может ложно падать, увеличить.

- Probes и Service / Deployment
  - **Service** использует **readiness** для Endpoints. Liveness на Service не влияет.
  - **Deployment rolling update** ждёт `Ready=true` (readiness) перед удалением старого пода. Без readiness — downtime.
  - **`minReadySeconds`** — под считается `Available` через N секунд после `Ready`. Защита от «мигнувших» подов.
  - **`progressDeadlineSeconds`** — если rollout не прогрессирует (readiness не проходит), Deployment помечается failed.
  - **HPA** учитывает `Ready` поды для масштабирования.

- Probes vs другие механизмы
  - **Probes** — проверка состояния контейнера kubelet'ом.
  - **`preStop` hook** — действие **перед** остановкой контейнера (graceful shutdown).
  - **`postStart` hook** — действие **после** старта контейнера (но до readiness).
  - **`terminationGracePeriodSeconds`** — сколько ждать graceful shutdown после SIGTERM.
  - **`minReadySeconds`** — задержка перед `Available`.
  - **`PodDisruptionBudget`** — сколько подов можно вывести при drain/eviction.

- Частые вопросы на собеседовании
  - **«Liveness vs readiness?»** — Liveness убивает и перезапускает контейнер, если процесс завис. Readiness убирает под из Endpoints, если он не готов принимать трафик, но не убивает.
  - **«Зачем startup probe?»** — Для медленно стартующих приложений: даёт время на старт, не убивая liveness'ом. После успеха больше не выполняется.
  - **«Что будет, если liveness упадёт?»** — kubelet убьёт контейнер (SIGTERM → grace → SIGKILL), контейнер перезапустится по `restartPolicy`. Под остаётся, IP не меняется.
  - **«Что будет, если readiness упадёт?»** — Под убирается из Endpoints Service'а, трафик не идёт, но контейнер живёт. Когда readiness снова успешна — возвращается.
  - **«Почему liveness не должен проверять БД?»** — Падение БД → все поды в рестарт → каскадный сбой. Для зависимостей — readiness.
  - **«Можно ли задать `successThreshold > 1` для liveness?»** — Нет, для liveness и startup всегда 1. Для readiness — можно.
  - **«Что такое `minReadySeconds`?»** — Под считается `Available` через N секунд после `Ready=true` — защита от «мигнувших» подов.
  - **«Как probes влияют на rolling update?»** — Deployment ждёт `Ready=true` (readiness) перед удалением старого пода. Без readiness — downtime.
  - **«`exec` probe в distroless — проблема?»** — Да, `curl`/`wget` нет, проба падает, контейнер в рестарт-лупе. Использовать `httpGet`/`tcpSocket` или бинарь health-check в образе.
  - **«`initialDelaySeconds` vs `startupProbe`?»** — `initialDelaySeconds` — фиксированная задержка, «костыль». `startupProbe` — гибкий гейт: пока не стартовал, liveness не выполняется; как только стартовал — сразу работает.
  - **«Можно ли probes на gRPC?»** — Да, `grpc` probe (K8s 1.24+ stable).

# Что такое BGP?

- Что это
  - Border Gateway Protocol 
  - **Протокол маршрутизации между автономными системами** (Exterior Gateway Protocol, EGP). Де-факто стандарт для интернета.
  - **Path-vector** протокол: каждый анонс несёт **полный список AS**, через которые прошёл префикс. Это позволяет обнаруживать петли и применять политики.
  - Работает **поверх TCP, порт 179**. Это даёт надёжную доставку, инкрементальные обновления (не periodic refresh), keepalive. Минус — congestion control на протоколе маршрутизации может мешать при перегрузке.
  - **Не про производительность, а про политику и связность**: BGP не выбирает «самый быстрый» путь по метрике — он выбирает путь, соответствующий политике AS (коммерческие отношения, фильтры, предпочтения).
  - Текущая версия — **BGP-4** (RFC 4271), поддерживает CIDR и 32-битные ASN.

- Ключевые понятия
  - **Autonomous System (AS)** — сеть под **единым административным контролем** с единой политикой маршрутизации. Например, провайдер, крупная компания, CDN. Каждая AS имеет уникальный **ASN** (16 или 32 бита).
  - **Префикс** — блок IP-адресов, который анонсируется (например, `192.0.2.0/24`). BGP анонсирует именно **префиксы**, а не отдельные хосты.
  - **BGP-пир (neighbor)** — другой маршрутизатор, с которым установлена TCP-сессия BGP.
  - **NLRI** (Network Layer Reachability Information) — префиксы в update-сообщении.
  - **RIB** (Routing Information Base) — таблица маршрутов BGP, из которой выбирается лучший путь и ставится в FIB (kernel routing table).

- eBGP vs iBGP — два режима
  - **eBGP (External BGP)** — сессия между роутерами **разных AS**. Обычно пиры **напрямую соединены** (directly connected). При анонсе eBGP меняет `NEXT_HOP` на свой адрес и **добавляет свой ASN в `AS_PATH`** (loop prevention).
  - **iBGP (Internal BGP)** — сессия между роутерами **внутри одной AS**. Не обязательно напрямую соединены (обычно через loopback, доступный по IGP). `NEXT_HOP` **не меняется**, `AS_PATH` **не меняется** (нет добавления ASN). iBGP **не анонсирует** маршруты, полученные от одного iBGP-пира, другому iBGP-пиру — отсюда требование full mesh или Route Reflector.
  - **Зачем iBGP**: eBGP-граничные роутеры узнают внешние маршруты, но остальные роутеры внутри AS тоже должны знать, как достичь этих префиксов. iBGP распространяет внешние маршруты внутри AS.
  - **Full mesh iBGP** — каждый с каждым. **Не масштабируется**: N роутеров → N(N-1)/2 сессий.
  - **Route Reflector (RR)** — решение проблемы full mesh: один (или несколько) роутеров отражают маршруты между клиентами. Клиенты не нуждаются в full mesh. Добавляются атрибуты `ORIGINATOR_ID` и `CLUSTER_LIST` для предотвращения петель.
  - **BGP Confederation** — альтернатива RR: AS делится на суб-AS, внутри — iBGP, между — eBGP-подобные сессии.

- Безопасность BGP
  - BGP **изначально не имеет встроенной аутентификации** анонсов. Любой может анонсировать чужой префикс → **BGP hijacking** (перенаправление трафика через себя).
  - **RPKI (Resource Public Key Infrastructure)** — криптографическая инфраструктура, где владелец префикса публикует **ROA** (Route Origin Authorization): «AS X имеет право анонсировать префикс Y».
  - **ROV (Route Origin Validation)** — маршрутизатор проверяет анонс против ROA: `Valid`, `Invalid`, `NotFound`. `Invalid` — дропать или понижать приоритет. Без ROV RPKI бесполезен.
  - **Проблема**: ROV принят **не полностью**; неполное развёртывание делает некоторые атаки «невидимыми» — таблицы выглядят нормально, но трафик уводится.
  - **BGPSec / ASPA** — будущие/развивающиеся механизмы для аутентификации всего `AS_PATH`, а не только origin. Пока не стандарт де-факто.
  - **TTL security (GTSM)** — проверка TTL=255 на eBGP-сессиях, защита от подделки пакетов.
  - **MD5/TCP-AO** — аутентификация BGP-сессии (слабая, но лучше чем ничего).
  - **Prefix filters / max-prefix** — ограничить, сколько префиксов можно принимать от пира (защита от «случайного» анонса полной таблицы).

- BGP в Kubernetes и DevOps
  - **Calico** — может использовать BGP для распространения pod CIDR и Service IP между нодами и в физическую сеть (BGP data plane). Ноды пирятся с ToR-роутерами, анонсируют свои pod CIDR. Это позволяет отказаться от overlay (VXLAN/IP-in-IP) и получить нативную маршрутизацию.
  - **Cilium** — имеет **BGP Control Plane** (с 1.13+) для анонса Service IP и pod CIDR. Заменяет kube-proxy в部分 сценариев и MetalLB. CRD: `CiliumBGPClusterConfig`, `CiliumBGPPeerConfig`, `CiliumBGPAdvertisement`.
  - **MetalLB в BGP-режиме** — каждый узел кластера устанавливает BGP-сессию с физическим роутером и анонсирует **внешние IP сервисов** (`LoadBalancer`). Роутер, поддерживающий multipath, распределяет трафик по нодам. `kube-proxy` (или eBPF) делает финальный хоп до пода.
  - **Зачем это в K8s**: on-prem окружения без облачного LB; нужно, чтобы внешние клиенты ходили на Service IP через физическую сеть; отказ от overlay в пользу нативной маршрутизации для производительности и observability.
  - **Anycast** — можно анонсировать один и тот же Service IP из нескольких кластеров/локаций, BGP приведёт клиента к ближайшему.

- Плюсы BGP
  - **Масштабируемость**: держит полную таблицу интернета (~1 млн префиксов) и работает между тысячами AS.
  - **Гибкая политика**: `LOCAL_PREF`, `AS_PATH`, `MED`, `COMMUNITY` — можно тонко управлять трафиком.
  - **Loop prevention** через `AS_PATH`.
  - **Стандарт де-факто** для интернета и для on-prem Kubernetes.
  - **Multipath / ECMP** — балансировка через несколько путей.
  - **Инкрементальные обновления** — не periodic refresh, экономия трафика.

- Минусы и подводные камни
  - **Медленная сходимость (convergence)**: после изменения топологии BGP может сходиться секунды-минуты. Для критичных сервисов — BFD (Bidirectional Forwarding Detection) для быстрого обнаружения.
  - **Отсутствие встроенной безопасности**: hijacking, route leaks — нужны RPKI/ROV, prefix filters, max-prefix.
  - **Сложность**: политики, атрибуты, iBGP full mesh / RR, «valley-free» routing — высокий порог входа.
  - **`AS_PATH` как метрика** не учитывает реальную пропускную способность/латентность — можно «уехать» на длинный, но политически предпочтительный путь.
  - **Full mesh iBGP** не масштабируется без RR/confederation.
  - **Медленное обнаружение blackhole** — BGP не всегда быстро понимает, что путь сломался.
  - **BGP-сессия на TCP/179** — если TCP-сессия рвётся, все маршруты от пира отзываются (unless graceful restart).
  - **Ошибка в `LOCAL_PREF`/`AS_PATH`** может «высосать» трафик на неподготовленную AS (route leak).

- Частые вопросы на собеседовании
  - **«Что такое BGP?»** — Протокол маршрутизации между AS, path-vector, поверх TCP/179. Не про кратчайший путь, а про политику и связность.
  - **«eBGP vs iBGP?»** — eBGP между разными AS, меняет `NEXT_HOP`, добавляет ASN в `AS_PATH`. iBGP внутри AS, не меняет `NEXT_HOP`/`AS_PATH`, требует full mesh или Route Reflector.
  - **«Зачем Route Reflector?»** — Решает проблему full mesh iBGP: клиенты пирятся с RR, RR отражает маршруты между ними, `ORIGINATOR_ID`/`CLUSTER_LIST` защищают от петель.
  - **«Как BGP выбирает лучший путь?»** — По атрибутам: `WEIGHT` → `LOCAL_PREF` → локально originated → `AS_PATH` → `ORIGIN` → `MED` → eBGP over iBGP → IGP metric → … → router ID.
  - **«Что такое `LOCAL_PREF` и `MED`?»** — `LOCAL_PREF` — предпочтение **внутри AS** (выше — лучше, не уходит в eBGP). `MED` — подсказка **соседней AS** (ниже — лучше, обычно между маршрутами от одного соседа).
  - **«Что такое BGP communities?»** — Теги на маршрутах для политик. Well-known: `NO_EXPORT`, `NO_ADVERTISE`, `BLACKHOLE`. Позволяют применять политики на удалённых AS.
  - **«Как защитить BGP?»** — RPKI/ROV (origin validation), prefix filters, max-prefix, TTL security (GTSM), MD5/TCP-AO, BGPSec/ASPA (в разработке).
  - **«Что такое BGP hijacking?»** — Злонамеренный (или ошибочный) анонс чужого префикса → трафик уводится. Защита — RPKI/ROV, но принята не полностью.
  - **«Зачем BGP в Kubernetes?»** — Calico/Cilium анонсируют pod CIDR и Service IP в физическую сеть; MetalLB анонсирует внешние IP сервисов. Позволяет on-prem LB и нативную маршрутизацию без overlay.
  - **«Почему BGP медленно сходится?»** — Path-vector, политики, TCP-сессии; нужны BFD, graceful restart, tuning timers.

# 3-way handshake (трёхстороннее рукопожатие TCP)

- Что это
  - Процесс установки TCP-соединения: три пакета, три шага.
  - Цель — **синхронизировать ISN** (Initial Sequence Number) обеих сторон и согласовать параметры.
  - Гарантирует, что **обе стороны живы** и могут отправлять/принимать.
  - Происходит **до** передачи данных, на уровне L4 (TCP), поверх IP.
  - В отличие от UDP, где соединения нет, TCP устанавливает состояние на обеих сторонах.

- Три шага
  - **Шаг 1: SYN (клиент → сервер)**
    - Клиент отправляет пакет с флагом **SYN=1**, случайным **ISN (seq=x)**, опциями (MSS, window scaling, SACK permitted, timestamps).
    - Клиент переходит в состояние **SYN_SENT**.
    - «Я хочу открыть соединение, мой начальный sequence number — x».
  - **Шаг 2: SYN-ACK (сервер → клиент)**
    - Сервер отвечает пакетом с флагами **SYN=1, ACK=1**, своим **ISN (seq=y)** и **ack=x+1** (подтверждает ISN клиента).
    - Сервер переходит в состояние **SYN_RECV**.
    - «Согласен, мой начальный sequence number — y, твой x я подтвердил».
  - **Шаг 3: ACK (клиент → сервер)**
    - Клиент отправляет пакет с **ACK=1**, **ack=y+1**, **seq=x+1**.
    - Клиент переходит в **ESTABLISHED**, сервер тоже — в **ESTABLISHED**.
    - «Твой y подтверждён, соединение установлено».
  - После третьего шага обе стороны могут передавать данные.

- Состояния на сторонах

| Шаг | Клиент | Сервер |
|---|---|---|
| До | CLOSED | LISTEN |
| После SYN | SYN_SENT | SYN_RECV |
| После SYN-ACK | SYN_SENT → ESTABLISHED (после ACK) | SYN_RECV |
| После ACK | ESTABLISHED | ESTABLISHED |
  - Видно в `ss -tan` / `netstat -tan`: `SYN-SENT`, `SYN-RECV`, `ESTABLISHED`.
  - **Half-open connection** — состояние `SYN_RECV` на сервере, если клиент не прислал ACK (например, SYN flood).

- Sequence numbers — зачем и почему случайные
  - **ISN** — начальный номер последовательности байтов. Каждый следующий байт увеличивает seq на 1.
  - **Случайность ISN** (RFC 6528) — защита от **TCP spoofing** и **TCP sequence prediction attacks**: если ISN предсказуем, атакующий может подделать пакеты и вклиниться в соединение.
  - **`ack=x+1`** — подтверждение получения байта x; следующий ожидаемый — x+1.
  - **SYN сам занимает один sequence number** (поэтому +1 в ack), хотя данных не несёт.

- Что согласуется в handshake (TCP options)
  - **MSS (Maximum Segment Size)** — максимальный размер данных в сегменте (без заголовков). Обычно MTU − 40 (IPv4) или − 60 (IPv6). Влияет на фрагментацию.
  - **Window scaling** (RFC 1323) — множитель для receive window, позволяет окна > 64 КБ (нужно для high-BDP сетей).
  - **SACK permitted** — Selective ACK: подтверждать не только «до», но и отдельные пропуски, ускоряет retransmission.
  - **Timestamps** — для RTT-измерений и защиты от **PAWS** (Protection Against Wrapped Sequences).
  - **TFO (TCP Fast Open)** — данные в SYN (опционально, редко включено).
  - Если стороны не поддерживают опцию — она не используется.

- Симметрия: 4-way termination
  - Закрытие требует **четырёх** шагов, потому что TCP — **полудуплексный** на уровне закрытия: каждая сторона закрывает своё направление отдельно.
  - **FIN → ACK → FIN → ACK**.
  - Инициатор после FIN переходит в **FIN_WAIT_1**, потом **FIN_WAIT_2**; получатель — в **CLOSE_WAIT**, потом **LAST_ACK**.
  - Инициатор после последнего ACK — в **TIME_WAIT** (2×MSL, обычно 60 секунд), чтобы запоздавшие пакеты старого соединения не попали в новое.
  - **Half-close**: можно закрыть только запись (`shutdown(SHUT_WR)`), оставив чтение — тогда FIN в одну сторону, ACK, а вторая сторона ещё передаёт данные.

- Атаки и защита
  - **SYN flood** — атакующий шлёт много SYN с поддельных IP, сервер отвечает SYN-ACK, держит half-open соединения в `SYN_RECV`, таблица переполняется, легитимные клиенты не могут подключиться (DoS).
  - **SYN cookies** — защита: сервер не хранит состояние для SYN, а кодирует его в ISN (hash от IP/порт/времени). При ACK восстанавливает состояние. Включается `net.ipv4.tcp_syncookies=1` (обычно включено по умолчанию).
  - **`tcp_max_syn_backlog`** — размер очереди half-open соединений.
  - **`somaxconn`** — размер очереди accept (полностью установленных, ждущих `accept()`).
  - **TCP spoofing / sequence prediction** — защита: случайный ISN, SYN cookies, TLS.
  - **Land attack** — SYN с src=src=dst, защита в современных ядрах.
  - **SYN-ACK flood** — реже, защита через rate limiting / firewall.

- 3-way handshake vs TLS handshake
  - **TCP 3-way handshake** — установка транспортного соединения (L4), 1 RTT.
  - **TLS handshake** — установка криптографического соединения (L5–7) **поверх** TCP: TLS 1.2 — 2 RTT, TLS 1.3 — 1 RTT (или 0-RTT при resumption).
  - Итого HTTPS: TCP handshake (1 RTT) + TLS handshake (1–2 RTT) + HTTP запрос.
  - **QUIC** — совмещает транспорт и TLS в одном handshake (1 RTT, 0-RTT при resumption), работает поверх UDP.

- Частые вопросы на собеседовании
  - **«Что такое 3-way handshake?»** — Установка TCP-соединения за три шага: SYN → SYN-ACK → ACK. Синхронизирует ISN, согласует параметры, подтверждает, что обе стороны живы.
  - **«Почему три шага, а не два?»** — Два шага не позволяют обеим сторонам **одновременно** синхронизировать ISN и подтвердить получение. Третий ACK подтверждает, что клиент получил SYN-ACK, и сервер уверен, что клиент жив. Также защищает от старых дубликатов SYN.
  - **«Почему ISN случайный?»** — Защита от spoofing и sequence prediction. Предсказуемый ISN позволяет атакующему подделать пакеты.
  - **«Что такое SYN flood и как защищаться?»** — Много SYN с поддельных IP → переполнение half-open очереди. Защита: SYN cookies, `tcp_max_syn_backlog`, rate limiting, firewall.
  - **«Почему закрытие — 4 шага, а открытие — 3?»** — TCP полудуплексный: каждая сторона закрывает своё направление отдельно (FIN + ACK), поэтому 4 шага. Открытие симметрично — третий ACK совмещает подтверждение и открытие.
  - **«Что такое half-open connection?»** — Состояние `SYN_RECV` на сервере: SYN получен, SYN-ACK отправлен, ACK не пришёл. Может быть нормой (медленный клиент) или признаком SYN flood.
  - **«Что такое TIME_WAIT и зачем?»** — Состояние после закрытия, 2×MSL (обычно 60 с). Защита от запоздавших пакетов старого соединения и гарантия, что последний ACK дошёл. Много TIME_WAIT → исчерпание портов, `SO_REUSEADDR`, тюнинг.
  - **«Сколько RTT занимает handshake?»** — 1 RTT (SYN → SYN-ACK → ACK). Плюс TLS: TLS 1.2 — 2 RTT, TLS 1.3 — 1 RTT (0-RTT при resumption).
  - **«Что такое SYN cookies?»** — Защита от SYN flood: сервер не хранит состояние для SYN, кодирует его в ISN (hash). При ACK восстанавливает. `net.ipv4.tcp_syncookies`.
  - **«Какие опции согласуются в handshake?»** — MSS, window scaling, SACK permitted, timestamps, TFO.

- Короткий ответ на собеседовании
  - 3-way handshake — это процесс установки TCP-соединения за три шага: клиент шлёт **SYN** со своим ISN, сервер отвечает **SYN-ACK** со своим ISN и подтверждением клиентского, клиент шлёт **ACK**. Цель — синхронизировать начальные sequence numbers обеих сторон, согласовать опции (MSS, window scaling, SACK, timestamps) и убедиться, что обе стороны живы и могут отправлять/принимать. ISN случайный для защиты от spoofing. Состояния: клиент `SYN_SENT` → `ESTABLISHED`, сервер `LISTEN` → `SYN_RECV` → `ESTABLISHED`. Handshake занимает 1 RTT; для HTTPS добавляется TLS handshake (TLS 1.2 — 2 RTT, TLS 1.3 — 1 RTT). Закрытие — **4-way** (FIN/ACK → ACK → FIN/ACK → ACK), потому что TCP полудуплексный. Главная атака — **SYN flood**: много SYN с поддельных IP, переполнение half-open очереди; защита — **SYN cookies** (`tcp_syncookies`), `tcp_max_syn_backlog`, rate limiting. Смотреть — `tcpdump` с фильтром по SYN, `ss -tan state syn-recv/syn-sent/established`.

- Что запомнить железно
  - **3-way: SYN → SYN-ACK → ACK**, 1 RTT.
  - **Цель** — синхронизировать ISN, согласовать опции, подтвердить, что обе стороны живы.
  - **ISN случайный** — защита от spoofing/sequence prediction.
  - **Состояния**: `SYN_SENT`, `SYN_RECV`, `ESTABLISHED`.
  - **Закрытие — 4-way** (FIN/ACK → ACK → FIN/ACK → ACK), TCP полудуплексный.
  - **TIME_WAIT** — 2×MSL после закрытия, защита от старых пакетов.
  - **SYN flood** — атака на half-open очередь, защита — **SYN cookies**, `tcp_max_syn_backlog`.
  - **`somaxconn`** — очередь accept, **`tcp_max_syn_backlog`** — очередь SYN.
  - **Опции**: MSS, window scaling, SACK, timestamps.
  - **HTTPS** = TCP handshake (1 RTT) + TLS handshake (TLS 1.2 — 2 RTT, TLS 1.3 — 1 RTT).
  - **QUIC** — handshake совмещён (1 RTT, 0-RTT), поверх UDP.
  - **`ss -tan state syn-recv`** — посмотреть half-open.

# Kubernetes. Фундаментальная модель сети подов

- фундаментальная модель сети подов
  - **Каждый под получает уникальный IP в кластере** — плоская сеть, без NAT между подами.
  - **Все контейнеры внутри пода делят один network namespace** — один IP, один localhost, общий порт-спейс.
  - **IP, который видит контейнер, — тот же, что видят другие поды** — нет NAT между подами, нет «внутреннего» и «внешнего» IP пода.
  - Под может общаться с любым другим подом **напрямую по IP**, без NAT, даже если они на разных нодах.
  - Это требование к CNI: **flat network** — все поды видят друг друга так, будто они в одной L2-сети.
  - **Важно:** это модель, а не «магия». Реализуется CNI-плагином (overlay, routing, eBPF).

- Уровень 2: как это реализовано в Linux
  - **Каждый под работает в своём network namespace** — не каждый процесс, как в заметке, а именно **под** (точнее, sandbox-контейнер пода). Процессы внутри одного контейнера делят netns, контейнеры внутри пода тоже делят один netns.
  - **pause-контейнер (sandbox)** — служебный контейнер в каждом поде, который **держит network namespace открытым**. Если контейнер приложения упадёт и перезапустится, netns останется, IP не поменяется. Pause создаётся kubelet'ом через CRI (containerd/CRI-O).
  - **veth-пара** — виртуальный Ethernet-кабель: один конец в netns пода, другой — в netns хоста (или в bridge/overlay). Так под «подключается» к сети ноды.
  - **Каждая нода получает свой CIDR** для подов (например, `10.244.1.0/24` на node-1, `10.244.2.0/24` на node-2). Под получает IP из диапазона своей ноды.
  - **Маршрутизация между нодами** — задача CNI:
    - **Overlay** (VXLAN, IP-in-IP) — пакет инкапсулируется, идёт по underlay-сети. Flannel (VXLAN), Calico (IP-in-IP), Weave.
    - **Routing** (BGP) — ноды анонсируют CIDR друг другу, пакеты идут напрямую. Calico (BGP), Cilium (BGP).
    - **eBPF** — Cilium, без iptables/kube-proxy для部分 сценариев.

# Kubernetes. CNI

- **CNI** — спецификация и набор плагинов, которые настраивают сеть пода: создают veth, назначают IP, настраивают маршруты, DNS.
- Kubelet вызывает CNI-плагин при создании/удалении пода.
- **Популярные CNI**:
  - **Calico** — BGP или IP-in-IP, поддержка NetworkPolicy, eBPF-режим (Calico eBPF), часто choice для прода.
  - **Cilium** — eBPF-based, L3/L4/L7 policy, observability (Hubble), замена kube-proxy, современный фаворит.
  - **Flannel** — простой overlay (VXLAN), **не поддерживает NetworkPolicy**, хорош для простых кластеров.
  - **Weave Net** — overlay, простой, но менее популярен сейчас.
  - **Antrea** — на Open vSwitch, поддержка NetworkPolicy.
  - **kubenet** — встроенный в kubelet, простой, но не для прода.
- **Flannel как DaemonSet** — да, обычно запускается как DaemonSet на каждой ноде, создаёт интерфейс `flannel.1` (VXLAN) или `cni0` (bridge).
- **Команда `kubectl describe configmaps kube-flannel-cfg -A`** — устаревшая, в современных версиях Flannel конфиг лежит иначе (в Secret/ConfigMap с другим именем, зависит от манифеста). В новых установках смотреть `kubectl -n kube-flannel get cm,secret`.
- **Не путать:** CNI — только про сеть **подов**. Service — отдельный механизм, реализуется kube-proxy или CNI (Cilium eBPF).

# Kubernetes. NetworkPolicy

- **NetworkPolicy** — это API-объект, который описывает, **какие поды** могут общаться с какими (по labels, namespace, портам, CIDR). По сути, это декларативный «сетевой firewall» для подов, который реализует принцип **Zero Trust** на уровне L3/L4.
- **Ключевой принцип работы:** Поды в Kubernetes по умолчанию **не изолированы** и могут общаться со всеми. Однако, как только хотя бы одна NetworkPolicy **выбирает** под (селектором `podSelector`), этот под становится **изолированным** для того направления трафика (Ingress/Egress), которое указано в `policyTypes`. С этого момента **разрешён только тот трафик, который явно описан в правилах** этой или любой другой политики, выбирающей этот под. Политики не имеют правил запрета (`deny`) — запрещено всё, что не разрешено.
- **Селекторы (на кого и на что действует политика):**
    - **`podSelector`** — основной селектор. Определяет, к каким подам в **своём namespace** применяется политика. Пустой `podSelector: {}` выбирает **все поды** в namespace.
    - **`namespaceSelector`** — позволяет разрешить трафик от подов из **других namespace**, выбранных по их labels. Это ключевой инструмент для跨-namespace коммуникации.
    - **`ipBlock`** — определяет диапазон IP-адресов (CIDR) для разрешения трафика, например, от внешнего балансировщика или к внешнему API. `namespaceSelector` и `ipBlock` не могут быть использованы в одном правиле `from`/`to` одновременно.
- **Правила (что разрешено):**
    - **`ingress` (входящий трафик):** описывает, **кому** и на **какие порты** можно подключаться к выбранным подам.
    - **`egress` (исходящий трафик):** описывает, **куда** и на **какие порты** могут подключаться выбранные поды.
    - Каждое правило состоит из списка **`from`/`to`** (источники/назначения) и списка **`ports`** (порты и протоколы).
- **Работает только на L3/L4** (IP-адреса, порты, протоколы TCP/UDP/SCTP). Политики **не анализируют L7-содержимое** (HTTP-методы, пути, заголовки) и не выполняют TLS-терминацию.
- **Требует поддержки CNI (Container Network Interface):** NetworkPolicy — это лишь декларация. Если CNI-плагин не умеет её реализовывать, политики будут созданы в API, но **молча игнорироваться** в data plane. Это создаёт опасную иллюзию безопасности.
    - ✅ **Поддерживают:** Calico, Cilium, Antrea, Weave Net (частично), Kube-router, облачные CNI (GKE, EKS, AKS).
    - ❌ **Не поддерживают:** Flannel (в классическом виде), kubenet (в некоторых конфигурациях). Для Flannel требуется установка дополнительного контроллера, например, Calico для policy enforcement.
- **Default Deny (политика «запрещено всё, что не разрешено»):**
    - Это **фундаментальная лучшая практика**. Создаётся политика с пустым `podSelector: {}` и `policyTypes: [Ingress, Egress]`, которая изолирует все поды в namespace и блокирует весь трафик.
    - После этого создаются отдельные политики, которые **точечно разрешают** только необходимые потоки трафика (например, от frontend к backend, от backend к БД).
- **Пример: Default Deny All**
  ```yaml
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: default-deny-all
    namespace: production
  spec:
    podSelector: {}
    policyTypes:
    - Ingress
    - Egress
  ```
- **Пример: Разрешить трафик от frontend к backend**
  ```yaml
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: allow-frontend-to-backend
    namespace: production
  spec:
    podSelector:
      matchLabels:
        app: backend
    policyTypes:
    - Ingress
    ingress:
    - from:
      - podSelector:
          matchLabels:
            app: frontend
      ports:
      - protocol: TCP
        port: 8080
  ```
- **NetworkPolicy не заменяет** RBAC, аутентификацию или авторизацию на уровне приложения. Это исключительно **сетевая изоляция** на уровне L3/L4.
- **Ограничения и важные нюансы:**
    - **Нет логирования:** стандартный API не позволяет логировать заблокированные или разрешённые соединения. Для этого нужны CNI-специфичные инструменты (например, Hubble в Cilium).
    - **Нет явного `deny`:** политики только разрешают. Запрет — это отсутствие разрешения.
    - **Селекторы по имени сервиса (FQDN):** стандартный `ipBlock` работает только с IP/CIDR. Для разрешения трафика по доменному имени (например, `api.external.com`) нужны расширения CNI, такие как Cilium FQDN policies.
    - **`hostNetwork: true`:** поды, использующие сеть хоста, **не управляются** NetworkPolicy стандартным образом, что создаёт брешь в изоляции.
    - **Производительность:** Включение enforcement политик может увеличить потребление ресурсов (память, CPU) процессами CNI в `kube-system` (например, ~128 MB RAM и ~300 millicores CPU).
    - **Множественные политики:** Если несколько политик выбирают один и тот же под, их разрешающие правила **складываются (аддитивны)**. Трафик разрешён, если его разрешает хотя бы одна из политик.
- **Лучшие практики:**
    1.  **Всегда начинайте с `default-deny-all`** в каждом namespace.
    2.  **Разрешайте только необходимые потоки** — минимально необходимые порты и источники/назначения.
    3.  **Тестируйте политики** в staging-окружении с помощью инструментов вроде `netcat`, `curl` или специализированных фреймворков, чтобы убедиться, что они работают как задумано, и не блокируют легитимный трафик.
    4.  **Используйте CNI с надежной поддержкой политик** (Calico, Cilium) для production-сред.
    5.  **Документируйте** каждое разрешающее правило, чтобы было понятно, зачем оно нужно.
    6.  **Помните о CNI-специфичных расширениях:** для L7-фильтрации или FQDN-политик используйте CiliumNetworkPolicy и аналогичные CRD, если ваш CNI их предоставляет.

# Kubernetes. Service

- Что это:
  - Объект API предоставляющий сетевой доступ к подам (внутри и снаружи)
  - **Service** — стабильный виртуальный IP (ClusterIP) + DNS-имя + балансировка на набор подов по selector.
  - **Реализуется kube-proxy** (или CNI): iptables/IPVS-правила на каждой ноде делают DNAT на поды.
  - **kube-proxy modes**:
    - **iptables** — default, правила iptables, O(n) при большом числе сервисов.
    - **IPVS** — быстрее и масштабируемее на больших кластерах (O(1) lookup), но требует модулей ядра.
    - **nftables** — новый режим (K8s 1.29+), замена iptables.
    - **userspace** — legacy, не использовать.
  - **Cilium может заменить kube-proxy** полностью (eBPF), без iptables/IPVS.

- Типы Service
  - **ClusterIP** (default) — виртуальный IP, доступен **только внутри кластера**. Не «ClusterApi», как в заметке — **ClusterIP**.
  - **NodePort** — открывает порт (30000–32767) на **каждой ноде**, трафик `NodeIP:NodePort` → Service → поды. Обращаться по адресам нод. Обычно используется как база для LoadBalancer или для dev.
  - **LoadBalancer** — облачный LB (AWS NLB/ALB, GCP LB, Azure LB), один внешний IP, трафик идёт на ноды → Service → поды. **Дороже** (каждый LB = деньги), cloud-controller-manager следит за нодами.
  - **ExternalName** — DNS CNAME на внешний сервис, без проксирования.
  - **Headless** (`clusterIP: None`) — без виртуального IP, DNS возвращает IP подов напрямую. Для StatefulSet, gRPC, когда нужен прямой доступ к конкретным подам.

# Что делает kubectl port-forward?
- Уровень 8: доступ к отдельному поду для отладки
  - **`kubectl port-forward`** — туннель с локальной машины на под/сервис через API-сервер, **минуя Service и CNI**.
  - `kubectl port-forward service/myservice 10000:80` — локальный порт 10000 → Service → под.
  - `kubectl port-forward pod/mypod 8080:80` — напрямую на под.
  - Только для отладки, **не для прода** (нет HA, нет балансировки, туннель через apiserver).

# Как развернуть высоконагруженную СУБД в Kubernetes

- Шаг 1: StatefulSet — обязательная база, но не решение
  - **Что даёт**: стабильную сетевую идентичность (`pg-0`, `pg-1`, `pg-2`), стабильное хранилище (свой PVC на каждый под, переживает пересоздание пода), упорядоченный запуск/остановку.
  - **Чего не даёт**: автоматического failover, репликации, бэкапов, PITR, обновлений версий. Решает только «где и как запустить экземпляр».

- Шаг 2: Оператор — «мозг» для управления БД
  - **Что это**: приложение, расширяющее API Kubernetes и инкапсулирующее знания эксперта по эксплуатации конкретной СУБД. Вы описываете желаемое состояние кластера БД в YAML, оператор приводит инфраструктуру к нему.
  - **Ключевые возможности**: развёртывание кластера, настройка репликации, **автоматический failover** (выбор нового мастера), бэкапы и восстановление, обновления версий, масштабирование.
  - **Примеры операторов**:
    - **CloudNativePG (CNPG)** — PostgreSQL, community-driven, CNCF Incubating. Управляет подами напрямую, без StatefulSet. Использует **primary/standby** с нативной потоковой репликацией и **кворумной синхронной репликацией** — транзакция подтверждается только после записи на кворум реплик, что исключает потерю данных при failover.
    - **Zalando Postgres Operator** — PostgreSQL, на Patroni, используется в масштабе Zalando.
    - **Crunchy PGO** — PostgreSQL, интегрирован с pgBackRest.
    - **Percona XtraDB Cluster (PXC) Operator** — MySQL, автоматически создаёт StatefulSet, настраивает master-slave и прокси.

- Шаг 3: Хранилище — фундамент производительности
  - **Local NVMe (рекомендуемый выбор для production)**:
    - Микросекундная задержка, полная пропускная способность диска.
    - **Минус**: данные привязаны к узлу, при отказе узла теряются.
    - **Durability** обеспечивается **репликацией на уровне СУБД** (несколько реплик на разных узлах, синхронная репликация).
    - Для автоматизации подготовки локальных дисков (RAID0, XFS) — `NodeConfig` CR (ScyllaDB Operator) или аналогичные механизмы оператора.
  - **Network-attached storage (EBS, Persistent Disk, Ceph RBD)**:
    - PV можно перемонтировать на другой узел — данные переживают потерю ноды.
    - **Минус**: latency на миллисекунды, ограниченная пропускная способность. **Не подходит для high-IOPS нагрузки.**
  - **`reclaimPolicy: Retain`** — обязательно для PVC с данными, чтобы случайное удаление PVC не привело к потере данных.
  - **`volumeBindingMode: WaitForFirstConsumer`** — обязательно для multi-AZ (EBS, GCE PD, local PV), иначе PV создастся в одной AZ, а под запланируется в другой.
  - **NFS для `$PGDATA` — нельзя**: риск потери данных из-за некорректной работы `fsync` на NFS.

- Шаг 4: Отказоустойчивость и планирование (Scheduling)
  - **Pods на отдельных узлах**: `podAntiAffinity` с `topologyKey: kubernetes.io/hostname` — каждая реплика на своём узле.
  - **Балансировка по зонам**: `topologySpreadConstraints` с `topologyKey: topology.kubernetes.io/zone` — равномерное распределение по AZ, чтобы потеря зоны не привела к потере кворума.

- Шаг 5: Ресурсы и производительность
  - **Guaranteed QoS**: `requests` = `limits` для CPU и памяти — поды в классе Guaranteed, защищены от eviction при нехватке ресурсов.
  - **Тюнинг под лимиты**: параметры СУБД (`shared_buffers` в PostgreSQL) настраиваются с учётом лимитов памяти контейнера, чтобы избежать OOM-kill.

- Шаг 6: Защита данных — бэкапы и PITR
  - **Непрерывное архивирование WAL**: все современные операторы (CNPG, Zalando, Crunchy) поддерживают архивацию WAL в объектное хранилище (S3, GCS, Azure Blob).
  - **Point-in-Time Recovery (PITR)**: восстановление на любой момент времени — критично для отката после ошибочных миграций.
  - **Полные бэкапы**: регулярные (pgBackRest, Barman Cloud) для быстрого восстановления.
  - **Velero** — бэкап всего состояния кластера (манифесты + PV snapshots или file-system backup) для защиты от ошибок оператора или катастрофических сбоев. Запускается по расписанию, управляется через GitOps.
  - **Репликация не заменяет бэкапы**: защищает от отказа узла, но не от логических ошибок (`DROP TABLE`, ошибочная миграция).

- Когда можно (и нужно) запускать БД в Kubernetes
  - **Подходит**: read-реплики, dev/test, временные сервисы, новые cloud-native приложения, где скорость развёртывания и автоматизация важнее абсолютной производительности на единицу ресурсов.
  - **Не подходит (пока)**: высоконагруженные **core** транзакционные системы с экстремальными требованиями к latency и ценой простоя — для них всё ещё предпочитают VM или выделенные серверы.

- Итоговый чек-лист для production

| Компонент | Рекомендация |
|---|---|
| **Управление** | Оператор (CloudNativePG, Zalando, Crunchy, Percona) |
| **Хранилище** | Local NVMe (скорость) + durability через репликацию СУБД |
| **reclaimPolicy** | Retain |
| **volumeBindingMode** | WaitForFirstConsumer |
| **Планирование** | podAntiAffinity по hostname + topologySpreadConstraints по zone |
| **Ресурсы** | Guaranteed QoS (requests = limits) |
| **Репликация** | Синхронная кворумная, минимум 3 инстанса |
| **Бэкапы** | WAL-архивация + полные бэкапы + PITR + Velero |
| **NFS для `$PGDATA`** | Не использовать |

- Короткий ответ на собеседовании
  - Запускать БД в Kubernetes можно, но только по правильному паттерну. «Голый» контейнер или даже StatefulSet недостаточно — они не решают failover, репликацию и бэкапы. Правильный подход: **Оператор** (CloudNativePG для PostgreSQL, Percona для MySQL) — он управляет жизненным циклом кластера БД как единым объектом, включая автоматический failover и кворумную синхронную репликацию. Для производительности выбирают **Local NVMe** (микросекундная latency), а durability обеспечивают **репликацией на уровне СУБД**. Поды разносим по узлам (`podAntiAffinity`) и зонам (`topologySpreadConstraints`), ставим **Guaranteed QoS** (`requests=limits`), тюним `shared_buffers` под лимиты. Бэкапы — двух уровней: встроенные средства оператора (WAL-архивация + PITR) и Velero для всего состояния кластера. `reclaimPolicy: Retain` и `WaitForFirstConsumer` — обязательны, NFS для `$PGDATA` — нельзя. Для core-транзакционных систем с экстремальными требованиями к latency всё ещё часто предпочитают VM, но тренд к K8s растёт (CNPG, Vitess, CockroachDB, TiDB в проде у крупных компаний).

- Что запомнить железно
  - **StatefulSet ≠ решение для БД** — только стабильные имена и диски.
  - **Оператор — единственный production-grade паттерн** для БД в K8s.
  - **Local NVMe** — для скорости, **durability через репликацию СУБД**.
  - **Network storage** — для мобильности PV, но выше latency.
  - **`podAntiAffinity` по hostname** + **`topologySpreadConstraints` по zone**.
  - **Guaranteed QoS** (`requests = limits`) — обязательно.
  - **Кворумная синхронная репликация**, минимум 3 инстанса.
  - **`reclaimPolicy: Retain`** и **`volumeBindingMode: WaitForFirstConsumer`** — обязательны.
  - **WAL-архивация + PITR + Velero** — два уровня защиты.
  - **NFS для `$PGDATA` — нельзя** (fsync).
  - **Репликация ≠ бэкап**: не защищает от `DROP TABLE` и ошибочных миграций.
  - **Core-транзакционные системы** — часто всё ещё VM, но тренд к K8s растёт.

# Kubernetes. Что такое QoS?

- Что это
  - Классификация подов по **приоритету выживания** при нехватке ресурсов на ноде.
  - Определяется **автоматически** kubelet'ом на основе `requests`/`limits` контейнеров — нельзя задать в YAML вручную.
  - Три класса: **Guaranteed**, **Burstable**, **BestEffort**.
  - Влияет на **eviction** при `MemoryPressure`, `DiskPressure`, `PIDPressure`, `NodePressure`.
  - Влияет на **OOM score** — при OOM killer ядра первыми умирают поды с высоким OOM score (BestEffort).
  - **Не путать с PriorityClass**: PriorityClass — это **вручную задаваемый** приоритет для **scheduler'а** (кого планировать первым и кого preempt'ить). QoS — автоматическая классификация для **kubelet eviction** и **OOM killer**. Они работают вместе, но это разные механизмы.

- Три класса QoS

  - **Guaranteed** (самый высокий)
    - Условие: **у каждого** контейнера в поде заданы **и `requests`, и `limits`**, и для **каждого ресурса** (CPU, memory) они **равны** (`requests == limits`).
    - Все контейнеры в поде должны соответствовать — один «неправильный» контейнер понижает весь под.
    - Поды **выселяются последними** при нехватке ресурсов.
    - Самый низкий OOM score — OOM killer убивает их последними.
    - Для чего: **БД, критичные сервисы, stateful-нагрузки** — то, что не должно умирать.

  - **Burstable** (средний)
    - Условие: **хотя бы один** контейнер имеет `requests` или `limits`, но **не выполняется условие Guaranteed** (не все ресурсы заданы, или `requests != limits`).
    - Самый частый класс на практике — так работает большинство приложений.
    - Поды выселяются **после** BestEffort, но **до** Guaranteed.
    - Может использовать больше ресурсов, чем `requests`, если на ноде есть свободное место (до `limits`).
    - OOM score зависит от того, насколько фактическое использование превышает `requests`.

  - **BestEffort** (самый низкий)
    - Условие: **ни один** контейнер не имеет `requests` и `limits` (вообще ничего не задано).
    - Поды выселяются **первыми** при любом давлении на ноду.
    - Самый высокий OOM score — OOM killer убивает их первыми.
    - Может использовать сколько угодно ресурсов, если они свободны, но при конкуренции — страдает первым.
    - Для чего: dev, тесты, неважные batch-задачи.

- Как проверить класс
  ```bash
  kubectl get pod <pod> -o jsonpath='{.status.qosClass}'
  kubectl describe pod <pod> | grep -i qos
  ```

- Eviction — что происходит при нехватке ресурсов
  - Kubelet мониторит ноду: `MemoryPressure`, `DiskPressure`, `PIDPressure`.
  - При давлении начинает **eviction** подов, начиная с **BestEffort**, потом **Burstable**, **Guaranteed** — последними.
  - Внутри одного класса — сортировка по **потреблению относительно `requests`**: кто больше превышает — тот уходит первым.
  - **`ephemeral-storage`** (локальный диск) тоже участвует: если под забивает диск, он может быть выселен независимо от QoS.
  - **`evictionHard`** и **`evictionSoft`** в kubelet-конфиге задают пороги (например, `memory.available<100Mi`).
  - **`pod.terminationGracePeriodSeconds`** — сколько ждать graceful shutdown при eviction.
  - **`PodDisruptionBudget`** — ограничивает, сколько подов можно вывести **добровольно** (drain, eviction API), но **не** защищает от **вынужденного** eviction при давлении на ноду.

- QoS vs PriorityClass — не путать

| | QoS | PriorityClass |
|---|---|---|
| Как задаётся | автоматически по `requests`/`limits` | вручную в `spec.priorityClassName` |
| Кто использует | kubelet (eviction, OOM score) | scheduler (порядок планирования, preemption) |
| Классы | Guaranteed, Burstable, BestEffort | произвольные (например, `high-priority`, `low-priority`) |
| Влияет на | eviction при давлении на ноду | кого планировать первым, кого вытеснять при нехватке места на ноде |
| Когда срабатывает | когда нода уже под давлением | когда scheduler не может найти место для пода |
  - **PriorityClass** нужен, чтобы критичный под запланировался **первым** и вытеснил менее важные поды (preemption), если места нет.
  - **QoS** нужен, чтобы критичный под **выжил** при eviction на уже работающей ноде.
  - **Обычно используют вместе**: БД → `Guaranteed` + `PriorityClass: high`.
  - **Системные поды** (`kube-system`) имеют высокий PriorityClass (`system-cluster-critical`, `system-node-critical`), чтобы не быть вытесненными.

- Практические рекомендации
  - **БД, stateful, критичное**: `Guaranteed` — `requests == limits` для CPU и memory. Плюс `PriorityClass: high` для планирования.
  - **Обычные stateless-приложения**: `Burstable` — `requests` для планирования, `limits` для защиты от runaway.
  - **Dev, тесты, batch**: `BestEffort` — без ресурсов, чтобы не занимать место, но готовы к eviction.
  - **Не задавать `limits` для CPU** — CPU throttling может сильно замедлить приложение (особенно latency-sensitive). Для CPU лучше `requests` = гарантия, `limits` = потолок, но иногда без `limits` лучше (Burstable с высоким `requests`).
  - **Всегда задавать `requests`** — иначе scheduler не знает, сколько нужно, и под может попасть на перегруженную ноду.
  - **`limits` для memory обязательны** — иначе под может съесть всю память ноды и вызвать OOM killer для других.
  - **Guaranteed для БД** — обязательно, иначе при `MemoryPressure` под выселится и БД упадёт.
  - **Помнить про `ephemeral-storage`** — `requests.ephemeral-storage` и `limits.ephemeral-storage` тоже влияют на eviction по `DiskPressure`.

- Типичные ошибки
  - **Задать `requests` без `limits`** → Burstable, но не Guaranteed, при eviction уйдёт раньше критичных.
  - **Задать `limits` без `requests`** → Burstable, `requests` = `limits` по факту, но лучше задать явно.
  - **`requests != limits` для Guaranteed** → на самом деле Burstable, класс не тот.
  - **Один контейнер в поде без ресурсов** → весь под BestEffort, даже если остальные Guaranteed.
  - **Думать, что QoS защищает от OOM killer** → нет, OOM killer ядра использует OOM score, который зависит от QoS, но `limits` — главная защита.
  - **Думать, что PodDisruptionBudget защищает от eviction** → нет, только от **добровольного** disruption (drain, eviction API), не от вынужденного при давлении на ноду.
  - **Путать QoS с PriorityClass** → разные механизмы для разных фаз.

- Частые вопросы на собеседовании
  - **«Что такое QoS в Kubernetes?»** — Автоматическая классификация подов (Guaranteed, Burstable, BestEffort) на основе `requests`/`limits`. Определяет порядок eviction при нехватке ресурсов и OOM score.
  - **«Как получить Guaranteed?»** — `requests == limits` для **всех** ресурсов **всех** контейнеров в поде. Один контейнер без ресурсов → весь под не Guaranteed.
  - **«Чем QoS отличается от PriorityClass?»** — QoS — автоматическая классификация для kubelet (eviction, OOM). PriorityClass — вручную задаваемый приоритет для scheduler (порядок планирования, preemption).
  - **«Какой класс для БД?»** — Guaranteed (`requests == limits`) + `PriorityClass: high` для планирования. Иначе при `MemoryPressure` БД выселится.
  - **«Что происходит при eviction?»** — Kubelet выселяет поды, начиная с BestEffort, потом Burstable, Guaranteed — последними. Внутри класса — кто больше превышает `requests`.
  - **«Может ли QoS защитить от OOM killer?»** — Косвенно: Guaranteed имеет низкий OOM score, убивается последним. Но главная защита — `limits` на память.
  - **«Защищает ли PDB от eviction?»** — Нет, только от **добровольного** disruption (drain, eviction API). От вынужденного eviction при давлении на ноду — нет.
  - **«Почему `limits` для CPU опасны?»** — CPU throttling может сильно замедлить latency-sensitive приложения. Для CPU часто лучше `requests` без `limits` (Burstable), чтобы использовать свободные CPU.
  - **«QoS и ephemeral-storage?»** — `requests.ephemeral-storage`/`limits.ephemeral-storage` тоже влияют на eviction по `DiskPressure`.

- Короткий ответ на собеседовании
  - QoS в Kubernetes — это автоматическая классификация подов по приоритету выживания при нехватке ресурсов. Три класса: **Guaranteed** (`requests == limits` для всех ресурсов всех контейнеров), **Burstable** (хотя бы один `requests`/`limits`, но не Guaranteed), **BestEffort** (ничего не задано). Класс определяется kubelet'ом автоматически, вручную задать нельзя. При `MemoryPressure`/`DiskPressure` kubelet выселяет поды: BestEffort первыми, Burstable средними, Guaranteed последними. OOM score также зависит от QoS — BestEffort умирает первым. QoS не путать с PriorityClass: QoS — для kubelet eviction и OOM, PriorityClass — для scheduler (порядок планирования, preemption). Для БД и критичных сервисов — Guaranteed + PriorityClass high. Для обычных приложений — Burstable. Для dev — BestEffort. PodDisruptionBudget защищает только от добровольного disruption (drain), не от вынужденного eviction. `limits` на память обязательны, на CPU — осторожно (throttling).

- Что запомнить железно
  - **QoS — автоматическая классификация**, не задаётся вручную.
  - **Три класса**: Guaranteed, Burstable, BestEffort.
  - **Guaranteed** = `requests == limits` для **всех** ресурсов **всех** контейнеров.
  - **Eviction**: BestEffort → Burstable → Guaranteed (последними).
  - **OOM score**: BestEffort убивается первым, Guaranteed — последним.
  - **QoS ≠ PriorityClass**: QoS — kubelet (eviction/OOM), PriorityClass — scheduler (планирование/preemption).
  - **БД → Guaranteed + PriorityClass high.**
  - **Обычные приложения → Burstable.**
  - **Dev/тесты → BestEffort.**
  - **PDB не защищает от вынужденного eviction** — только от добровольного.
  - **`limits` на память обязательны**, на CPU — осторожно (throttling).
  - **Один контейнер без ресурсов → весь под BestEffort.**
  - **`ephemeral-storage`** тоже участвует в eviction по `DiskPressure`.
  - **Проверить**: `kubectl get pod <pod> -o jsonpath='{.status.qosClass}'`.

# Kubernetes. Что такое PriorityClass?

- Что это
  - **Cluster-scoped** (не namespaced) объект API `scheduling.k8s.io/v1`.
  - Сопоставляет **имя класса** (например, `high-priority`) с **целым числом** — приоритетом.
  - **Чем выше число — тем выше приоритет.**
  - Под получает приоритет, если в его `spec.priorityClassName` указано имя PriorityClass.
  - **Напрямую `spec.priority` задавать нельзя** — он вычисляется из PriorityClass.
  - Feature state: **Stable** с Kubernetes v1.14.

- Зачем нужен
  - **Порядок планирования**: scheduler ставит поды с более высоким приоритетом **впереди** в очереди ожидания.
  - **Preemption (вытеснение)**: если под не может быть запланирован, scheduler **вытесняет** поды с более низким приоритетом, чтобы освободить место.
  - **Защита критичных нагрузок**: БД, ingress, мониторинг, DNS — должны планироваться первыми и не страдать от «голодных» batch-задач.
  - **Отличие от QoS**: QoS работает **после** планирования (eviction на ноде при давлении). PriorityClass работает **до** планирования (preemption для освобождения места).

- Как работает preemption (пошагово)
  1. Под с высоким приоритетом не может быть запланирован — на всех нодах недостаточно ресурсов.
  2. Scheduler ищет ноду, с которой можно **вытеснить** поды с **более низким приоритетом**, чтобы освободить достаточно места.
  3. Выбирает **набор жертв** с **наименьшим приоритетом** (QoS при этом **не учитывается** в выборе жертв — только PriorityClass).
  4. Вытесняемым подам отправляется **graceful termination** (SIGTERM, ожидание `terminationGracePeriodSeconds`).
  5. После освобождения места высокоприоритетный под планируется.
  5. **Preemption respects graceful termination, но не гарантирует соблюдение PodDisruptionBudget**.

- Ключевые поля PriorityClass
  - **`value`** (обязательное) — целое число, **чем больше, тем выше**. Диапазон: **-2,147,483,648 … 1,000,000,000** (32-bit signed, но значения >1 млрд зарезервированы за встроенными системными классами).
  - **`globalDefault`** (опционально) — если `true`, этот класс применяется к подам **без `priorityClassName`**. В кластере может быть **только один** такой класс.
  - **`description`** (опционально) — произвольная строка для документации: когда использовать класс.
  - **`preemptionPolicy`** (опционально) — `PreemptLowerPriority` (по умолчанию) или `Never` (не вытеснять других).

- Встроенные PriorityClass
  - Kubernetes уже содержит два класса для **критичных системных компонентов**:
    - **`system-cluster-critical`** — критичные для кластера add-on'ы (DNS, metrics-server, ingress и т.д.). Значение: **2,000,000,000**.
    - **`system-node-critical`** — **самый высокий** доступный приоритет, даже выше cluster-critical. Значение: **2,000,001,000**.
  - Поды с этими классами **гарантированно планируются первыми** и не должны вытесняться.
  - **Важно**: приоритет не предотвращает eviction полностью — он гарантирует, что под **будет пересоздан** и не останется навсегда недоступным.

- Пример PriorityClass
  ```yaml
  apiVersion: scheduling.k8s.io/v1
  kind: PriorityClass
  metadata:
    name: high-priority
  value: 1000000
  globalDefault: false
  description: "Для критичных сервисов (БД, ingress)"
  ```
  Применение к поду:
  ```yaml
  spec:
    priorityClassName: high-priority
    containers: ...
  ```

- PriorityClass vs QoS — не путать

| | PriorityClass | QoS |
|---|---|---|
| Как задаётся | **вручную** в `spec.priorityClassName` | **автоматически** по `requests`/`limits` |
| Кто использует | **scheduler** (порядок планирования, preemption) | **kubelet** (eviction при давлении, OOM score) |
| Когда срабатывает | когда под **не может быть запланирован** | когда нода **уже под давлением** ресурсов |
| Что делает | вытесняет низкоприоритетные поды, чтобы освободить место | выселяет поды с низким QoS при нехватке ресурсов на ноде |
| Учитывается ли при выборе жертв preemption | **Да** (только он) | **Нет** (QoS не учитывается в preemption) |
| Для БД | `high` + `Guaranteed` | `Guaranteed` (requests==limits) |
  - **Scheduler учитывает PriorityClass раньше, чем QoS**.
  - Обычно **используют вместе**: БД → PriorityClass `high` + QoS `Guaranteed`.

- Практические рекомендации
  - **Не создавать слишком много классов** — 3–5 достаточно (critical, high, normal, low, batch).
  - **Не давать `system-*` классы пользовательским подам** — только для системных add-on'ов.
  - **`globalDefault: true`** — удобно для дефолтного приоритета, но помнить: в кластере может быть **только один** такой класс.
  - **Preemption может «шуметь»**: вытесняемые поды перезапускаются, это может вызывать каскадные эффекты. Для batch-задач — рассмотреть `preemptionPolicy: Never` или низкий приоритет.
  - **Защита от злоупотреблений**: в недоверенном кластере пользователь может создать под с максимальным приоритетом и вытеснить всё. Использовать **ResourceQuota** и **RBAC**, чтобы ограничить, кто может создавать поды с высокими PriorityClass.
  - **Preemption не гарантирует PDB** — если критично, использовать `PodDisruptionBudget` для **добровольных** disruption'ов (drain), но preemption его **не соблюдает**.
  - **Мониторинг**: отслеживать события `Preempted`, `FailedScheduling` с указанием приоритета.

- Типичные ошибки
  - **Путать PriorityClass и QoS** — разные механизмы, работают на разных фазах.
  - **Задать `spec.priority` напрямую** — нельзя, только через `priorityClassName`.
  - **Дать всем подам `system-node-critical`** — тогда preemption не работает (все равны), и системные компоненты могут пострадать.
  - **Ожидать, что PriorityClass защитит от OOM killer** — нет, для этого нужен QoS `Guaranteed` и `limits` на память.
  - **`globalDefault: true` на нескольких классах** — ошибка валидации, только один.
  - **Preemption «убивает» stateful-поды** — если вытеснят БД с низким PriorityClass, она перезапустится. Для БД — высокий PriorityClass + Guaranteed QoS.
  - **Удаление PriorityClass** — существующие поды сохраняют приоритет, но новые с этим именем создать нельзя.

- Частые вопросы на собеседовании
  - **«Что такое PriorityClass?»** — Cluster-scoped объект, задающий целочисленный приоритет подам. Scheduler использует его для порядка планирования и preemption (вытеснения низкоприоритетных подов при нехватке места).
  - **«Как работает preemption?»** — Если под не может быть запланирован, scheduler ищет ноду, с которой можно вытеснить поды с более низким приоритетом (QoS не учитывается при выборе жертв), ждёт graceful termination, затем планирует под.
  - **«PriorityClass vs QoS?»** — PriorityClass — ручной приоритет для scheduler (preemption). QoS — автоматическая классификация для kubelet (eviction при давлении, OOM score). Работают на разных фазах, обычно вместе.
  - **«Какие встроенные PriorityClass?»** — `system-cluster-critical` (2 млрд) и `system-node-critical` (2,000,001,000 — самый высокий). Для системных add-on'ов.
  - **«Что такое `globalDefault`?»** — Класс по умолчанию для подов без `priorityClassName`. Только один такой класс в кластере.
  - **«Можно ли задать приоритет напрямую?»** — Нет, только через `spec.priorityClassName`, ссылающийся на PriorityClass.
  - **«Preemption и PodDisruptionBudget?»** — Preemption **не соблюдает** PDB, только graceful termination.
  - **«Как защититься от злоупотребления высокими приоритетами?»** — RBAC + ResourceQuota, ограничить, кто может создавать поды с высокими PriorityClass.
  - **«Что такое `preemptionPolicy: Never`?»** — Под с этим классом **не вытесняет** другие поды, даже если у него высокий приоритет (non-preempting).

- Короткий ответ на собеседовании
  - PriorityClass — это cluster-scoped объект, который задаёт целочисленный приоритет подам. Scheduler использует его для **порядка планирования** (высокоприоритетные поды впереди очереди) и **preemption**: если под не может быть запланирован, scheduler вытесняет поды с более низким приоритетом, чтобы освободить место. Preemption **не учитывает QoS** при выборе жертв — только PriorityClass. Два встроенных класса: `system-cluster-critical` и `system-node-critical` (самый высокий) — для системных компонентов. Поля: `value` (−2^31 … 1 млрд), `globalDefault` (только один в кластере), `description`, `preemptionPolicy` (`PreemptLowerPriority` или `Never`). **Не путать с QoS**: PriorityClass — ручной приоритет для scheduler (preemption), QoS — автоматическая классификация для kubelet (eviction при давлении на ноду, OOM score). Обычно используют вместе: БД → PriorityClass `high` + QoS `Guaranteed`. Preemption не гарантирует PDB, а злоупотребление высокими приоритетами ограничивается RBAC и ResourceQuota.

- Что запомнить железно
  - **PriorityClass — cluster-scoped**, задаёт **целое число** (выше = важнее).
  - **Scheduler использует для preemption**, QoS — **не учитывается** при выборе жертв.
  - **Preemption** = вытеснение низкоприоритетных подов, когда место не хватает.
  - **Два встроенных**: `system-cluster-critical`, `system-node-critical` (высший).
  - **`globalDefault`** — только один класс в кластере.
  - **`preemptionPolicy: Never`** — под не вытесняет других.
  - **PriorityClass ≠ QoS**: PriorityClass — scheduler/preemption, QoS — kubelet/eviction.
  - **Не задавать `spec.priority` напрямую** — только через `priorityClassName`.
  - **Preemption не соблюдает PDB**, только graceful termination.
  - **RBAC + ResourceQuota** — защита от злоупотребления приоритетами.
  - **Для БД**: `PriorityClass: high` + `QoS: Guaranteed`.

# Как CNPG управляет бд без StatefulSet?

- Ключевое архитектурное решение CloudNativePG (CNPG), которое объясняет, как он управляет базами данных без `StatefulSet`, — это реализация **собственного кастомного контроллера** для управления подами и хранилищем. 
- Вместо того чтобы полагаться на стандартный контроллер `StatefulSet`, CNPG берет на себя всю логику оркестрации, что дает ему гораздо более тонкий и точный контроль над каждым экземпляром PostgreSQL.

- Архитектура CNPG строится на взаимодействии двух основных частей:
  - 1.  **Кастомный контроллер (Operator)**: Это центральный "мозг" системы. Он работает как обычный под в Kubernetes и постоянно отслеживает (reconcile) состояние вашего кластера, описанное в ресурсе `Cluster`. Вместо делегирования задач `StatefulSet`, он **напрямую управляет** созданием, удалением и обновлением ресурсов `Pod` и `PersistentVolumeClaim` (PVC) для каждого экземпляра PostgreSQL.
  - 2.  **Instance Manager**: Это легковесный процесс, который работает **внутри каждого пода с PostgreSQL как PID 1**. Он не является сайдкаром. Именно он управляет жизненным циклом самого процесса `postgres`, обрабатывает сигналы, читает конфигурацию и предоставляет эндпоинты для проверок `liveness` и `readiness` для `kubelet`. Это позволяет CNPG отказаться от использования внешних инструментов для управления failover, таких как Patroni, и полагаться только на Kubernetes API.

- Отказ от `StatefulSet` в пользу прямого контроля дает несколько важных преимуществ, которые критичны для управления базами данных:
  - **Интеллектуальный Failover, основанный на данных, а не на порядковых номерах**: `StatefulSet` оперирует порядковыми номерами (pod-0, pod-1). CNPG же принимает решение о повышении реплики до роли `primary` на основе **Log Sequence Number (LSN)**, которую `Instance Manager` сообщает через Kubernetes API. Это гарантирует, что новый `primary` будет выбран как **наиболее актуальная реплика**, независимо от ее имени или индекса. Это обеспечивает более быстрый и предсказуемый failover.
  - **Гибкое управление версиями и параметрами**: `StatefulSet` обновляет все поды по порядку, не понимая их роли. CNPG, зная, кто является `primary`, а кто `replica`, может применять обновления или изменять параметры (например, `max_connections`) в правильном порядке. Например, сначала обновить реплики, затем повысить одну из них до `primary` и только потом обновить старый `primary`.
  - **Прямое управление хранилищем (PVC)**: `StatefulSet` имеет известные ограничения, например, не поддерживает изменение размера PVC. CNPG управляет PVC напрямую, что позволяет ему использовать возможности `StorageClass` для **изменения размера томов** «на лету» и обеспечивать согласованность данных при использовании нескольких PVC (например, для `PGDATA` и `WAL`).
  - **Более быстрое и предсказуемое восстановление**: Благодаря прямому контролю, CNPG может обеспечить более быстрое восстановление после сбоя. Повышение реплики до `primary` обычно занимает **менее 10 секунд**, в то время как решения на основе Patroni и `StatefulSet` могут требовать 30-60 секунд.

- CNPG не использует `StatefulSet`, потому что эта абстракция создана для универсальных stateful-приложений и не обладает нужным уровнем интеллекта для управления сложным кластером PostgreSQL. Реализуя собственный контроллер и внедряя `Instance Manager` в каждый под, CNPG получает **хирургический контроль** над каждым аспектом жизненного цикла базы данных, что позволяет ему обеспечивать более быстрый failover, гибкое управление обновлениями и эффективную работу с хранилищем.

# Kubernetes. Что такое StatefulSet?

- Что это
  - Контроллер для stateful-приложений (`apps/v1`, `kind: StatefulSet`).
  - Гарантирует **стабильную идентичность** каждого пода: имя, DNS, хранилище.
  - В отличие от Deployment, поды **не взаимозаменяемы** — `pg-0` ≠ `pg-1`.
  - Управляет подами **по порядку**: создаёт 0 → 1 → 2, удаляет 2 → 1 → 0.
  - **Не решает** failover, репликацию, бэкапы — это задача Оператора (CNPG, Percona, Zalando).
  - **Stable** с Kubernetes v1.9.

- Три гарантии StatefulSet
  - **Стабильное сетевое имя**: `pg-0`, `pg-1`, `pg-2` — не меняются при пересоздании.
  - **Стабильный DNS**: `pg-0.pg.default.svc.cluster.local` через **headless Service**.
  - **Стабильное хранилище**: у каждого пода **свой PVC** (`data-pg-0`, `data-pg-1`), который переживает пересоздание пода и привязан к нему по имени.

- Ключевые поля
  - **`serviceName`** (обязательное) — имя **headless Service** (`clusterIP: None`), который даёт DNS-имена подам. Без него StatefulSet не работает как ожидается.
  - **`replicas`** — количество подов.
  - **`selector`** — по каким labels находить поды (иммутабелен, должен совпадать с `template.metadata.labels`).
  - **`template`** — шаблон пода (как в Deployment).
  - **`volumeClaimTemplates`** — шаблон PVC, из которого создаётся **свой PVC на каждый под** (`data-pg-0`, `data-pg-1`, ...).
  - **`podManagementPolicy`** — `OrderedReady` (по умолчанию) или `Parallel`.
  - **`updateStrategy`** — `RollingUpdate` (по умолчанию) или `OnDelete`.
  - **`revisionHistoryLimit`** — сколько ревизий хранить (default 10).
  - **`persistentVolumeClaimRetentionPolicy`** (K8s 1.27+, stable 1.32) — удалять ли PVC при удалении пода/StatefulSet.

- Порядок создания и удаления (OrderedReady)
  - **Создание**: строго по порядку `0 → 1 → 2`. Под `N+1` создаётся **только когда под `N` стал `Ready`**.
  - **Удаление**: строго в обратном порядке `2 → 1 → 0`.
  - **Rolling update**: обновляет поды в обратном порядке (с наибольшего номера), по одному, ждёт `Ready`.
  - **Зачем**: для кластеров с quorum (Zookeeper, etcd, Kafka) — нельзя поднимать всех одновременно, иначе не будет кворума.
  - **`podManagementPolicy: Parallel`** — создаёт/удаляет все поды одновременно, без ожидания `Ready`. Для приложений, где порядок не важен, но нужна идентичность (например, некоторые кэши).

  - **`clusterIP: None`** — Service не имеет виртуального IP, DNS возвращает **IP подов напрямую**.
  - DNS-имена:
    - `pg-0.pg.default.svc.cluster.local` — конкретный под.
    - `pg.default.svc.cluster.local` — все поды (round-robin на уровне DNS).
  - **Зачем**: StatefulSet использует `serviceName`, чтобы дать каждому поду **уникальное DNS-имя**. Приложение (или Оператор) может обращаться к конкретному поду (`pg-0` — primary, `pg-1` — replica).
  - **Без headless Service** StatefulSet создастся, но DNS-идентичности не будет — pods будут видны только по IP, которые меняются.
  - Для каждого пода создаётся **свой PVC**: `data-pg-0`, `data-pg-1`, `data-pg-2`.
  - PVC **привязан к поду по имени** — при пересоздании пода `pg-0` он монтирует **тот же** `data-pg-0`.
  - **PVC не удаляются** при удалении пода или scale down — данные сохраняются.
  - **При удалении StatefulSet** PVC **тоже остаются** (по умолчанию) — нужно чистить вручную или через `persistentVolumeClaimRetentionPolicy: Delete`.
  - **Resize PVC**: если StorageClass `allowVolumeExpansion: true`, можно увеличить размер PVC, но **не уменьшить**.
  - **`volumeBindingMode: WaitForFirstConsumer`** — обязательно для multi-AZ (EBS, GCE PD, local PV), иначе PV создастся в одной AZ, а под запланируется в другой.

- Пример StatefulSet
  ```yaml
  apiVersion: apps/v1
  kind: StatefulSet
  metadata:
    name: pg
  spec:
    serviceName: pg
    replicas: 3
    selector:
      matchLabels:
        app: postgres
    template:
      metadata:
        labels:
          app: postgres
      spec:
        containers:
        - name: postgres
          image: postgres:16
          ports:
          - containerPort: 5432
          volumeMounts:
          - name: data
            mountPath: /var/lib/postgresql/data
    volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: fast
        resources:
          requests:
            storage: 100Gi
  ```

- StatefulSet vs Deployment

| | StatefulSet | Deployment |
|---|---|---|
| Имена подов | стабильные (`pg-0`, `pg-1`) | случайные (`pg-7d4b9c8f5-abcde`) |
| DNS | стабильный per-pod через headless Service | общий Service (ClusterIP) |
| Хранилище | свой PVC на под, переживает пересоздание | общий PVC или вообще без |
| Порядок создания/удаления | строгий (OrderedReady) | параллельный |
| Rolling update | по одному, в обратном порядке, ждёт Ready | maxSurge/maxUnavailable, параллельно |
| Идентичность | под = конкретный экземпляр (primary/replica) | поды взаимозаменяемы |
| Для чего | БД, Kafka, Zookeeper, Elasticsearch | stateless-сервисы, web, API |
| Failover/репликация | **не решает** — нужен Оператор | не применимо |

- StatefulSet vs Оператор
  - **StatefulSet** даёт: имена, DNS, PVC, порядок.
  - **StatefulSet не даёт**: автоматический failover, репликацию, бэкапы, PITR, выбор primary, обновления версий БД.
  - **Оператор** (CNPG, Percona, Zalando, Crunchy) **оборачивает** StatefulSet (или управляет подами напрямую, как CNPG) и добавляет логику эксплуатации.
  - **Правило**: для БД в проде — **Оператор**, а не «голый» StatefulSet.
  - **CNPG** вообще **не использует StatefulSet** — управляет подами и PVC напрямую через свой контроллер + instance manager в поде.

- `podManagementPolicy`
  - **`OrderedReady`** (default) — строгий порядок: создаёт `0 → 1 → 2`, ждёт `Ready` перед следующим. Удаляет `2 → 1 → 0`.
  - **`Parallel`** — все поды создаются/удаляются одновременно, без ожидания `Ready`. Быстрее, но нет гарантий порядка.
  - **Когда `Parallel`**: приложения, где порядок не важен, но нужна идентичность (например, кэши, некоторые worker'ы).
  - **Когда `OrderedReady`**: quorum-based (Zookeeper, etcd, Kafka), БД с primary/replica.

- `updateStrategy`
  - **`RollingUpdate`** (default) — обновляет поды по одному, в обратном порядке (`2 → 1 → 0`), ждёт `Ready` перед следующим.
  - **`OnDelete`** — не обновляет автоматически; новый под создаётся только когда старый **удалён вручную**. Для ручного контроля (например, БД, где обновление требует orchestration).
  - **`partition`** (в RollingUpdate) — обновлять только поды с номером `>= partition` (canary-подход).

- `persistentVolumeClaimRetentionPolicy` (K8s 1.27+ beta, stable 1.32)
  ```yaml
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain   # при удалении StatefulSet
    whenScaled: Retain    # при scale down
  ```
  - **`Retain`** (default) — PVC остаются (данные сохраняются).
  - **`Delete`** — PVC удаляются вместе с подом/StatefulSet.
  - **Осторожно с `Delete`**: данные теряются. Для прода с БД — `Retain`.

- Типичные проблемы и подводные камни
  - **Забыли `serviceName` / headless Service** → нет стабильного DNS, Оператор не может найти поды по имени.
  - **`podManagementPolicy: OrderedReady` + под не становится `Ready`** → весь StatefulSet застревает (например, `pg-1` не поднялся → `pg-2` не создаётся).
  - **Readiness probe критична**: без неё StatefulSet считает под готовым сразу после запуска и идёт дальше — можно получить неготовый кластер.
  - **PVC не удаляются при удалении StatefulSet** → «висящие» PVC, занимают место. Чистить вручную или `persistentVolumeClaimRetentionPolicy`.
  - **PVC не удаляются при scale down** → scale down с 5 до 3 оставляет `data-pg-3`, `data-pg-4`. При scale up обратно — они переиспользуются.
  - **Resize PVC только вверх** — уменьшить нельзя.
  - **`volumeBindingMode: Immediate` + multi-AZ** → PV в одной AZ, под в другой → Pending. Нужен `WaitForFirstConsumer`.
  - **StatefulSet не делает failover** — при падении `pg-0` (primary) никто не назначит нового primary. Нужен Оператор.
  - **`OrderedReady` + rolling update** → обновление идёт с последнего пода, но если `pg-2` не поднялся, `pg-1` и `pg-0` не обновятся.
  - **`selector` иммутабелен** — нельзя поменять после создания.
  - **`commonLabels` в Kustomize** может сломать `selector` — использовать `labels`.

- Частые вопросы на собеседовании
  - **«Что такое StatefulSet?»** — Контроллер для stateful-приложений, даёт стабильные имена, DNS и PVC на каждый под, упорядоченный жизненный цикл.
  - **«StatefulSet vs Deployment?»** — StatefulSet: стабильные имена/DNS/PVC, порядок, поды не взаимозаменяемы. Deployment: случайные имена, общий Service, поды взаимозаменяемы, для stateless.
  - **«Зачем headless Service?»** — Даёт стабильные DNS-имена подам (`pg-0.pg.default.svc.cluster.local`), чтобы можно было обращаться к конкретному экземпляру. Без него StatefulSet не даёт сетевой идентичности.
  - **«Что такое `volumeClaimTemplates`?»** — Шаблон PVC, из которого создаётся **свой PVC на каждый под** (`data-pg-0`, `data-pg-1`). PVC привязан к поду по имени, переживает пересоздание.
  - **«Что происходит с PVC при удалении StatefulSet?»** — По умолчанию **остаются** (Retain). Удаляются только при `persistentVolumeClaimRetentionPolicy: Delete`.
  - **«`OrderedReady` vs `Parallel`?»** — OrderedReady: строгий порядок (0→1→2), ждёт Ready. Parallel: все сразу, для приложений без порядка.
  - **«Делает ли StatefulSet failover?»** — **Нет**. StatefulSet только даёт идентичность. Failover, репликацию, бэкапы делает Оператор (CNPG, Percona, Zalando).
  - **«Можно ли использовать StatefulSet для БД в проде?»** — Технически да, но нужен Оператор сверху. «Голый» StatefulSet не решает failover и бэкапы.
  - **«Что такое `persistentVolumeClaimRetentionPolicy`?»** — Управляет удалением PVC при удалении StatefulSet или scale down. `Retain` (default) или `Delete`.
  - **«Почему StatefulSet обновляет поды в обратном порядке?»** — Чтобы не потерять quorum и primary: сначала обновляются реплики, потом (если нужно) primary через orchestration Оператора.
  - **«CNPG использует StatefulSet?»** — **Нет**, CNPG управляет подами и PVC напрямую через свой контроллер + instance manager. StatefulSet не даёт нужного контроля для failover по LSN.

- Короткий ответ на собеседовании
  - StatefulSet — это контроллер Kubernetes для stateful-приложений. Он даёт три гарантии: стабильные имена подов (`pg-0`, `pg-1`), стабильный DNS через headless Service (`pg-0.pg.default.svc.cluster.local`) и стабильное хранилище — свой PVC на каждый под через `volumeClaimTemplates`, который переживает пересоздание пода. Поды управляются в строгом порядке (`OrderedReady`: 0→1→2, ждёт Ready), обновляются по одному в обратном порядке. В отличие от Deployment, поды не взаимозаменяемы — `pg-0` и `pg-1` имеют разную идентичность. StatefulSet **не решает** failover, репликацию, бэкапы, PITR — для этого нужен **Оператор** (CNPG, Percona, Zalando, Crunchy), который оборачивает StatefulSet (или управляет подами напрямую, как CNPG). `podManagementPolicy: Parallel` — для приложений без порядка. `persistentVolumeClaimRetentionPolicy` управляет удалением PVC при удалении StatefulSet или scale down. Типичные ловушки: забыли headless Service, `OrderedReady` + под не Ready → весь StatefulSet застревает, PVC остаются после удаления, `volumeBindingMode: Immediate` + multi-AZ → Pending, resize PVC только вверх.

- Что запомнить железно
  - **StatefulSet = стабильные имена + DNS + PVC на под + порядок**.
  - **Headless Service (`clusterIP: None`) обязателен** для DNS-идентичности.
  - **`volumeClaimTemplates`** → свой PVC на каждый под (`data-pg-0`).
  - **PVC переживают пересоздание пода**, по умолчанию **не удаляются** с StatefulSet.
  - **`OrderedReady`** (default): 0→1→2, ждёт Ready. **`Parallel`** — все сразу.
  - **Rolling update** — по одному, в обратном порядке.
  - **StatefulSet не делает failover** — для этого Оператор.
  - **`persistentVolumeClaimRetentionPolicy`** (1.27+): `Retain` (default) или `Delete`.
  - **Readiness probe критична** — без неё StatefulSet идёт дальше с неготовым подом.
  - **`volumeBindingMode: WaitForFirstConsumer`** — для multi-AZ.
  - **Resize PVC только вверх**, при `allowVolumeExpansion: true`.
  - **CNPG не использует StatefulSet** — управляет подами напрямую.

# Kubernetes. Что такое ResourceQuota?

- Что это
  - **Объект API** (`v1`), который применяется в масштабе **namespace**.
  - Задаёт **совокупные ограничения** на все поды, сервисы, PVC и другие объекты в этом namespace.
  - Работает как **admission-контроллер**: проверяет запросы на создание/обновление ресурсов и **отклоняет** их (HTTP 403), если они превышают лимит.
  - **Не влияет на уже созданные** ресурсы: если вы уменьшили квоту, существующие поды продолжат работать (пока не будут пересозданы).
  - Feature state: **Stable** (включён по умолчанию во многих дистрибутивах).

- Зачем нужен
  - **Справедливое распределение**:防止 одна команда или приложение займёт все ресурсы кластера.
  - **Мультитенантность**: безопасно делить кластер между командами/проектами, давая каждой свой namespace с бюджетом.
  - **Защита от «шумных соседей»**: ограничивает, сколько суммарно CPU, памяти, диска и объектов может создать namespace.
  - **Контроль затрат**: в облаке помогает не выйти за бюджет, ограничивая количество дорогих ресурсов (например, `LoadBalancer` сервисов).

- Что можно ограничивать (ключи в `spec.hard`)
  - **Вычислительные ресурсы** (суммарно по всем подам):
    - `requests.cpu`, `limits.cpu`
    - `requests.memory`, `limits.memory`
    - `requests.ephemeral-storage`, `limits.ephemeral-storage`
    - `requests.nvidia.com/gpu` (и другие GPU)
  - **Хранилище**:
    - `requests.storage` — суммарный объём PVC
    - `persistentvolumeclaims` — количество PVC
  - **Количество объектов** (по API kind):
    - `pods`, `services`, `configmaps`, `secrets`, `replicationcontrollers`, `resourcequotas`
    - `count/deployments.apps`, `count/statefulsets.apps`, `count/jobs.batch` и т.д.
    - `services.loadbalancers`, `services.nodeports` — отдельно по типам сервисов
  - **Пример квоты**:
    ```yaml
    apiVersion: v1
    kind: ResourceQuota
    metadata:
      name: team-a-quota
      namespace: team-a
    spec:
      hard:
        requests.cpu: "10"
        requests.memory: 20Gi
        limits.cpu: "20"
        limits.memory: 40Gi
        pods: "50"
        services: "10"
        persistentvolumeclaims: "5"
        requests.storage: 100Gi
    ```

- Как это работает
  - **При создании** объекта (пода, PVC, сервиса) API-сервер проверяет, не превысит ли новый объект лимиты, заданные в ResourceQuota.
  - **Если превышает** — запрос отклоняется с **HTTP 403 Forbidden** и сообщением, какое ограничение нарушено.
  - **Квота учитывает `requests` и `limits`**, указанные в поде. Поэтому, если в namespace включена квота на CPU/память, **каждый под обязан иметь `requests` и `limits`** для этих ресурсов, иначе он не будет создан.
  - **LimitRange** решает эту проблему: он может автоматически проставлять дефолтные `requests`/`limits`, чтобы поды не отклонялись из-за их отсутствия.

- ResourceQuota vs LimitRange (частый вопрос на собеседовании)

| | **ResourceQuota** | **LimitRange** |
|---|---|---|
| **Уровень** | Весь namespace (суммарно) | Отдельный под/контейнер |
| **Что ограничивает** | Общее потребление CPU/памяти/диска и количество объектов | Минимальные/максимальные `requests` и `limits` для одного контейнера, а также дефолтные значения |
| **Когда срабатывает** | При создании/обновлении объекта, если суммарное потребление превышает лимит | При создании/обновлении пода/контейнера, если его `requests`/`limits` выходят за рамки min/max или не заданы (тогда подставляются дефолты) |
| **Цель** | Соблюдение бюджета namespace | Защита от «слишком маленьких» или «слишком больших» контейнеров и заполнение пропущенных ресурсов |
| **Взаимодействие** | Часто используется **вместе** с LimitRange, чтобы все поды имели явные `requests`/`limits` и квота могла их учитывать |

- Плюсы
  - **Простота**: один YAML-объект на namespace.
  - **Гибкость**: можно ограничивать как суммарные ресурсы, так и количество объектов по типам.
  - **Мультитенантность**: основа для безопасного shared-кластера.
  - **Интеграция с admission**: работает автоматически, не требует изменений в приложениях.

- Минусы и подводные камни
  - **Не влияет на уже запущенные поды**: если уменьшить квоту, существующие поды не будут выселены, но новые создать не получится.
  - **Требует явных `requests`/`limits`**: если в namespace включена квота на CPU/память, поды без этих полей будут отклонены.
  - **Не заменяет мониторинг**: квота — это жёсткий лимит, а не рекомендация; при неправильных значениях можно заблокировать создание нужных подов.
  - **Конкуренция за ресурсы**: если суммарные квоты всех namespace превышают容量 кластера, при одновременном пике ресурсы могут не достаться всем (работает принцип «первый пришёл — первый получил»).
  - **`count/*` квоты** не учитывают поды, созданные контроллерами (Deployment, StatefulSet), — они считают объекты API, а не фактические поды.

- `scopes` — дополнительные области действия
  - ResourceQuota можно ограничить определёнными **классами приоритета** или **QoS**:
    - `scope: PriorityClass` — квота только для подов с определённым `priorityClassName`.
    - `scope: BestEffort`, `scope: NotBestEffort` — квота для подов с определённым QoS.
  - Позволяет, например, задать отдельный бюджет для критичных (Guaranteed) и для batch (BestEffort) нагрузок.

- Частые вопросы на собеседовании
  - **«Что такое ResourceQuota?»** — Объект, ограничивающий **суммарное** потребление ресурсов (CPU, память, хранилище) и количество объектов в рамках **namespace**.
  - **«Чем отличается от LimitRange?»** — ResourceQuota — **суммарный** лимит на namespace. LimitRange — лимиты на **каждый отдельный** контейнер/под (min/max/default).
  - **«Что происходит при превышении квоты?»** — API-сервер отклоняет запрос с **HTTP 403 Forbidden** и сообщением о нарушенном ограничении.
  - **«Влияет ли изменение квоты на существующие поды?»** — **Нет**, существующие поды продолжают работать. Квота проверяется только при создании/обновлении объектов.
  - **«Почему под не создаётся, хотя квота не превышена?»** — Возможно, в namespace включена квота на CPU/память, а в поде не заданы `requests`/`limits`. Нужно добавить их или настроить LimitRange для дефолтов.
  - **«Можно ли ограничить количество LoadBalancer-сервисов?»** — Да, через `services.loadbalancers` в `spec.hard`.
  - **«Что такое `scopes` в ResourceQuota?»** — Позволяют применять квоту только к подам с определённым PriorityClass или QoS (например, только к BestEffort).

- Короткий ответ на собеседовании
  - ResourceQuota — это объект Kubernetes, который задаёт **жёсткие лимиты на совокупное потребление ресурсов и количество объектов в рамках одного namespace**. Он работает как admission-контроллер: если создание или обновление ресурса превышает квоту, API-сервер отклоняет запрос с ошибкой 403 Forbidden. ResourceQuota ограничивает суммарные `requests`/`limits` CPU и памяти, объём хранилища, количество подов, сервисов, PVC, ConfigMap и т.д. Важно не путать его с **LimitRange**: ResourceQuota управляет бюджетом всего namespace, а LimitRange — ограничениями на каждый отдельный контейнер (min/max/default). Обычно их используют вместе: LimitRange проставляет дефолтные `requests`/`limits` контейнерам, чтобы ResourceQuota мог корректно учитывать их сумму. ResourceQuota не влияет на уже созданные поды, но блокирует создание новых, если они превышают лимит.

- Что запомнить железно
  - **ResourceQuota — это бюджет namespace**, а не отдельного контейнера.
  - **Ограничивает сумму** CPU, памяти, хранилища и **количество** объектов.
  - **При превышении — 403 Forbidden** при создании/обновлении.
  - **Не влияет на уже запущенные поды**.
  - **Требует явных `requests`/`limits`** у подов, если квота на CPU/память включена.
  - **LimitRange дополняет** ResourceQuota: задаёт дефолты и min/max для контейнеров.
  - **Проверка**: `kubectl get resourcequota -n <namespace>`.

# Что такое Data Plane, Control Plane, Management Plane?

Data Plane (плоскость данных) — это одна из трёх фундаментальных логических плоскостей в архитектуре сетей и распределённых систем. Если Control Plane — это «мозг», который принимает решения и строит логику, то Data Plane — это «руки», которые эту логику исполняют, напрямую обрабатывая и передавая пользовательский трафик.

- **Data Plane (Плоскость данных, также User Plane / Forwarding Plane)**
  - **Что это**: Совокупность всех процессов и механизмов, которые **непосредственно обрабатывают и пересылают пакеты данных** от источника к получателю.
  - **Основная задача**: Реализация решений, принятых Control Plane. Data Plane **зависит** от Control Plane, который программирует правила (например, таблицы маршрутизации).
  - **Ключевая характеристика**: Работает с **каждым отдельным пакетом** в реальном времени. Скорость и пропускная способность здесь критичны.
  - **Примеры в Kubernetes**: 
    - **CNI-плагины** (Calico, Cilium, Flannel), которые настраивают сеть для подов.
    - **kube-proxy** (в режиме iptables/IPVS), который реализует правила Service на каждой ноде.
    - **Envoy** (sidecar-прокси), который непосредственно обрабатывает и маршрутизирует запросы между подами.
  - **Аналогия**: Курьер, который физически везёт посылку по адресу, указанному диспетчером.

- **Control Plane (Плоскость управления)**
  - **Что это**: «Мозг» системы, который **создаёт логику и программирует действия** для Data Plane.
  - **Основная задача**: Принимать решения о том, **куда и как** должен направляться трафик. Строит таблицы маршрутизации, вычисляет оптимальные пути.
  - **Ключевая характеристика**: Работает медленнее Data Plane, но выполняет сложные вычисления и координирует работу множества устройств.
  - **Примеры в Kubernetes**: 
    - **kube-apiserver**, **etcd**, **kube-scheduler**, **kube-controller-manager** — компоненты, которые хранят состояние кластера и принимают решения о размещении подов.
    - **istiod** (в Istio) — control plane для service mesh, который раздаёт конфигурацию Envoy-прокси.
  - **Аналогия**: Диспетчер, который прокладывает маршрут и говорит курьеру, куда ехать.

- **Management Plane (Плоскость администрирования)**
  - **Что это**: Плоскость, которая **настраивает, мониторит и обслуживает** саму сеть и устройства, на которых работают Control и Data Plane.
  - **Основная задача**: Управление конфигурацией, мониторинг состояния, сбор логов и телеметрии, обновление ПО. Это «плоскость для администраторов», а не для пользовательского трафика.
  - **Ключевая характеристика**: Работает с **состоянием устройств и сети в целом**, а не с отдельными пакетами или маршрутами.
  - **Примеры в Kubernetes**: 
    - **kubectl**, **Helm**, **Kustomize**, **ArgoCD/Flux** — инструменты, через которые администраторы и CI/CD применяют конфигурацию.
    - **Prometheus**, **Grafana**, **Loki** — системы мониторинга и логирования.
    - **Velero** — резервное копирование состояния кластера.
  - **Аналогия**: Начальник склада, который следит за исправностью транспорта, закупает новый транспорт и ведёт учёт, но сам посылки не возит.

- **Другие плоскости (расширения и уточнения)**
  - **Application Plane (Плоскость приложений)**: В некоторых архитектурах (например, в телеком-сетях) выделяют плоскость, которая предоставляет высокоуровневые функции для конкретных доменов (например, обработка голоса, видео), опираясь на сервисы, предоставляемые нижними плоскостями.
  - **Service Plane (Плоскость сервисов)**: Промежуточный уровень между Application и Data Plane, который отвечает за предоставление и поддержание состояния сервисов для пользователей.
  - **Security Plane (Плоскость безопасности)**: В некоторых фреймворках (например, ITU-T X.805) выделяют плоскости безопасности (Management, Control, User), которые применяются к соответствующим слоям для обеспечения защиты.

- **Короткий ответ на собеседовании**
  - В архитектуре сетей и распределённых систем выделяют три основные плоскости. **Data Plane** — это «руки», которые непосредственно пересылают пакеты данных, исполняя правила. **Control Plane** — это «мозг», который эти правила создаёт и программирует (например, вычисляет маршруты). **Management Plane** — это «администратор», который настраивает, мониторит и обслуживает саму систему, но не участвует в передаче пользовательского трафика. В Kubernetes Data Plane — это CNI (Calico/Cilium) и kube-proxy, Control Plane — это kube-apiserver, scheduler, controller-manager и etcd, а Management Plane — это kubectl, Helm, ArgoCD и системы мониторинга.

- **Что запомнить железно**
  - **Data Plane** = пересылка пакетов (скорость, пропускная способность). **Control Plane** = принятие решений (логика, маршруты). **Management Plane** = настройка и мониторинг (администрирование).
  - Data Plane **зависит** от Control Plane.
  - В Kubernetes Data Plane — это **CNI** и **kube-proxy**, Control Plane — это **kube-apiserver**, **etcd**, **scheduler**, **controller-manager**.
  - Management Plane — это инструменты вроде **kubectl**, **Helm**, **ArgoCD**, **Prometheus**.

# Kubernetes. Что такое commonLabels?

`commonLabels` — это поле в файле `kustomization.yaml` (инструмент Kustomize), которое позволяет добавить набор меток (labels) ко **всем** ресурсам, генерируемым данной конфигурацией. Его ключевая особенность и одновременно источник основных проблем в том, что он добавляет эти метки не только в `metadata.labels`, но и в **селекторы** (`spec.selector`) таких ресурсов, как Deployment и Service.

- **Что это и как работает**
  - **Назначение**: Добавить одинаковый набор меток (например, `app: myapp`, `owner: alice`, `environment: prod`) ко всем манифестам, которые создаются или изменяются с помощью Kustomize.
  - **Ключевая особенность**: В отличие от обычных меток, `commonLabels` **автоматически проникает в селекторы** (`.spec.selector`) ресурсов, которые их используют (Deployment, Service, DaemonSet и т.д.). Это гарантирует, что селектор Service будет соответствовать меткам Pod'ов, созданных Deployment'ом.
  - **Пример**: Если в `kustomization.yaml` указать `commonLabels: {app: bingo}`, то в итоговом манифесте Deployment метка `app: bingo` появится и в `metadata.labels`, и в `spec.selector.matchLabels`, и в `spec.template.metadata.labels`.

- **Главная проблема и причина устаревания**
  - Поле `commonLabels` было **признано устаревшим (deprecated) начиная с Kustomize v5.0.0**.
  - Причина в том, что **селекторы (`.spec.selector`) в таких ресурсах, как Deployment и Service, являются неизменяемыми (immutable)** после создания ресурса в кластере. Если вы добавите новый `commonLabel` к уже работающему Deployment, Kustomize попытается изменить его `spec.selector`, что приведет к ошибке при `kubectl apply`.
  - Именно из-за этого риска сломать существующие ресурсы и было введено новое, более гибкое поле `labels`.

- **Замена: поле `labels`**
  - На смену `commonLabels` пришло поле `labels` с более тонкими настройками. Оно позволяет контролировать, куда именно будут добавляться метки.
  - **`includeSelectors: true`**: Это прямой аналог `commonLabels`. Метки добавляются в `metadata.labels`, в селекторы и в шаблон Pod'а. **Использовать с осторожностью** на существующих ресурсах, так как это меняет неизменяемый селектор.
  - **`includeSelectors: false` (по умолчанию)**: Безопасный режим. Метки добавляются **только** в `metadata.labels`, не затрагивая селекторы. Это идеальный вариант для добавления информационных меток (например, `owner`, `cost-center`).
  - **`includeTemplates: true`**: Добавляет метки в `metadata.labels` и в `spec.template.metadata.labels` (метки Pod'ов), но **не трогает селекторы**. Полезно, чтобы метки попали на поды, но при этом не сломать неизменяемый селектор.

- **Короткий ответ на собеседовании**
  - «`commonLabels` — это устаревшее поле в Kustomize, которое добавляет метки ко всем ресурсам и, что важно, автоматически проникает в их селекторы. Из-за того, что селекторы в Deployment и Service неизменяемы, использование `commonLabels` на уже работающих ресурсах может привести к ошибкам. Начиная с Kustomize v5.0.0 его рекомендовано заменить на поле `labels`. Новое поле `labels` безопаснее, так как по умолчанию добавляет метки только в `metadata.labels`, не затрагивая селекторы, а для эмуляции старого поведения нужно явно указать `includeSelectors: true`».

- **Что запомнить железно**
  - **`commonLabels`** — добавляет метки **и в `metadata.labels`, и в селекторы** (`spec.selector`).
  - **Устарел (deprecated) в Kustomize v5.0.0**.
  - **Риск**: изменение селектора у существующего Deployment — **ошибка**, так как селектор неизменяем.
  - **Замена**: поле **`labels`**.
  - **Безопасный режим**: `labels` с `includeSelectors: false` (по умолчанию) — меняет только `metadata.labels`.
  - **Полный аналог**: `labels` с `includeSelectors: true` — ведёт себя как `commonLabels`.

# Kubernetes. Что такое RDS?

В контексте Kubernetes «RDS» — это не компонент самого Kubernetes, а внешний управляемый сервис баз данных от AWS (Amazon Relational Database Service). Проще говоря, это способ вынести stateful-нагрузку (базу данных) из кластера и переложить её эксплуатацию на плечи облачного провайдера.

📌 RDS — это не часть Kubernetes, а внешний сервис
- RDS предоставляет управляемые реляционные базы данных (PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, Aurora) как сервис. Вы не управляете сервером, на котором работает СУБД: AWS берёт на себя установку, патчинг, резервное копирование, репликацию и отказоустойчивость (Multi-AZ).
- В архитектуре с Kubernetes это выглядит так: приложение работает в подах, а база данных — в RDS, и поды подключаются к ней по сети через эндпоинт RDS. Это классический паттерн разделения stateless-приложений (в K8s) и stateful-данных (в managed-сервисе).

🔗 Как это связано с Kubernetes на практике

- Управлять RDS можно **декларативно прямо из Kubernetes**, не переключаясь в консоль AWS. Для этого есть два основных инструмента:
  - **AWS Controllers for Kubernetes (ACK)**: официальный проект AWS. Контроллер для RDS позволяет создавать, изменять, масштабировать и удалять инстансы RDS, а также управлять репликами и кластерами Aurora через Kubernetes-манифесты (CRD). Это «родной» способ для тех, кто уже плотно сидит в экосистеме AWS.
  - **Crossplane**: если вы используете его как универсальный control plane, провайдер `provider-aws` предоставляет Managed Resources для RDS (например, `RDSInstance` или `DBInstance`), позволяя управлять базами данных так же, как и другими облачными ресурсами.

⚖️ RDS vs База данных внутри Kubernetes
- Это ключевой архитектурный выбор, который часто обсуждается на собеседованиях.

| Критерий | База данных в Kubernetes (StatefulSet) | Amazon RDS |
| :--- | :--- | :--- |
| **Управление** | Вы (патчинг, бэкапы, failover) | AWS (managed-сервис) |
| **Операционная нагрузка** | Высокая | Низкая |
| **Гибкость настройки** | Полная | Ограничена возможностями RDS |
| **Стоимость** | Ресурсы кластера | Отдельная плата за сервис |
| **Когда выбирать** | Нужен полный контроль, on-prem, специфичные расширения | Нужно снизить операционные затраты, стандартная СУБД |

- По сути, RDS — это антоним «запуска СУБД в контейнере» в том смысле, что вы **сознательно отказываетесь** от управления базой в кластере в пользу готового сервиса.

💎 Короткий ответ на собеседовании

> «RDS — это Amazon Relational Database Service, управляемый сервис баз данных. В контексте Kubernetes это не компонент кластера, а внешняя managed-база, которую используют вместе с приложениями в подах, чтобы не эксплуатировать stateful-нагрузку самостоятельно. При этом управлять жизненным циклом RDS можно декларативно из Kubernetes — через AWS Controllers for Kubernetes (ACK) или Crossplane. Это архитектурный выбор в пользу снижения операционных затрат, в отличие от запуска СУБД в StatefulSet внутри кластера».

🎯 Что запомнить железно
- **RDS — это сервис AWS**, а не объект Kubernetes.
- **RDS = managed database**, снимает с вас бэкапы, патчинг и failover.
- **Управлять RDS из K8s** можно через **ACK** или **Crossplane**.
- Это **альтернатива** запуску СУБД в StatefulSet, а не дополнение к ней.

# Поэтапный процесс https соединения

Установка HTTPS-соединения — это многоэтапный процесс, который начинается с установления базового TCP-соединения и затем «оборачивает» его в защищённый TLS-туннель. Весь процесс можно разделить на три ключевые фазы: **TCP-рукопожатие**, **TLS-рукопожатие** и **Передача данных**.

📡 Фаза 1: TCP-рукопожатие (3-way Handshake)

Прежде чем клиент и сервер смогут обмениваться зашифрованными данными, они должны установить надёжное соединение на транспортном уровне. Для этого используется стандартное трёхстороннее рукопожатие TCP.

- **Шаг 1: SYN**: Клиент отправляет серверу пакет с флагом `SYN`, чтобы инициировать соединение (обычно на порт 443 для HTTPS).
- **Шаг 2: SYN-ACK**: Сервер отвечает пакетом с флагами `SYN` и `ACK`, подтверждая получение запроса клиента и предлагая своё соединение.
- **Шаг 3: ACK**: Клиент отправляет пакет с флагом `ACK`, подтверждая получение ответа сервера. На этом этапе TCP-соединение считается установленным.

🔐 Фаза 2: TLS-рукопожатие (TLS Handshake)

Это сердце HTTPS. Именно на этом этапе стороны договариваются о параметрах шифрования, аутентифицируют друг друга и безопасно обмениваются ключами для дальнейшей симметричной шифрации данных.

Процесс **TLS-рукопожатия** значительно различается в зависимости от версии протокола. Современный стандарт **TLS 1.3** быстрее и безопаснее, чем **TLS 1.2**.

#TLS 1.2: Классический подход (2 RTT)

В TLS 1.2 рукопожатие требует двух полных круговых задержек (Round-Trip Time, RTT) до начала передачи данных, что делает его медленнее.

1.  **ClientHello**: Клиент отправляет серверу сообщение, в котором указывает поддерживаемые версии TLS, наборы шифров (cipher suites), а также случайное число для генерации ключей.
2.  **ServerHello, Certificate, ServerKeyExchange, ServerHelloDone**: Сервер отвечает выбранным набором шифров, своим сертификатом (содержащим публичный ключ) и, при необходимости, параметрами для обмена ключами (например, для эфемерного Диффи-Хеллмана).
3.  **ClientKeyExchange, ChangeCipherSpec, Finished**: Клиент проверяет сертификат сервера. Затем он генерирует «предварительный мастер-секрет» (pre-master secret), шифрует его публичным ключом сервера и отправляет обратно. После этого обе стороны вычисляют общий «мастер-секрет» и сессионные ключи. Клиент отправляет сообщение `Finished`, подтверждая, что готов перейти на шифрованную связь.
4.  **ChangeCipherSpec, Finished (сервер)**: Сервер расшифровывает pre-master secret своим приватным ключом, также вычисляет сессионные ключи и отправляет свой `Finished`. С этого момента рукопожатие завершено, и можно передавать данные.

#TLS 1.3: Современный стандарт (1 RTT)

Главное преимущество TLS 1.3 — **сокращение рукопожатия до одного RTT**. Это достигается за счёт того, что клиент и сервер обмениваются параметрами для обмена ключами (`key_share`) уже в первых сообщениях, а весь процесс аутентификации и согласования происходит параллельно.

1.  **ClientHello + Key Share**: Клиент отправляет сообщение `ClientHello`, которое уже содержит его долю для обмена ключами (key share) и список поддерживаемых шифров.
2.  **ServerHello, EncryptedExtensions, Certificate, CertificateVerify, Finished**: Сервер, получив key share клиента, может сразу вычислить общий секрет. Он отправляет свой `ServerHello` со своей долей ключа, а затем в **зашифрованном виде** отправляет остальные сообщения: свой сертификат, подпись для его проверки (`CertificateVerify`) и своё сообщение `Finished`.
3.  **Finished (клиент) + HTTP-запрос**: Клиент проверяет сертификат и подпись сервера. Убедившись в подлинности, он вычисляет общий секрет и отправляет своё сообщение `Finished`. **Важно:** Клиент может отправить свой первый HTTP-запрос сразу после `Finished`, не дожидаясь подтверждения от сервера.

📨 Фаза 3: Передача данных

После успешного завершения TLS-рукопожатия устанавливается **сессия**, и все последующие данные (например, HTTP-запросы и ответы) шифруются с использованием согласованных **симметричных сессионных ключей**. Это означает, что содержимое трафика (URL, заголовки, cookies, тело запроса/ответа) надёжно защищено от перехвата и подмены.

💎 Итог

Таким образом, HTTPS-соединение — это результат последовательной работы двух протоколов. Сначала **TCP** обеспечивает надёжную доставку пакетов, а затем **TLS** «надстраивается» над ним, обеспечивая конфиденциальность и целостность передаваемых данных. Ключевое отличие современного **TLS 1.3** от предыдущих версий — в скорости и безопасности: он завершает рукопожатие за один RTT, в то время как **TLS 1.2** требует двух.

Keepalived — это программное обеспечение для Linux, которое решает две ключевые задачи сетевой инфраструктуры: **обеспечение высокой доступности (High Availability, HA)** и **балансировку нагрузки (Load Balancing)**. Его часто используют для создания отказоустойчивых шлюзов, балансировщиков и точек входа в кластеры.

### 🎯 Две главные функции Keepalived

Keepalived работает как единый демон, реализующий два независимых, но дополняющих друг друга фреймворка:

1.  **Высокая доступность (через VRRP)**: Это основная и самая известная функция. Keepalived реализует протокол **VRRP (Virtual Router Redundancy Protocol)**. Он позволяет группе серверов (например, два балансировщика) разделить один **виртуальный IP-адрес (VIP)**. Один сервер становится **MASTER** и владеет VIP, а остальные — **BACKUP** и находятся в режиме ожидания.
2.  **Балансировка нагрузки (через LVS/IPVS)**: Keepalived использует модуль ядра Linux **IPVS (IP Virtual Server)** для балансировки трафика на уровне L4 (TCP/UDP). Он управляет пулом реальных серверов и распределяет между ними входящие соединения.

### ⚙️ Как работает высокая доступность (VRRP)

Принцип работы VRRP в Keepalived строится на выборе лидера и периодических проверках его доступности:

*   **Выбор MASTER**: Каждому серверу в группе VRRP назначается **приоритет** (число). Сервер с наивысшим приоритетом становится MASTER и принимает на себя виртуальный IP-адрес. Если приоритеты равны, побеждает сервер с более высоким реальным IP-адресом.
*   **Мониторинг через анонсы**: MASTER периодически (по умолчанию раз в секунду) рассылает **VRRP-анонсы** (multicast-пакеты), сообщая всем остальным, что он жив.
*   **Failover (переключение)**: Если BACKUP-серверы не получают анонсы от MASTER в течение определённого времени (по умолчанию — три пропущенных анонса), они считают, что MASTER отказал. Тогда BACKUP с наивысшим приоритетом «захватывает» виртуальный IP-адрес и становится новым MASTER. Этот процесс происходит автоматически и незаметно для клиентов.

### ⚖️ Как работает балансировка нагрузки (LVS/IPVS)

Когда Keepalived используется как балансировщик, он управляет правилами для модуля IPVS в ядре. Он поддерживает несколько **методов пересылки (forwarding methods)**, которые определяют, как трафик доставляется до реальных серверов:

*   **NAT (Network Address Translation)**: Балансировщик работает как шлюз. Он принимает запрос, меняет IP-адрес назначения на адрес одного из реальных серверов и отправляет пакет. Ответ от реального сервера проходит обратно через балансировщик, который меняет IP-адрес отправителя на свой. Это универсальный, но более ресурсоёмкий режим, так как весь трафик идёт через балансировщик.
*   **DR (Direct Routing)**: Более производительный режим. Балансировщик меняет только MAC-адрес получателя в пакете на MAC-адрес выбранного реального сервера и отправляет его. Реальный сервер отвечает **напрямую** клиенту, минуя балансировщик. Это снижает нагрузку на балансировщик, но требует, чтобы все серверы находились в одном L2-сегменте.
*   **TUN (IP Tunneling)**: Используется для географически распределённых кластеров. Балансировщик инкапсулирует исходный пакет в новый IP-пакет и отправляет его реальному серверу, который может находиться в другой сети.

Также Keepalived выполняет **проверки работоспособности (health checks)** реальных серверов. Если сервер перестаёт отвечать, Keepalived автоматически исключает его из пула балансировки, и трафик на него больше не направляется.

### ☸️ Keepalived в контексте Kubernetes

В контексте Kubernetes Keepalived чаще всего используется для обеспечения высокой доступности **самого кластера** или его точек входа, особенно в средах **bare-metal (on-premise)**.

*   **Высокодоступный API Server**: Это классический сценарий. Несколько control-plane узлов (master) объединяются в VRRP-группу с помощью Keepalived. Они делят один виртуальный IP-адрес, который является конечной точкой для доступа к Kubernetes API (порт 6443). Если мастер-узел, владеющий VIP, выходит из строя, Keepalived автоматически переносит VIP на другой узел, обеспечивая непрерывный доступ к API.
*   **Балансировка нагрузки для Service типа LoadBalancer**: В облачных средах LoadBalancer предоставляется провайдером. В bare-metal для этого используют инструменты вроде **MetalLB** или **kube-vip**. Keepalived может быть частью такого решения, хотя существуют и более специализированные для K8s инструменты. Например, связка **HAProxy + Keepalived** — это популярный способ создать отказоустойчивый балансировщик для трафика, поступающего на узлы кластера.
*   **Сравнение с другими инструментами**: Важно понимать, что в K8s-мире есть альтернативы.
    *   **kube-vip** — это специализированный инструмент, который может обеспечивать VIP как для control-plane, так и для Service, используя механизмы выбора лидера на основе API Kubernetes, а не VRRP.
    *   **MetalLB** — это реализация LoadBalancer для bare-metal, которая также может использовать L2-режим (похожий на VRRP) или BGP.
    *   Keepalived, в свою очередь, работает независимо от API Kubernetes, что может быть преимуществом для обеспечения доступности самого API Server.

### 💎 Итог

Keepalived — это проверенный временем и очень гибкий инструмент. Он идеально подходит для создания отказоустойчивых шлюзов и балансировщиков в традиционных инфраструктурах и на bare-metal серверах. В контексте Kubernetes его основная ниша — обеспечение высокой доступности control-plane и создание точки входа в кластер, хотя для управления жизненным циклом Service в K8s существуют и более «родные» инструменты.

Если захотите углубиться в какой-то из аспектов, например, в настройку `keepalived.conf` или сравнение с `kube-vip`, дайте знать.

# CNI (Container Network Interface)

CNI — это **спецификация и набор плагинов** для настройки сети контейнеров в Linux. Когда kubelet создаёт под, он не «знает», как назначить IP, создать veth-пару, настроить маршруты и DNS — он делегирует это CNI-плагину. CNI — это **не один инструмент**, а **стандарт интерфейса** между оркестратором (Kubernetes, containerd, CRI-O, Podman) и сетевым плагином (Calico, Cilium, Flannel). Без CNI поды не получат IP и не смогут общаться. Важно не путать: **CNI — это про сеть подов** (L3/L4), а **Service и Ingress** — отдельные механизмы (kube-proxy, Ingress Controller), хотя Cilium умеет заменять и их.

- Что это
  - **Спецификация** (CNI spec, github.com/containernetworking/cni) — набор правил, как оркестратор вызывает плагин.
  - **Набор плагинов** — бинарники в `/opt/cni/bin/`, которые реализуют spec.
  - **Не демон и не сервис** — плагин вызывается **по требованию** (exec) при создании/удалении пода.
  - **Ответственность**: назначить IP поду, создать veth-пару, настроить маршруты, bridge, DNS, политики (если плагин умеет).
  - **Не отвечает** за: Service (ClusterIP), Ingress, NetworkPolicy (хотя многие CNI умеют), DNS (CoreDNS).
  - Спецификация: **CNI spec v1.0+** (стабильная), до этого 0.4.0.

- Зачем нужен
  - **Единый интерфейс**: kubelet не знает, какой CNI установлен — он вызывает плагин по спецификации.
  - **Плоская сеть подов**: каждый под получает уникальный IP, общается с любым подом без NAT.
  - **Сменяемость**: можно заменить Flannel на Calico или Cilium, не меняя Kubernetes.
  - **Разные сценарии**: overlay (VXLAN), routing (BGP), eBPF, cloud-native (AWS VPC CNI, Azure CNI).
  - **Расширяемость**: NetworkPolicy, encryption (WireGuard, IPsec), observability (Hubble в Cilium).

- Как работает (пошагово)
  1. Kubelet создаёт sandbox-контейнер (pause) и **network namespace** для пода.
  2. Kubelet читает конфиг CNI (`/etc/cni/net.d/*.conf`) — какой плагин использовать.
  3. Kubelet вызывает **CNI-бинарник** (`/opt/cni/bin/<plugin>`) с командами `ADD`, `DEL`, `CHECK`.
  4. Плагин через stdin получает JSON с параметрами: netns, имя интерфейса, IPAM-конфиг.
  5. Плагин:
     - создаёт **veth-пару** (один конец в netns пода, другой — в netns хоста или bridge);
     - через **IPAM-плагин** (`host-local`, `dhcp`, `calico-ipam`, `cilium`) выделяет IP;
     - настраивает маршруты, DNS (`/etc/resolv.conf`), bridge, iptables/nftables/eBPF.
  6. Плагин возвращает JSON с результатом: IP, MAC, gateway, DNS.
  7. Kubelet записывает результат в `Pod.status` (podIP).
  8. При удалении пода — `DEL` — плагин убирает интерфейсы, освобождает IP.

- Команды CNI (что вызывает kubelet)
  - **`ADD`** — создать сеть для пода, назначить IP.
  - **`DEL`** — удалить сеть, освободить IP.
  - **`CHECK`** — проверить состояние сети (опционально, CNI 0.4+).
  - **`GC`** — сборка мусора (CNI 1.0+, опционально).
  - **`VERSION`** — версия spec.

- Конфигурация CNI
  - **`/etc/cni/net.d/`** — конфиги (kubelet читает первый по алфавиту).
  - **`/opt/cni/bin/`** — бинарники плагинов.
  - **`/var/lib/cni/`** — состояние (IPAM, кэш).
  - **`/var/lib/calico/`, `/var/run/cilium/`** — состояние конкретных CNI.
  - Пример конфига (упрощённо):
    ```json
    {
      "cniVersion": "1.0.0",
      "name": "mynet",
      "type": "calico",
      "ipam": { "type": "calico-ipam" }
    }
    ```

- IPAM (IP Address Management)
  - **Что это**: подсистема, которая выделяет IP подам из пула.
  - **Плагины**:
    - **`host-local`** — простой, хранит состояние в файлах на ноде, статический пул.
    - **`dhcp`** — запрашивает IP по DHCP.
    - **`calico-ipam`** — выделяет из IP-пулов Calico (IPPool), поддерживает блоки на ноду.
    - **`cilium`** — свой IPAM (cluster-pool, kubernetes, multi-pool, ENI).
    - **`whereabouts`** — cluster-wide IPAM для multi-node (часто с Flannel/Multus).
  - **CIDR на ноду**: каждая нода получает свой **pod CIDR** (например, `/24` из `10.244.0.0/16`), из него выделяются IP подам.
  - **`--pod-network-cidr`** в `kubeadm init` — задаёт общий пул.

- Виды CNI по реализации

  - **Overlay (VXLAN, IP-in-IP)**
    - **Как работает**: пакет инкапсулируется в UDP/IP и идёт по underlay-сети. Ноды не обязаны быть в одном L2.
    - **Плюсы**: работает везде, не требует BGP, простой.
    - **Минусы**: overhead (инкапсуляция), MTU ниже (обычно 1450 вместо 1500), latency.
    - **Примеры**: **Flannel (VXLAN)**, **Weave Net**, **Calico (IP-in-IP, VXLAN)**, **Cilium (VXLAN, Geneve)**.

  - **Routing (BGP)**
    - **Как работает**: ноды анонсируют свои pod CIDR через BGP, пакеты идут напрямую без инкапсуляции.
    - **Плюсы**: нативная производительность, нет overhead, MTU 1500.
    - **Минусы**: требует поддержки BGP в сети (ToR-роутеры), сложнее в настройке.
    - **Примеры**: **Calico (BGP)**, **Cilium (BGP)**, **MetalLB (BGP)**.

  - **eBPF-based**
    - **Как работает**: eBPF-программы в ядре заменяют iptables/kube-proxy, обрабатывают пакеты быстрее, дают L7-observability.
    - **Плюсы**: производительность, L7 policy, observability (Hubble), замена kube-proxy.
    - **Минусы**: требует ядра 4.19+/5.x+, сложнее в отладке.
    - **Примеры**: **Cilium** (лидер), **Calico eBPF mode**.

  - **Cloud-native**
    - **Как работает**: CNI интегрируется с облачной сетью (VPC, ENI, IPAM облака).
    - **Плюсы**: нативная производительность, интеграция с security groups, VPC routing.
    - **Минусы**: vendor lock-in, лимиты облака (кол-во ENI, IP).
    - **Примеры**: **AWS VPC CNI** (по ENI на под), **Azure CNI**, **GKE CNI**.

  - **Host-local / bridge**
    - **Как работает**: bridge + host-local IPAM, простой.
    - **Плюсы**: просто, без зависимостей.
    - **Минусы**: только single-node, не для прода.
    - **Примеры**: **bridge**, **macvlan**, **host-device** (стандартные плагины).

- Популярные CNI-плагины

  - **Calico**
    - BGP или IP-in-IP/VXLAN, eBPF-режим.
    - **NetworkPolicy** — да (полноценно).
    - **Encryption** — WireGuard.
    - Используется в проде, enterprise-поддержка (Tigera).
    - Хорош для on-prem и cloud.

  - **Cilium**
    - eBPF-based, замена kube-proxy, L3/L4/L7 policy.
    - **NetworkPolicy** — да, плюс CiliumNetworkPolicy (L7: HTTP, Kafka, gRPC).
    - **Observability** — Hubble (UI, метрики, трейсы).
    - **Encryption** — WireGuard, IPsec.
    - **BGP** — да (с 1.13+), может заменить MetalLB.
    - Современный фаворит, CNCF Graduated.

  - **Flannel**
    - Простой overlay (VXLAN), host-local IPAM.
    - **NetworkPolicy — НЕТ** (в классическом виде).
    - **Encryption — нет** (кроме WireGuard-варианта).
    - Для простых кластеров, где не нужна изоляция.

  - **Weave Net**
    - Overlay, простой, но менее популярен сейчас.
    - NetworkPolicy — частично.
    - Проект фактически в maintenance mode.

  - **Antrea**
    - На Open vSwitch, NetworkPolicy, Windows-поддержка.
    - Разработка VMware.

  - **kubenet**
    - Встроенный в kubelet, простой bridge + host-local.
    - Не для прода (нет NetworkPolicy, нет overlay между нодами).

  - **Multus**
    - **Мета-плагин**: позволяет поду иметь **несколько сетевых интерфейсов** (например, management + data + storage).
    - Используется в NFV, telco, ML (RDMA), где нужны multiple networks.

  - **AWS VPC CNI**
    - Каждый под получает **ENI** (или secondary IP) из VPC.
    - Нативная производительность, но лимиты на кол-во ENI/IP на инстанс.
    - NetworkPolicy — только с Calico поверх (или VPC CNI network policy, с 1.20+).

- CNI и NetworkPolicy
  - **NetworkPolicy** — API-объект, но **реализует его CNI**.
  - **Поддерживают**: Calico, Cilium, Antrea, Weave (частично), AWS VPC CNI (с 1.20+).
  - **Не поддерживают**: Flannel (в классическом виде), kubenet.
  - Если CNI не поддерживает — политики **молча игнорируются** (опасная иллюзия безопасности).
  - Для L7 policy (HTTP-методы, пути) — только **Cilium** (CiliumNetworkPolicy).

- CNI и Service / kube-proxy
  - **CNI — про сеть подов** (L3/L4), **Service** — отдельный механизм (kube-proxy, iptables/IPVS).
  - **Cilium** может **заменить kube-proxy** полностью (eBPF), обрабатывая Service без iptables.
  - **Calico** в eBPF-режиме тоже может заменить kube-proxy (с 3.13+).
  - **Ingress** — отдельный слой (Ingress Controller), работает поверх Service.

- CNI и Service Mesh
  - **Service mesh** (Istio, Linkerd) — sidecar-прокси, работают **поверх** CNI.
  - **Cilium Service Mesh** — sidecar-less, на eBPF, встроен в CNI.
  - **Istio ambient mode** — ztunnel (L4) на ноде + waypoint (L7), тоже без sidecar.
  - CNI и mesh — **разные слои**, но пересекаются в eBPF-решениях.

- Плюсы CNI как подхода
  - **Стандарт**: единый интерфейс, сменяемость плагинов.
  - **Гибкость**: overlay, routing, eBPF, cloud-native — под разные задачи.
  - **Расширяемость**: NetworkPolicy, encryption, observability, multi-network (Multus).
  - **Экосистема**: Calico, Cilium, Flannel — зрелые, проверенные в проде.
  - **Не привязан к Kubernetes**: работает с Podman, containerd, Nomad.

- Минусы и подводные камни
  - **Не все CNI одинаковы**: Flannel без NetworkPolicy — частая ошибка (думают, что изоляция есть).
  - **MTU**: overlay уменьшает MTU (1450 вместо 1500), забыли — фрагментация, странные ошибки.
  - **BGP требует инфраструктуры**: ToR-роутеры должны поддерживать BGP, иначе routing не работает.
  - **eBPF требует ядра**: 4.19+/5.x+, не на всех дистрибутивах и managed-кластерах.
  - **Лимиты облака**: AWS VPC CNI ограничен ENI/IP на инстанс.
  - **Отладка**: `tcpdump`, `ip`, `ss` внутри netns пода — нужно уметь (`nsenter`, `kubectl debug`).
  - **Смена CNI**: нетривиально, часто требует пересоздания кластера или простоя.
  - **Производительность**: overlay медленнее routing/eBPF, eBPF — самый быстрый.
  - **IPAM-конфликты**: неправильный CIDR → пересечение с VPC или другими сетями.
  - **`hostNetwork: true`** — поды вне CNI, не управляются NetworkPolicy.

- Отладка CNI
  ```bash
  # Конфиги CNI
  ls /etc/cni/net.d/
  cat /etc/cni/net.d/*.conf

  # Бинарники
  ls /opt/cni/bin/

  # Pod IP и интерфейсы
  kubectl get pod <pod> -o wide
  kubectl exec <pod> -- ip a
  kubectl exec <pod> -- ip route

  # В netns пода (если в образе нет утилит)
  nsenter -t <pid> -n ip a
  nsenter -t <pid> -n ss -tulpn

  # На ноде
  ip a | grep -E 'cni|veth|cali|cilium|flannel'
  ip route
  iptables -t nat -L -n -v   # или nft list ruleset

  # Логи CNI
  kubectl logs -n kube-system <cni-pod>
  journalctl -u kubelet | grep -i cni

  # Проверить CNI вручную (осторожно)
  CNI_COMMAND=ADD CNI_CONTAINERID=test CNI_NETNS=/var/run/netns/test \
    CNI_IFNAME=eth0 CNI_PATH=/opt/cni/bin /opt/cni/bin/calico < config.json
  ```

- Частые вопросы на собеседовании
  - **«Что такое CNI?»** — Спецификация и набор плагинов для настройки сети подов. Kubelet вызывает плагин (ADD/DEL/CHECK) при создании/удалении пода.
  - **«CNI — это демон?»** — Нет, плагин вызывается по требованию (exec), не работает постоянно. Демоны есть у конкретных CNI (calico-node, cilium-agent) — они управляют состоянием, но сам CNI-вызов — exec.
  - **«Что делает CNI при создании пода?»** — Создаёт veth-пару, назначает IP через IPAM, настраивает маршруты, bridge, DNS, возвращает результат kubelet.
  - **«Calico vs Cilium vs Flannel?»** — Flannel — простой overlay, без NetworkPolicy. Calico — BGP/eBPF, NetworkPolicy, encryption. Cilium — eBPF, L7 policy, observability (Hubble), замена kube-proxy, BGP.
  - **«Кто реализует NetworkPolicy?»** — CNI. Flannel — не поддерживает, Calico/Cilium/Antrea — поддерживают. Если CNI не умеет — политики игнорируются.
  - **«Что такое IPAM?»** — Подсистема выделения IP подам: host-local, dhcp, calico-ipam, cilium, whereabouts.
  - **«Как поды общаются между нодами?»** — Overlay (VXLAN/IP-in-IP), routing (BGP), или eBPF. Каждая нода имеет свой pod CIDR.
  - **«Что такое Multus?»** — Мета-CNI для нескольких сетевых интерфейсов в поде (NFV, telco, ML).
  - **«Может ли CNI заменить kube-proxy?»** — Да, Cilium (eBPF) и Calico (eBPF mode) могут.
  - **«Как отладить сеть пода?»** — `kubectl exec` + `ip`/`ss`, `nsenter`, `kubectl debug`, `tcpdump` на ноде, логи CNI.
  - **«Что такое MTU в overlay и почему важен?»** — Инкапсуляция уменьшает MTU (1450 вместо 1500), неправильный MTU → фрагментация и странные ошибки.

- Короткий ответ на собеседовании
  - CNI (Container Network Interface) — это спецификация и набор плагинов для настройки сети контейнеров в Linux. Когда kubelet создаёт под, он создаёт network namespace (pause-контейнер) и вызывает CNI-плагин командами ADD/DEL/CHECK, передавая JSON с параметрами. Плагин создаёт veth-пару, через IPAM выделяет IP, настраивает маршруты, bridge, DNS, возвращает результат. CNI отвечает только за сеть подов (L3/L4) — плоская сеть, каждый под с уникальным IP, без NAT. Service (kube-proxy), Ingress, DNS — отдельные механизмы, хотя Cilium умеет заменять kube-proxy. Популярные CNI: Calico (BGP/eBPF, NetworkPolicy, encryption), Cilium (eBPF, L7 policy, Hubble, замена kube-proxy), Flannel (простой overlay, **без NetworkPolicy**), Weave, Antrea, AWS VPC CNI (cloud-native), Multus (multi-network). NetworkPolicy реализуется CNI: если CNI не поддерживает — политики молча игнорируются. Виды: overlay (VXLAN, overhead, MTU 1450), routing (BGP, нативно), eBPF (Cilium, быстро, L7), cloud-native (ENI, лимиты облака). Отладка: `kubectl exec` + `ip`/`ss`, `nsenter`, логи CNI, `tcpdump`.

- Что запомнить железно
  - **CNI — спецификация + плагины**, не демон; вызывается по требованию (ADD/DEL/CHECK).
  - **Отвечает за сеть подов** (L3/L4), не за Service/Ingress/DNS.
  - **Плоская сеть**: уникальный IP на под, без NAT между подами.
  - **Каждая нода — свой pod CIDR**, маршрутизация — CNI.
  - **IPAM** — выделение IP: host-local, calico-ipam, cilium, whereabouts.
  - **NetworkPolicy реализует CNI**, Flannel — не поддерживает.
  - **Calico** — BGP/eBPF, NetworkPolicy. **Cilium** — eBPF, L7, Hubble, замена kube-proxy. **Flannel** — простой, без policy.
  - **Overlay (VXLAN)** — overhead, MTU 1450. **Routing (BGP)** — нативно. **eBPF** — быстро, L7.
  - **Multus** — multi-network в поде.
  - **`/etc/cni/net.d/`** — конфиги, **`/opt/cni/bin/`** — бинарники.
  - **`nsenter -t <pid> -n`** — зайти в netns пода для отладки.
  - **Cilium может заменить kube-proxy** (eBPF).
