# Что такое inode?
- Inode - структура метаданных файла в файловой системе Unix/Linux.
- Имя файла хранится не в inode, а в каталоге: запись "имя -> номер inode".
- В inode хранятся:
  - тип файла, права, uid/gid;
  - размер, timestamps: atime/mtime/ctime;
  - link count;
  - указатели на блоки данных / extents;
  - xattr/ACL и служебные поля.
- Номер inode уникален только в пределах одной ФС.
- Hard link — это ещё одно имя в каталоге, указывающее на тот же inode.
- Inode exhaustion: если закончились inode, новые файлы не создаются, даже если есть свободное место.
- Удаление файла:
  - `unlink()` удаляет имя из каталога и уменьшает link count;
  - inode и данные освобождаются, когда link count = 0 и нет открытых fd;
  - если файл открыт процессом, место не освобождается до закрытия.

# kubernetes. Что такое оператор в kubernetes? Как их делать?
- работают как клиенты API и расширяют его возможности
- задача - автоматизация и кодификация операционных знаний о приложении: как его развертывать, обновлять, масштабировать, бекапить и восстанавливать после сбоев
- это программное расширение, которое использует Custom Resources (CR) для управления приложениями и их компонентами, следуя принципу цикла управления (control loop)
- состоит из:
  - Custom Resource Definition (CRD) расширение API Kubernetes, которое определяет новый тип ресурса (например, `SampleDB` или `PostgreSQL`). CRD описывает, какие поля и настройки могут быть у пользовательского ресурса
  - Controller: непрерывно отслеживает изменения пользовательских ресурсов и приводит реальное состояние системы к желаемому (reconciliation)
- При создании экземпляра CR (например, `SampleDB`), контроллер видит это и автоматически создает необходимые ресурсы Kubernetes (StatefulSet, PersistentVolumeClaims, Job и т.д.), а также управляет их жизненным циклом
- как создать оператор:
  - Operator SDK. на базе Kubebuilder. Go, Ansible, Helm. Самый распространенный путь для «классических» операторов на Go
  - Kubebuilder. Go. Часто используется напрямую или как основа Operator SDK; предоставляет каркас проекта и генерацию кода
  - Java Operator SDK. Готовый фреймворк для написания операторов на Java
  - KubeOps. SDK для создания операторов на платформе .NET
  - cdk8s-operator. TypeScript, Python и др. работает на конструкциях CDK8s
- пример создания на Kubebuilder
  - установить: `Go (1.24+), kubectl, Docker, Minikube, Kubebuilder`
  - инит проекта: `kubebuilder init --domain example.com --repo github.com/yourname/namespace-labeler`
  - создать API (CRD): `kubebuilder create api --group apps --version v1 --kind NamespaceLabeler`
  - kubebuilder сгенерирует структуры для CRD и заготовку контроллера
  - в сгенерированном файле `controllers/namespacelabeler_controller.go` нужно реализовать функцию `Reconcile`. Она будет вызываться при создании или изменении ресурса `NamespaceLabeler`. Внутри функции вы описываем, какие действия должен выполнить оператор (например, добавить метки `team` и `env` к целевому namespace)
  - Сборка и развертывание:
```bash
make docker-build docker-push IMG=yourrepo/namespace-labeler:tag
make deploy IMG=yourrepo/namespace-labeler:tag
```
  - после этого оператор запустится в кластере и начнет отслеживать пользовательские ресурсы
  - создать экземпляр CR:
```yaml
apiVersion: apps.example.com/v1
kind: NamespaceLabeler
metadata:
  name: my-labeler
spec:
  labels:
    team: backend
    env: production
```
  - оператор автоматически применит эти метки ко всем новым namespace (или к указанному, в зависимости от логики).
- Для простых задач (например, автоматическое добавление меток) достаточно минимального контроллера; для сложных stateful-приложений (базы данных, очереди) оператор может управлять десятками связанных ресурсов.

# kubernetes. Что такое pod?
- под это объект описывающий запуск одного или более контейнера на ноде
- минимальная единица планирования
- все контейнеры из одного пода находятся в одной подсети одного сетевого неймспейса и разделяют томы хранилища
- каждый под имеет свой собственный уникальный внутренний IP-адрес
- PID namespace по умолчанию отдельный, но можно включить `shareProcessNamespace: true`.
- В каждом поде есть служебный **pause-контейнер** (sandbox). Он держит network namespace, чтобы контейнеры могли перезапускаться без потери IP.

# Диски и файловая система. Что такое LVM? Для решения каких задач он предназначен?
- с помощью `LVM` можно объеденить несколько блочных устройств в `Volume Group (VG)`
- внутри `VG` создаются `Logical Volumes (LV)`
- и эти логические тома можно разбить как нам нужно на тома с файловыми системами
- впоследствии `Volume Group` можно расширять новыми блочными устройствами 
- и соответственно увеличивать LV и тома с файловыми системами:
- `resize2fs` для `ext4`, `xfs_growfs` для `XFS`
- всё это можно делать на лету, без перезагрузки системы и размонтирования разделов
- есть возможность создавать быстрые снапшоты
- также средствами LVM можно создать программный рейд
- Сжимать сложнее: XFS не умеет shrink вообще; ext4 умеет, но только offline (размонтировать, e2fsck, resize2fs, lvreduce)
- Порядок при расширении: LV → ФС. При сжатии: ФС → LV

# Cеть. Как работает NAT, зачем он нужен? Частные и публичные IP-адреса. NAT Network Address Translation
- NAT это средство меняющее адреса назначения/отправителя в соответствеии с заданными этому NAT правилами. есть множество реализаций например masquerade
- состоит из SNAT и DNAT соответственно
- например у нас кластер и в нём есть машина с внешиним адресом. на внешний адрес прилетает запрос попадающий под правило. нат меняет адрес назначения на адрес например веб сервера в кластере, пересылает, получает ответ, меняет адрес отправителя на свой внешний и отправляет обратно клиенту
- все такие соединения записываются в таблицу conntrack
- частные адреса это адреса в диапазоне 192.168.0.0/16, 172.16.0.0/12 и 10.0.0.0/8
- почти все остальные адреса (кроме технических, зарезервированных) используются как внешние
- есть  ещё carrier-grade NAT CGNAT. этот механизм импользуют провайдеры

# linux. Опишите, что происходит (с точки зрения процессов), при выполнении любой команды в консоли, например: ls -l
- системный вызов fork()
- создаётся копия процесса консоли
- копия процесса выполняет команду с помощью системного вызова exec().
- После выполнения команды, копия процесса выполняет системный вызов exit()
- оригинальному процессу консоли отправляется сигнал SIGCHLD
- во время работы копии процесса, оригинальный процесс находится в ожидании из-за системного вызова wait()

# Аббревиатура ACID, как расшифровывается?
- ключевые свойства транзакции
- atomicity атомарность (транзакиция либо выполняется либо нет)
- consistency согласованность (любая транзакция переводит из допустимого в допустимое состояние)
- isolation изоляция (параллельные транзакции не оказывают влияния друг на друга)
- durability устойчивость (если транзакция завершена успешно, записанные ей изменения не пропадут даже в случае аппаратноги или системного сбоя)
- Для атомарности и устойчивости: Используются журналы предзаписи транзакций (например, WAL — Write-Ahead Log) и механизмы отката (Rollback)

# Сеть. Что такое TLS и SSL?
- это протоколы шифрования
- SSL1 не был выпущен и SSL2 был с уязвимостями, SSL3 прожил до 2014 года, после инцидента запрещён. TLS1.1 устаревший с 2021, TLS1.2 ещё актуален TLS1.3 2018 - современный, безопаснее и быстрее
- TLS является основой например HTTPS, openvpn wireguard
- упрощенно: у клиента есть набор корневых сертификатов CA, а у сервера открытый сертификат CRT и закрытый ключ KEY
- выпускает все эти связанные сертификаты удостоверяющий центр
- и при подключении клиента к серверу (при условии что key не был скомпроментирован) - клиент гарантированно общается с нужным сервером (нет подмены), и трафик зашифрован (нет риска MITM)
- в общем случае TLS использует стандарт формата сертификатов x509

# Диски и файловая система. Какую файловую систему выбрать ext4 или xfs?
- преимущество xfs - динамические айноды, можно записывать большое количество мелких файлов, хорошие показатели при многопоточной записи, что необходимо для s3 хранилищ, например minio, также поддерживает очень большие разделы (500тб) (но эти ограничения обусловлены ОС. теоретически они больше) и файлы, хорош для многопоточной нагрузки, 
- недостаток xfs - раздел нельзя уменьшать
- преимущество ext4 - раздел можно уменьшить
- недостаток - статическое количество inode задаваемое при создании файлловой системы. значение inode-per-file - 16кб по умолчанию. что для обычных систем (не s3) обычно достаточно. максимальный раздел 50 тб

# Что такое файловый дескриптор?
- это номер, который процесс получает, когда открывает файл
- процесс не работает с файлом напрямую
- он говорит ядру: «открой мне файл /var/log/app.log». Ядро открывает, создаёт внутри себя структуру для работы с этим файлом и возвращает процессу номер — это и есть FD.
- Дальше процесс говорит не «прочитай мне файл по пути /var/log/app.log», а «прочитай мне из файла номер 3». Так проще и быстрее: ядру не надо каждый раз искать файл по имени
- FD 0,1,2 это stdin, stdout, stderr
- после закрытия close() FD не действителен
- у каждого процесса своя таблица FD
- ядро по FD находит inode и работает с файлом. Процесс inode не видит — он видит только свой номер
- для связи FD и inode используется struct file и open file description

# Что такое open file description?
- «карточка открытого файла» которую ядро создаёт при open() и хранит у себя. 
- представлена структурой `struct file` (VFS объект)
- описывает состояние работы с файлом
- содержит:
  - Где мы сейчас в файле — текущая позиция чтения/записи (offset).
  - Как открыт файл — только читать, только писать, дописывать в конец и т.д.
  - Ссылка на inode — чтобы ядро знало, с каким файлом вообще работаем.
  - Ссылка на файловую систему — ext4, XFS, NFS и т.д.
- один файл можно открыть дважды и для каждого FD будет свой OFD и они могутт работать независимо. либо два FD могут ссылаться на один OFD

# linux. Что такое зомби-процесс? Как можно создать такой процесс? Процесс создания зомби-процесса
- зомби процесс это процесс, коротый завершился, но по какой то причине его статус завершения не был считан родительским процессом.
- фактически это не процесс, а просто запись в  списке процессов
- при ошибках программирования список процессов может закончиться (32000-419000)и система не сможет запустить новых
- чтобы создать зомби - нужно создать дочерний процесс из основного, тут же его завершить, и, например "усыпить" родительский. пока родительский спит - дочерний в стоянии зомби
- чтобы убить зомби - родитель жолжен вызвать wait()
- сирот ядро подчищает

# Диски и файловая система. Для чего необходимы файлы /etc/fstab, /etc/mtab, /etc/mdadm/mdadm.conf?

- при сборке контейнера порядок слоёв оптимально определять таким образом чтобы часто меняемые слои идут последними, и наоборот
- цепочка слоёв описана в image manifest (JSON), где перечислены SHA256 digest'ы слоёв по порядку
- таким образом при изменениях не нужно перезаливать весь образ при push/pull. достаточно перелить изменнные слои
- Каждый слой это результат одной инструкции Dockerfile, которая меняет файловую систему (RUN, COPY, ADD). FROM не создаёт слой — он берёт готовый образ как основу. Инструкции ENV, LABEL, EXPOSE, WORKDIR, CMD, ENTRYPOINT создают metadata-only слои — они меняют конфиг образа, но не файловую систему.
- OverlayFS — это union-файловая система в ядре Linux. Она «склеивает» несколько директорий (слоёв) в одну виртуальную, не копируя данные

# Python Что такое декоратор?
- которая принимает другую функцию, оборачивает её и возвращает новую функцию с расширенным поведением, не меняя исходный код.
- например роуты в flask
- можно для простого примера описать логгер, таймер, retry, кэш
```python
import functools, time

def timed(f):
    @functools.wraps(f)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return f(*args, **kwargs)
        finally:
            print(f"{f.__name__} took {time.perf_counter() - start:.3f}s")
    return wrapper

@timed
def slow():
    time.sleep(0.5)

slow()
# slow took 0.500s
```

# Что такое CPU pinning?
- это привязка потоков процесса к определённым ядрам процессора
- в противном случае потоки будут распределены алгоритмом балансировки что вызывает следующие проблемы:
  - потеря cache locality — данные, которые были в L1/L2, остаются на старом ядре;
  - NUMA-эффекты — задача может уехать на ядро в другом NUMA-узле, а память останется в старом → remote memory access;
  - разделение ресурсов с другими задачами на том же ядре.

# Что такое разделяемая память?
- это один из вариантов реализации межпроцессного взаимодействия
- самый быстрый вариант потому что процессы пишут напрямую, а не через ядро как в случае с pipe/socket
- сама по себе не следит за синхронизацией, поэтому может возникнуть гонка данных. чтобы решить эту проблему следует использовать примитивы синхронизации: блокировки, семафоры, мьютексы, futex
- используется в СУБД, веб-серверах, кэшировании, ML (PyTorch)
- докер по умолчанию выдёт 64мб контейнеру, из за чего могут возникать ошибки. можно увеличить --shm-size=1g
- в kubernetes это volume emptyDir

# Что такое семафоры, мьютексы, futex?
- примитивы синхронизации
- Mutex = MUTual EXclusion. Даёт эксклюзивный доступ: только один поток в критической секции. Остальные ждут. Кто захватил — тот и должен отпустить.
- Семафор — счётчик. не «принадлежит» потоку, а просто считает, сколько разрешений осталось. wait() / P() / down() — уменьшить счётчик. Если 0 — ждать. 
post() / V() / up() — увеличить счётчик, разбудить ждущих. бывает двоичный counting
- Futex = Fast Userspace muTEX. Это низкоуровневый механизм ядра Linux, на котором построены мьютексы и семафоры в glibc и других библиотеках.

# Базы данных. Индексация. Зачем она и как работает?
- Primary Key (или _id в MongoDB) автоматически получает уникальный индекс
- идея похожа на inode — отдельная структура (обычно B-tree или hash таблица, есть другие структуры), указывающая на данные строку с данными, но в БД индекс опционален и строится по конкретному полю
- также, для больших таблиц/коллекций важно индексировать поля, по которым фильтруют, сортируют, джойнят, и где индекс реально используется планировщиком. это нужно для ускорения
- существуют разные типы индексов для разных типов и структур данных
- позволяет находить строки без полного перебора таблицы
- ускоряет чтение, замедляет запись и занимает место. не надо индексировать всё

- в случае потери лидера - через консенсус-протокол выбирается новый лидер из оставшихся членов и система продолжает работать

# Базы данных. Что такое хранимые процедуры?

# Linux. Зачем нужна система инициализации? Какие системы инициализации используются в современных дистрибутивах?
- система инициализации загружается сразу после загрузки ядра имеет PID 1, запускает все демоны, и работает пока работает система.

  - OpenRC (используется в Gentoo, Alpine Linux), runit и s6 (для контейнерных окружений и минималистичных дистрибутивов)

# Docker. Что такое docker commit?
- это команда, при выполнении которой все изменения сделанные в файловой системе после запуска контейнера станут новым read-only слоем нового образа контейнера
- полезно, когда нужно срочно что то изменить в существующем образе а Dockerfile утерян, отладки.эксперимента, вендор отдал только образ, легаси. 
- в целом антипаттерн:
  - Не воспроизводимо
  - Не версионируется в Git
  - Раздувает образ
  - Безопасность, секреты — можно случайно закоммитить токены, пароли, ключи, которые были в контейнере
- но правильно в этом случае использовать Dockerfile. есть инструменты позволяющие восстановить Dockerfile (по большей части) из образа контейнера:

  - whaler, dockerfile-from-image, dfimage — обратная сборка Dockerfile (частично, неточно)

# Infrastructure as Code. Что это такое?
- это подход, при котором инфраструктура (сети, серверы, балансировщики, базы данных) описывается в конфигурационных файлах, а не настраивается вручную через веб-интерфейсы или скрипты. Этот код хранится в системе контроля версий (например, Git), проходит проверки и применяется автоматически.
- Ключевые преимущества:
  - Воспроизводимость: Одна и та же конфигурация каждый раз создаёт идентичную среду, что исключает ошибки, связанные с «человеческим фактором».
  - Скорость и масштабируемость: Можно быстро развернуть целую инфраструктуру или создать её копию для тестирования.
  - Управление версиями: Все изменения инфраструктуры фиксируются в Git. Это даёт возможность проводить ревью, откатываться к предыдущим версиям и видеть полную историю изменений.
  - Безопасность и соответствие: Подход «инфраструктура как код» позволяет сканировать конфигурации на наличие уязвимостей и проверять соответствие политикам безопасности до развёртывания.

# Terraform. Зачем нужен. Аналоги. Чем выделяется.
- фактически стандарт для декларативного управления инфраструктурой, особенно в мультиоблачных средах
- Основной рабочий процесс состоит из трёх этапов: Write (написание конфигурации), Plan (создание плана изменений) и Apply (применение плана).
- Файл состояния (State): Terraform хранит состояние управляемой инфраструктуры в специальном файле (terraform.tfstate). Этот файл сопоставляет ресурсы из вашей конфигурации с реальными объектами в облаке. Он критически важен для понимания того, что уже существует, и что нужно изменить.
- Провайдеры (Providers): Это плагины, которые позволяют Terraform взаимодействовать с API различных платформ: облаков (AWS, Azure, GCP), локальных систем (VMware), SaaS-сервисов (Cloudflare, GitHub) и других. Именно благодаря провайдерам Terraform обеспечивает свою мультиоблачность.
- Модули (Modules): Это переиспользуемые блоки конфигурации, которые позволяют инкапсулировать сложные архитектуры и использовать их многократно, как функции в программировании.
- аналоги:
  - OpenTofu	Декларативный (HCL)	Open-source форк Terraform. Появился после смены лицензии Terraform на BSL. Полностью совместим с HCL и провайдерами Terraform (начиная с версии 1.5.x).
  - Pulumi	Императивный (Code-first)	Позволяет описывать инфраструктуру на языках программирования общего назначения (TypeScript, Python, Go, C#). Даёт больше гибкости для сложной логики, но требует навыков программирования.
  - AWS CloudFormation	Декларативный (YAML/JSON)	Нативный инструмент AWS. Обеспечивает глубокую интеграцию с сервисами AWS, но сильно привязывает к этому облаку (vendor lock-in).
  - Ansible	Процедурный (YAML)	Инструмент управления конфигурацией, а не провижининга. Он не создаёт инфраструктуру с нуля, а настраивает уже существующие серверы (устанавливает ПО, управляет файлами). Работает без агентов.
  - Crossplane	Декларативный (Kubernetes-native)	Управляет облачными ресурсами через Kubernetes API (CRD). Позволяет использовать GitOps-подход для инфраструктуры, делая Kubernetes единой контрольной точкой.

# Kubernetes. Crossplane. Что это такое, и зачем нужно?
- инструмент превращающий Kubernetes в универсальную панель управления для любых облачных ресурсов, не только для контейнеров.
- позволяет управлять внешними ресурсами (например, базой данных AWS RDS, бакетом S3 или балансировщиком GCP) точно так же, как вы управляете подами или деплойментами внутри кластера Kubernetes — через YAML-манифесты и kubectl
- достигается за счёт расширения API Kubernetes с помощью Custom Resource Definitions (CRDs). Crossplane устанавливает свои контроллеры, которые следят за этими новыми типами ресурсов и приводят реальную инфраструктуру в соответствие с описанным в них желаемым состоянием
- так же как и terraform реализует подход infrastructure-as-a-code но не является заменой. скорее дополнением. больше подходит как инструмент для создания платформы для разработчиков
- ключевые компоненты:
  - Providers (Провайдеры): Это плагины, которые «учат» Crossplane общаться с API различных облачных платформ (AWS, GCP, Azure и др.). Провайдер устанавливает набор Managed Resources (Управляемых ресурсов) — это CRD, которые представляют собой один-к-одному реальный облачный ресурс (например, RDSInstance или S3Bucket).
  - Managed Resources (Управляемые ресурсы): Это низкоуровневое представление реального облачного ресурса в Kubernetes. Вы можете создавать их напрямую, но на практике это используется редко, так как они слишком детализированы.
  - Composite Resources (XR) и CompositeResourceDefinitions (XRD): Это сердце платформенного подхода Crossplane.
  - XRD (CompositeResourceDefinition) — это, по сути, схема вашего «золотого пути». Платформенная команда создаёт XRD, который определяет высокоуровневый API для разработчиков. Например, Database с полями size, engine, region.
  - XR (Composite Resource) — это экземпляр, созданный по этой схеме. Разработчик пишет простой манифест kind: Database, и не заботится о том, что под капотом будут созданы RDS, Security Group, Subnet Group и Secret с паролем.
  - Compositions (Композиции): Это «рецепт» или «шаблон», который объясняет Crossplane, как именно из одного высокоуровневого XR (например, Database) развернуть набор низкоуровневых Managed Resources (RDS + Security Group + Secret и т.д.). Композиции позволяют инкапсулировать всю сложность и лучшие практики безопасности.

# Базы данных. ClickHouse. Чем отличается от других бд? Где лучше применять?
- колоночная аналитическая СУБД с открытым исходным кодом, созданная для выполнения сложных аналитических запросов (OLAP) по огромным объёмам данных с максимально возможной скоростью
- хранит данные колоночно а не построчно
- за счёт этого достишается экстремальная производительность на чтение: Это главная цель ClickHouse. Это достигается за счёт векторизованных вычислений (обработка блоками, а не по одной строке) и параллельной обработки на всех ядрах CPU
- специализация на аналитике (OLAP), а не транзакциях (OLTP)
- поддерживает шардирование и репликацию 
- колоночное хранение также обеспечивает эффективное сжатие данных
- аналоги: Apache Druid, Pinot

# Базы данных. ElasticSearch. Чем отличается от других бд? Где лучше применять?
- распределённый поисковый и аналитический движок, созданный на базе Apache Lucene. 
- оптимизирован не для транзакций, а для максимально быстрого поиска по тексту и анализа данных
- Инвертированный индекс: слово → список документов, где оно встречается
- не предназначен для обеспечения строгой согласованности (ACID) и не поддерживает транзакции в классическом понимании
- no-sql
- шардирование и репликация из коробки
- также применятся для Observability и анализа логов: Elasticsearch (в составе стека ELK/EFK) — это де-факто стандарт для централизованного сбора, хранения и анализа логов, метрик и трассировок
- Инвертированный индекс и агрегации требуют много памяти (RAM) и дискового пространства. Стоимость хранения может быть выше, чем у реляционных БД

# Какие сетевые модели существуют? Чем они отличаются?
- Мне известны модели OSI и DoD (TCP/IP)
- OSI разработана исторически раньше (скорее акадимечиская чем практическая модель) и состит из уровней:
  - 1. физический (сигнал в среде передачи)
  - 2. канальный (мак адреса, VLAN, одна сеть)
  - 3. сетевой (ip адреса, маршрутизация между сетями)
  - 4. транспортный (tcp/udp порты)
  - 5. сеансовый (RPC, sockets (частично), NetBIOS, PPTP, SIP (частично), TLS handshake (частично))
  - 6. представления (шифрование, сжатие, TLS (между 5 и 6))
  - 7. прикладной (http, ssh и другие)
- Модель TCP/IP (реальная модель, сформирована на практике, короче и лаконичнее)
  - 1. уровень доступа к сети (объединяет OSI L1 + L2)
  - 2. сетевой (ip адреса, VLAN, маршрутизация между сетями)
  - 3. транспортный (tcp/udp порты)
  - 4. прикладной (http, ssh, tls и другие)

# Что такое декларативный подход? 
- Описание желаемого состояния, а не последовательности шагов. Terraform, Kubernetes-манифесты, Ansible в declarative-режиме, Helm values
- Единый источник правды — Git. Всё, что не в Git, не существует
- Immutable infrastructure — не патчим серверы руками, а пересоздаём из кода.
- Версионирование — каждое изменение = коммит + PR + ревью.
- Идемпотентность — повторное применение даёт тот же результат

# Что такое GitOps?
- Git — единственный источник правды для состояния кластера/инфраструктуры.
- Оператор в кластере (ArgoCD, Flux) непрерывно сверяет реальное состояние с Git и приводит к нему.
- Pull-модель: оператор сам тянет изменения из Git, а не CI пушит в кластер. Это безопаснее — кластер не даёт внешний доступ.
- Drift detection: если кто-то руками поменял ресурс — оператор откатит.
- Аудит: кто, что, когда изменил — всё в истории Git.
- Rollback = git revert + оператор применит
- PR-based workflow: изменение → PR → ревью → CI-проверки (lint, plan, policy) → merge → деплой.
- Политики (Policy as Code): OPA/Gatekeeper, Kyverno, Conftest — проверяют манифесты на соответствие правилам до применения.
- Secrets management: не хранить секреты в Git. Sealed Secrets, External Secrets Operator, Vault, SOPS.
- Разделение окружений: отдельные директории/ветки/кластеры для dev/stage/prod, но один и тот же код с разными values.
- Дрифт-менеджмент: terraform plan в CI на регулярной основе, argocd app diff, алерты на drift

# Как тестировать изменения? Пирамида тестирования
- Локально / pre-commit — линтеры (tflint, hadolint, yamllint), форматтеры (terraform fmt, prettier), pre-commit hooks.
- Unit / статические проверки в CI — terraform validate, terraform plan (показать diff), helm template, kustomize build, kubeconform (валидация схем), conftest/OPA (политики).
- Секьюрити-сканы — trivy, grype (образы), checkov, tfsec, kics (IaC), gitleaks (секреты), semgrep (код).
- Интеграционные тесты — развернуть в ephemeral-окружении (namespace, kind, отдельный аккаунт), прогнать smoke-тесты, API-тесты.
- Test / Dev environment — первое реальное окружение, максимально похожее на прод.
- Stage / Pre-prod — копия прода (или максимально близко), с прод-данными (анонимизированными) или синтетикой.
- Prod — canary, blue/green, feature flags.

# Зачем в веб-приложении nginx в качестве фронтенда?
- nginx это зарекомендовавший себя годами, де-факто стандарт в качестве веб сервера
- написан на С, за счёт чего имеет высокую производительность и стабильность. один воркер поддерживает десятки тысяч соединенийй
- хорош в качетсве L7 reverse proxy: принимает соединение, разбирает HTTP, проксирует запрос на upstream, возвращает ответ. Клиент не знает, что за nginx стоит другой сервер
- также в качестве провайдера HTTPS
- можно с помощью него например удобно вывести в интернет поддомен (либо path). а внутри этот обратный прокси будет перенаправлять на любую внутреннюю машину, любой порт. своего рода "L7 маршрутизация/DNAT"
- имеет множество параметров, защищающих от атак. например медленных (буферизация), умеет ограничивать rate, connections, размер запроса, фильтровать по User-Agent/IP, интегрируется с fail2ban. Это снижает нагрузку от ботов и сканеров,
- ведёт подробное access логирование
- также хорош для отдачи статики
- можно использовать в качетс=стиве балансировшика
- им модно реализовать A/B-тесты, canary
- может проксировать grpc
- потребление памяти на порядок меньше Apache
- может перечитать конфигурацию без разрыва соединений
- альтернативы: envoy, HAProxy, Traefik, Caddy, Pingora

# Чем отличается GitOps от IaC?
- IaC — это широкий подход: инфраструктура описывается кодом, обычно в Git, и применяется через terraform apply, ansible-playbook или kubectl apply. 
- Это push-модель — CI или инженер запускает применение. 
- IaC не гарантирует, что реальное состояние совпадает с кодом прямо сейчас: дрейф обнаружится только при следующем plan. 
- GitOps — это частный случай IaC с конкретной операционной моделью: Git — единственный источник правды, а агент внутри кластера (ArgoCD, Flux) сам тянет изменения из Git и непрерывно сверяет реальное состояние с описанным, автоматически исправляя дрейф. 
- Это pull-модель, безопаснее для кластера, и даёт непрерывный drift detection. 
- Всякий GitOps — это IaC, но не всякий IaC — GitOps: Terraform из CI — IaC, но не GitOps. 
- Terraform можно сделать GitOps через Atlantis или Flux/Crossplane. 
- GitOps в первую очередь Kubernetes-центричен, не решает миграции БД, секреты и динамическую конфигурацию — для них нужны отдельные инструменты.

# чем отличается CI от CD ?
- CI — Continuous Integration — это практика частых мержей в основную ветку с автоматической сборкой и тестами на каждое изменение. Цель — быстрая обратная связь и борьба с merge hell. 
- CD имеет два значения. 
- Continuous Delivery — это CI плюс автоматическая доставка артефакта в stage, но деплой в прод по кнопке, с ручным подтверждением. 
- Continuous Deployment — это когда каждое зелёное изменение автоматически едет в прод без человека. 
- Delivery — про готовность к проду с контролем, Deployment — про максимальную скорость с автоматикой. 
- Для Continuous Deployment нужны зрелые тесты, feature flags, canary, мониторинг и быстрый rollback. 
- CI/CD — это практики, а не инструменты; Jenkins или GitLab CI — лишь реализация.

  - 4xx	Client Error ошибка клиента
  - 5xx	Server Error — ошибка сервера

# Что такое NUMA?
- Non-Uniform Memory Access, доступ к неоднородной памяти, архитектура построения многопроцессорных серверов
- В отличие от старых систем, где все процессоры имели равный доступ ко всей памяти (UMA), в NUMA-системе память физически разделена на блоки, и каждый блок привязан к своему процессору (или сокету).
- NUMA-узел по сути «кластер» внутри одного физического сервера, который состоит из: 
  - определённой группы процессорных ядер (например, ядра 0–15)
  - Локального блока оперативной памяти (RAM), который физически расположен ближе всего к этим ядрам.
- Процессор может получить доступ к памяти любого узла, но доступ к «своей» (локальной) памяти происходит значительно быстрее, чем к «чужой» (удалённой, remote). Разница в задержке (latency) может быть в разы.

# Жизненный цикл linux процесса
1. Создание: fork() / clone() → копия через COW, новый PID.
2. Замена образа: exec() → новая программа, PID сохраняется.
3. Выполнение: R (running/runnable).
4. Ожидание: S (interruptible), D (uninterruptible I/O).
5. Остановка: T (SIGSTOP / Ctrl+Z), SIGCONT возобновляет.
6. Завершение: exit() → Z (zombie), SIGCHLD родителю.
7. Пожинание: wait()/waitpid() → X (dead), запись удалена.
- Состояния:
  - R — running / runnable
  - S — sleeping (interruptible)
  - D — uninterruptible sleep (I/O), kill -9 не работает
  - T — stopped (SIGSTOP, Ctrl+Z)
  - Z — zombie (завершён, не пожали)
  - X — dead (почти не видно)
- Сигналы
 - SIGTERM (15) — graceful, перехватывается
 - SIGKILL (9) — жёстко, НЕ перехватывается
 - SIGINT (2) — Ctrl+C
 - SIGSTOP — остановка, НЕ перехватывается
 - SIGCONT — продолжить
 - SIGCHLD — ребёнок завершился
 - SIGHUP (1) — reload / терминал закрыт

# Что такое socket?
- Это endpoint (конечная точка) для обмена данными между процессами
- IP:порт на одной стороне + IP:порт на другой стороне + протокол. Пара сокетов образует соединение.
- используется для сетевого и межпроцессного взаимодействия
- В Linux сокет — это файловый дескриптор, с которым можно работать как с обычным файлом (read/write/close)
- На одном порту может быть много сокетов (разные клиенты)
- Порт ≠ сокет. Порт — число, сокет — структура
- есть сетевые сокеты а есть юникс сокеты
- юникс сокет это файл, например /var/run/docker.sock
- юникс сокет в отличии от tcp сокета на локалхост безопаснее и быстрее

# Чем контейнеризация отличается от виртуализации?
- виртуализация предоставляет виртуальные устройства, диски, BIOS, на которую устанавливается полноценная ОС со своим ядром. требует больше ресурсов. безопаснее, меньше поверхность атаки. требуются когда нужна другая ОС, ядро.
- контейниризация обеспечивает изоляцию процесса (с помощью неймспейсов PID, NET, MNT, UTS, IPC, USER, CGROUP). контейнеры используют ядро хостовой ОС, своего ядра у них нет. только приложение и зависимости. образы и контейнеры намного легче. быстрее разворачиваются и требуют меньше накладных ресурсов. предпочтительнее когда нужна скорость развёртывания и легковесность
- существуют гибридные реализации: Kata, gVisor, Firecracker, KubeVirt

# Чем отличается хардлинк от софтлинк?
- Софтлинк это самостоятельный файл-ссылка c собственным inode, содержимое которого - указатель на другой файл
- Софтлинк в одной файловой системе может указывать на файл в другой файловой системе
- Софтлинк может быть "битым" (если целевой файл удален)
- Можно делать софтлинк на директорию
- Хардлинк это запись в файловой системе с ссылкой на inode, ещё одно имя для того же inode
- В каждой inode есть счётчик отображающий сколько хардлинков ссылается на неё
- Когда все хардлинки будут удалены, счётик достигнет нуля и нет процессов, которые держат файл открытым - данные и inode будут удалены.
- lsof +L1

# Что такое load average?
- Экспоненциально сглаженное среднее число задач в R (running/runnable) + D (uninterruptible sleep) за 1/5/15 минут.
- минута самый отзывчивый, реагирует на всплески. 5 минут — компромисс. 15 минут  самый сглаженный, показывает тренд.
- зависит от количества ядер. допустим у нас 4 ядра. число 4.0 означает что загрузка процессора около 100%
- если число превышает например в 2 раза - скорее всего очередь задач накопилась из за I/O устройств (диск/сеть)

# Ситуация: системный диск забит на 99,9% Твои действия?
- смортрю df -h чтобы проверить какая фс забита
- начиная с корня выполняю команду `du -sh ./*` и проваливаюсь в подозрительно большие папки (есть утилита ncdu которой можно сделать это быстрее, но не факт что она установлена и получится установить на забитый диск)
- обычно корень проблем - какой нибудь большой лог в /var/log/
- удалить его обычно либо не получится - он будет занят процессом, либо файл удалится а место - нет, пока не будет завершен процесс
- каким процессом занят можно узнать утилитой lsof
- убить этот процесс скорее всего нельзя, критичный. можно файл занулить. `cat /dev/null > файл` и свободное место на диске будет увеличено или `truncate -s 0 file`
- Проверить удалённые, но открытые файлы `lsof +L1` и обнулить `truncate -s 0 /proc/<pid>/fd/<n>
- если лог важный и есть возможность - копировать на другой диск
