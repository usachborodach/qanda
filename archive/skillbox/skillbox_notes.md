# модель сети
- контейнеры внутри пода иеют один уникальный айпи
- поды могут общаться с любыми другими подами используя адреса без нат
- айпи который видит контейнер должен быть быть таким для всех

#
- в современном линуксе каждый процесс работает в своём сетевом неймспейсе
- все контейнеры в поде находятся в одном неймспейсе
- в каждом поде есть служебный контейнер pause чтобы держать сетевой неймспейс открытым
- поды подключаются к хосту с помощью veth
- на разных хостах используются разные сети для подов
- CNI Container Network Interface
- Calico, Flannel, Weave Net, Cillium
- Flannel, например запускается как daemonset
- kubectl describe configmaps kube-flannel-cfg -A
- Flannel создаёт на нодах свои интерфейсы
- для ограничения доступа используют NetworkPolicy (Flannel не поддердживает)
- Calico поддерживает NetworkPolicy
- это всё про взаимодействие между подами
- а для доступа извне - Service и kube-proxy
- ipvs работает быстрее iptables
- kubectl port-forward service/myservice 10000:80
- кроме  СlusterApi есть NodePort, LoadBalancer и Ingress
- СlusterApi доступен только внутри кластера
- NodePort открывает порт на внешнем интерфейсе каждой ноды (и нужно обращаться по адресам нод)
- LoadBalancer (для облачных балансировщиков) один адрес снаружи - перенаправляет по нодам. облачный провайдер следит за ними. это может быть дорого
- HostNetwork: занимает внешний адрес ноды на котором запущен 

# Ingress
- как по мне очень напоминает обратный прокси nginx (в итоге им и является)
- может перенаправлять по роуту/эндпоинту url
- может по поддомену, домену
- может переписывать/скрывать части url от подов
- Ingress от Kebernetes: на основе nginx, самый простой
- Ingress от nginx: ha, есть платный
- Traefik: go, rev-proxy, load-balancer, canary
- HAProxy
- Kong, основан на nginx, имеет много модулей

# service mesh и istio
- с помощью service mesch модно жно вынести балансировку, TLS, метрики, хелсчеки
- curcuit breaker: механизм отключающий сбоящие сервисы
- для етого нужен прокси и в подавляющем случае это envoy (динамичный в отличии от nginx)
- сервис меши: istio, linkerd, consul, traefik mesh, kuma, aws app mesh
- istio запускает envoy как init контейнер во все поды (c лейблом)
- istio control plane (istiod): pilot (прокси), citadel (шифрование), galley(конфигурация)

# установка istio
- istioctl (производит проверки)

- устанавливает свои компоненты в istio-system
- istioctl kube-inject -f <pod_manifest.yml> > <pod_manifest.yml>
- статья по линуксовым сетевым неймспейсам: digging into linux namespaces
- посмотреть адрес в сетевом неймспейсе: nsenter -t <pid> -n ip a
- установить nsenter: apt install util-linux

# 11. Kubernetes для непрерывной поставки. Интеграция с CI-сервисом
# 11.1 Деплоймент-стратегии
- стратегии обновления:
  - rolling update (неприменим при бд миграциях)
  - recreate (даунтайм)
  - canary (постепенное переключения трафика. управляется количеством подов)
  - blue/green (постепенное переключения трафика. управляется процентным соотношением именно трафика)

# 11.2 Liveness, Readiness и Startup probes (07:30)
- запуск команды, http запрос, tcp подкючение
- health проверки:
  - liveness (если не проходит - контейнер убивается)
  - readiness (если не проходит - контейнер убирают из ендпоинтов)
  - startup (прекращает проверку после запуска контейнера)
