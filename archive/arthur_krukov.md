# компоненты control plane
- k8s api (rest, всё взаимодействие  между компонентами идёт через него)
- etcd (данные в виде kv db, кластерная)
- controller (общается только с api, проверяет на предмет новых манифестов, создаёт задания) есть контроллеры подов, деплойментов, репликасет и так далее
- sheduler (следит за заданиями, определяет на каком сервере кластера запустить под)
- kubelet (на нодах, исполняемый, запускает контейнеры)
- k-proxy (на нодах, контейнер-под, управляет сетями сервисов)
- service (распределяет трафик по нодам, вроде балансировщика)

- CSI (драйвер хранилища. Container Storage Interface, тоже есть разные)
- Ad controllers (Дополнительные контроллеры)

# deployment:

- replicas: количество
- seleсtor:
    matchlabels: (пример)
      app: такой-то

# replicaset:
- создаётся контроллером деплоймент
- создаётся при каждом изменении деплоймент
- в случае неуспеха можно откатиться к предыдущим replicaset
- по умолчанию хранится 10 штук

# политики перезапуска
- rollingUpdate (перезапуск следущего пода происходит после того как пройдут пробы предыдущего)
- recreate (сначала всё убивает, потом создаёт)
- можно вызывать вручную, либо например работают при изменении деплоймента
- rollingUpdate.maxSurge (необязательное. максимальное количество подов сверх желаемиого количество)
- rollingUpdate.maxUnaibailable - (необязательное. минимально допустимое количество подов)

# Service
- объект обеспечивающий доступ к портам непосредственно сервиса внутри контейнера
- прикручивается с помощью selectors по тегам
- port: какой порт service свящать с каким портом в контейнере
- чтобы высунуть service наружу: kubectl -n work port-forward svc/myfirstnginx 8080:80
- направляет запросы по очереди на каждый под. называется round-robin

# endpointSlice
- создаётся сервисом
- содержит массив адрес-портов контейнеров

---

# StatefulSet
- имеет уникальное предсказуемое (без хэшей) имя пода serviceName
- нужен для приложений которые должны сохранять состояние. например бд
- строгий порядок перезапуска подов (алфавитный). пока не запустится первый - не запустится второй.
- можно оподключать volume 

# HeadlessService
- spec: clusterIP: none
- позволяет обратиться к конкретному поду по днс имени

---

# DaemonSet
- запускает по одному поду на всех нодах
- не предусмотрен ключ replicas
- сервис к ним обычно не прекручивают. обычно они что то делают фоновое внутри и всё
- можно указать метки нод в nodeSelector

# Taint
- Формат key=[value]:Effect
- Эффекты: NoShedule (запрещает создание новых под), NoExecute (запрещает и удаляет существующие), PreferenceNoShedule (планировщик будет пытаться разместить, но это не гарантрировано)
- Если нужно разместить под - у него должен быть toleration. key, value, если нет value - operator: Exists, и соответствующий Effect
- taint вешается командой

можно ставить метки на ноды
не желательно использовать метку hostname

# Job
- нужен для одноразового запуска
- restartPolicy: (Never,  )
- backoffLimit - количество попыток. по умолчанию 6
- каждая следующая попытка с большим интервалом
- ttlSecondsAfterFinished - после этого таймаута джоб (и соответственно под) будет удалён

# CronJob
- для периодический джобов
- successfulJobsHistoryLimit
- failedJobsHistoryLimit

# Affinity
- nodeAffinity предпочтение размещения подов на нодах кластера
- podAffinity предпочтение размещения подов рядом с другими подами
- podAntiAffinity правила запрещающие рамещение подов рядом с другими подами
- параметры подов-нодов указывать селекторами
- есть жесткие и мягкие правила required и preffered
- preffered можно задавать weight

# podTopologySpreadConstraints
- задаёт разницу в количестве подов между зонами
- может учитывать и не учитвать Affinity и Taints

# volumes

- persistentVolumes: постоянные

# ConfigMap
- metadata: name
- data: kv
- а подам указать envFrom: имя конфигмапа. тогда весь конфигмап прикрутится
- либо можно прикрутить какое то определённое значение с помощью valueFrom
- immutable: запрет на правку конфигмапа на лету
- ConfigMap прикручивается как volume (директория ..ISOdatetime) и монтируется в нужную директорию
- если не установлен immutable - содержимое конфигмапа успешно заменится на лету
- можно примонтировать как один файл среди прочих

# Secret
- Base64
- Opaque(generic), kubernetes.ip/tls, kubernetes.ip/dockerconfigjson
- максимальный размер ConfigMap и Secret: 1mb, a annotation: 256кб
- stingData: строка, Data: base64
- kubernetes.ip/tls для хранения сертификатов
- dockerconfigjson: для доступа к docker-registry
- можно примонтировать как и Config Map как volume
- kubernetes secrets никак не шифруются так что к безопасности отношения особо не имеет

- можно использовать оперативную память

# DownwardAPI
- позволяет приложениям в контейнере получать информацию о самих себе и окружении
- например: metadata.name, metadata.namespace, status.podIP, spec.nodeName, spec.seviceAccountName, metadata.labels['<key>'], metadata.annotations['<key>']
- можно передать внутрь с помощью env (статический вариант)
- а можно передать с помощью volume (есть соответствующий тип volume: downwardAPI). (динамически)

# RBAC
- ограничения дрступа пользователей
- RoleBasedAccessControl
- один из способов аутентификации - сертификат
- контроллерам так же нужно давать права (токен)
- Role, ClusterRole
- привязщываются к неймспейсу
- после аутентификации прав к апи по умолчанию нет
- сертификат > пользователь > роль
- все поды имеют права сервис акаунта
- и нужно роль пользователя и сервис акаунта связать с помощью ClusterRoleBinding
- сгенерировать конфиг файл для подключения к кластеру и отдать пользователю
- контекстом связывается поьзователь с кластером. и можно добавить параметр "контекст по  умолчанию"

---

- rules в роли: apiGroups, resources, verbs
- в манифесте роли обязательно указывается неймспейс
- RoleBinding манифест связывающий роль и пользователя
- пример: ApiGroup: ['v1'], resources['pods'], verbs['list']
- соответствующие ошибки видит пользователь когда ему не хватает на что то прав
- чтобы запускать поды взаимодействующие с самим кубером - нужна учетка serviceAcccount с соотвествтвующими правами. для всех остальных хватит default аккаунта
- пользователи авторизуются сертификатом и связываются по CN а serviceAccount по токену
